# 证据与改进归属

## 先保存事实，再作判断

可用证据包括 ATT 命令与日志、项目状态、Survey/QA/WriteBack 报告、前后文件差异、用户截图与
触发步骤、获准的运行观察、源码调用关系和修复后的复验结果。记录具体发生了什么、对用户造成
什么影响以及什么修改改变了结果；不要把第一处报错位置直接写成根因。

## 把发现放到唯一责任位置

| 发现 | 归属 | 进入条件 |
| --- | --- | --- |
| 某个游戏的译名、地图、插件实例、存档或专用写回位置 | 该游戏任务材料 | 只服务当前游戏 |
| 同类游戏可直接采用的调查、翻译、漏翻返修或验收方法 | `skills/translate-with-att/references/` | 方法已经成功，适用特征和限制明确 |
| 执行者必须遵守的触发、读取顺序、状态选择或恢复动作 | 对应 `SKILL.md` | 执行方式确实发生变化，详细事实仍留在权威来源 |
| 重复出现且需要确定性执行的调查、转换或校验 | 对应 Skill 的 Python 工具与测试 | 已有当前消费者，工具能承担明确职责 |
| ATT 共享规则、状态、接口、错误或 CLI 行为缺陷 | 现行规格、Rust 实现和回归测试 | 根因属于产品实现，并已检查全部受影响调用方 |
| 发行包缺文件、资源不一致、默认配置或验收缺口 | 发行规格、同步或验收脚本 | 问题发生在发行边界，修复后验证完整发行内容 |
| 尚未确认的猜测、失败修法或可能改进 | 本轮监督汇报或开发任务候选 | 明确标出证据缺口，不写入权威经验 |

只改文档不能消除实现缺陷时，把文档经验和实现建议分别放到各自责任位置。只改当前游戏能够恢复
用户结果，但共享根因仍存在时，同时完成当前游戏返修并向开发者提出 ATT 改进建议。

## 经验收录条件

一项内容进入可分发经验前同时确认：

1. 证据能说明原问题、实际消费者和最终结果；
2. 采用的方法已经在真实任务中成功，失败候选没有伪装成推荐做法；
3. 删除游戏名、用户路径和具体译文后，仍能准确指导具有相同结构的项目；
4. 能指出下一位 Agent 在什么条件下读取，以及读取后采取什么行动；
5. 写明尚未覆盖的场景和哪些 ATT 行为变化后需要重新验证；
6. 没有复制规格、CLI 文档或代码已经负责的完整契约；
7. 不包含凭据、私人数据、存档内容或大段游戏原文。

同一次个案可以证明一个清楚、可复现的通用机制；证据只支持当前实例时，继续留在任务材料。

## 全局改进建议的最小内容

每项建议至少回答：

- 哪个真实任务暴露了什么用户问题；
- 根因位于源码、CLI、Python 工具、Skill、发行资源还是任务专用内容；
- 同一根因还影响哪些当前引擎、调用方或流程；
- 推荐修改什么，为什么由该位置负责；
- 用户可观察行为是否变化；
- 需要同步哪些测试、规格、指南、Skill 或发行内容；
- 用什么静态、单元、集成、端到端或用户实玩证据验收；
- 哪些风险、权限或产品选择需要开发者决定。

“全局视角”表示检查共享责任和全部当前影响范围，不表示无证据地扩大重构。修法只对单个插件或
游戏成立时，明确保持专用，不把它包装成 ATT 通用能力。

## 每轮结束时的处理顺序

1. 确认独立翻译任务完成当前游戏已获授权范围内的返修和静态验证；监督任务不接手执行；
2. 把需要开发者实机确认的场景列清楚；
3. 根据证据区分游戏事实、可复用经验和 ATT 产品问题；
4. 先向开发者汇报 ATT 改进建议，取得批准后再修改源码或发行工具；
5. 更新其他 Agent 确实会读取的 Skill 或 reference，并检查入口链接；
6. 说明本轮没有收录的候选及原因，避免未经验证的结论进入下一次任务。
