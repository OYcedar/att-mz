# 监督 ATT 真实翻译与持续改进

## 目标

组织“独立翻译任务执行 → 监督过程与结果 → 开发者实玩 → 根据反馈继续返修 → 改进 ATT 与复用经验”的持续过程。
当前游戏必须得到可测试译本；同类用户的 Agent 必须能从发行 Skill、参考文档和工具中直接采用已经验证的方法。

本 Skill 是 ATT 开发专用能力，源文件位于 `maintenance/skills/`，不得进入 ATT 发行包。
开始工作前完整读取[证据与改进归属](references/evidence-and-improvement-routing.md)，并遵守当前
仓库根 `AGENTS.md`。

## 区分四个角色

- 开发者选择 ATT 发行包、游戏、目标语言和范围，决定是否允许 Agent 启动游戏，并审批 ATT
  源码、工具包和发行资源的实质修改。
- 监督任务创建和跟进独立翻译任务，检查方向、状态、证据和风险，接收实玩反馈，提出 ATT
  改进建议并整理已验证经验。
- 独立翻译任务模拟真实用户的 Agent，只使用指定发行根及其文档、Skill 和工具完成汉化与返修，
  不读取监督任务的预设结论或源码仓库中的替代资源。
- 开发者实际游玩译本，把截图、场景、触发步骤、原文和期望结果作为下一轮输入；没有明确授权时，
  监督任务和翻译任务都不代替开发者实机操作。

### 监督任务的绝对边界

监督任务绝不参与任何游戏汉化执行。不得在监督会话中运行游戏项目的 ATT Init、Extract、
Translate、Manual、WriteBack 或 Lua 命令，不翻译文本，不编辑游戏专用 Rules、Manual、术语、
Placeholder、Generic 输入或写回脚本，不修改、复制或部署译本，也不启动游戏。翻译任务失败、
停止或方向错误时，只能把证据和纠正要求发回该翻译任务；不得为了加快进度在监督会话接手。

监督任务可以只读检查翻译任务的日志、状态和产物，可以维护本开发仓库中的监督 Skill、可复用
经验和改进建议，也可以只读分析 ATT 源码、规格和调用关系。这些行为不得写入或改变任何游戏
翻译项目。

## 启动独立翻译任务

只有开发者明确要求开启新任务时才创建用户可见的新任务。先从现有文件和发行信息确认以下事实；
只有无法查明且会改变结果或权限时才询问：

- 实际 `att.exe` 和发行根；
- 原版游戏根、游戏版本、补丁或 MOD；
- 目标语言、翻译范围和目标目录；
- Agent 是否获准启动游戏；
- ATT 实质修改是否仍需逐次审批。

给独立翻译任务的初始消息必须要求它：

1. 使用发行包中的 `skills/translate-with-att/SKILL.md`；
2. 在首次调查或每轮用户反馈返修前，读取发行包中的游戏类型经验索引和全部适用经验文件；
3. 只依赖指定发行根，不从源码仓库拼接程序、文档、Prompt 或工具；
4. 完成翻译、静态 QA、WriteBack 和获准范围内的验收，并报告自然路径、状态和未验证范围；
5. 保持原版只读，保留用户存档和活动配置；
6. 不修改 ATT 源码，把发现的产品或工具问题连同证据交给监督任务。

初始消息只提供执行所需事实和权限，不提供监督者尚未验证的根因、预设答案或候选修法。

## 监督执行

优先使用任务管理工具读取增量状态和等待结果，不在监督任务中运行任何游戏翻译命令。
检查以下事实：

- 是否使用指定发行包、原版和目标范围；
- 是否按发行 Skill 读取了适用经验，而不是凭聊天记忆执行；
- 是否遵守 ATT 项目租约、所有权、Manual、WriteBack 和发行目录契约；
- 命令失败、warning、Partial、Unavailable 和未验证范围是否被如实处理；
- 结论是否由实际产物、日志、静态检查或获准的运行观察支持；
- 是否出现重复操作、人工绕过、专用补丁或可以由共享能力消除的使用阻力。

发现方向错误或安全风险时立即向独立任务发送具体纠正信息。普通进度不频繁打断；任务等待外部
模型或长时间检查时使用等待机制。独立任务失败时继续由该任务诊断和恢复，监督者不得接手翻译。
监督者可以只读检查源码、规格、调用方和任务材料来确定根因与影响范围，但在开发者批准前不实施
ATT 实质修改。

## 处理开发者实玩反馈

把截图、场景、触发步骤、原文和期望结果当作新的运行证据。把证据发送给负责该游戏的原翻译
任务并唤醒它，不要在监督会话修复，也不要另建平行项目或丢失既有 ATT 状态。要求独立任务：

1. 定位真实消费者和文本所有者；
2. 判断应由 Builtin、Rules、Generic、Manual、字体或 WriteBack 排版负责；
3. 修复同一根因影响的当前范围，重新执行受影响的 Extract、QA 和 WriteBack；
4. 静态验证精确位置，并把实机复查项交回开发者；
5. 只声明已经访问或验证的范围。

监督者始终不启动游戏。开发者或获得明确授权的独立翻译任务负责运行确认；监督者不得把静态
通过写成运行通过。

## 提出 ATT 全局改进

每轮监督都检查问题是否应由 ATT 自身消除。建议范围包括：

- Rust 业务实现、共享契约、状态和错误语义；
- CLI 输入、输出、诊断和恢复方法；
- RPG Maker、Generic、字体、QA、运行观察等 Python 工具；
- 翻译 Skill、游戏类型经验和执行顺序；
- 发行资源、同步脚本、默认配置和验收流程；
- 跨引擎共享能力与各引擎独立职责。

每项建议写清实际证据、用户影响、根因和责任位置、当前受影响调用方、推荐修改、外部行为变化、
验证方法和风险。共享根因必须横向检查全部当前调用方和同语义实现；游戏特例保持在任务材料中。
如果代码或工具修改才能改善使用结果，不以文档提醒代替实现建议。开发者批准后，再按仓库规则
实施源码、测试、规格、Skill 和发行资源的最小完整改动。

## 整理可复用经验

每轮交付或返修结束后，按[证据与改进归属](references/evidence-and-improvement-routing.md)分类。
只有已取得证据、修法已经成功、去掉游戏名和本机路径后仍能指导同类任务的内容，才进入可分发
经验。经验必须写明适用特征、已验证方法、ATT 与 Agent 的分工、未验证范围和重新验证条件。

独立翻译任务继续使用发行包中的 `translate-with-att` Skill；监督者负责把新的通用经验写到该
Skill 会明确读取的位置。没有新增可复用事实时，不为制造记录而修改文档。

## 每轮汇报

向开发者简洁报告：

- 当前游戏得到什么结果，哪些范围等待开发者实机确认；
- 独立任务出现了哪些错误、重复操作或有效方法；
- 哪些事实只属于当前游戏，哪些已经整理成可复用经验；
- 建议修改 ATT 的哪些位置、原因、影响和验证方式；
- 哪些 ATT 修改等待批准，哪些已获批准并完成验证。
