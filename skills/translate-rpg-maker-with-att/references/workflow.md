# ATT RPG Maker 翻译工作要求

本文说明执行型任务怎样调查、选择能力、完成三个阶段并解释异常结果。ATT 的命令、字段、
API、状态、错误和恢复行为只由本次实际发布目录中的现行文档定义；本文只负责把用户目标
连接到应读取的资料和应验证的结果。

执行型任务进入任务清单前完整读取本文；进入某阶段、修改配置或处理异常时，再读取对应
部分和实际产品文档。只读请求按需要读取本文相关部分，不因此进入执行模式。

## 产品能力与文档路由

先读取发布根 `README.md` 和 `docs/README.md`。前者说明产品与输出边界，后者是现行文档
入口。随后按实际意图完整读取：

| 意图或事实 | 发布目录中的现行资料 |
|---|---|
| 了解运行时、任一命令、继续任务或运行方案 | `docs/runtime/README.md`、`docs/runtime/cli.md` |
| 选择或解析 `--config`、Profile、Client、Prompt 根 | `docs/runtime/configuration.md` |
| 调查 RPG Maker 项目和选择能力 | `docs/rpg-maker/README.md` |
| 建立项目、冻结来源、核对 engine 或 metadata | `docs/rpg-maker/init.md` |
| 提取 Builtin、Rules、Standard Lua 或 Managed 快照 | `docs/rpg-maker/extraction.md`，按需读取 `rules.md`、`lua.md`、`lua-cookbook.md` 与 `examples/README.md` |
| 翻译、Current、拒绝、人工候选 | `docs/rpg-maker/translation.md`、`terminology.md`、`prompts.md`、`docs/runtime/chat-completions.md` |
| 使用 Managed、低级 Lua 或独立项目 Lua | `docs/rpg-maker/lua.md`、`lua-cookbook.md`、`examples/README.md` |
| 启用或调查模型任务记录 | `docs/rpg-maker/task-records.md` |
| 写回、布局、Lua 候选和最终发布 | `docs/rpg-maker/write-back.md`、`docs/runtime/directory-publishing.md` |
| 解释任一命令的项目日志 | `docs/runtime/project-log.md` |
| 直接只读核对数据库、事务或 OutcomeUnknown | `docs/runtime/sqlite.md` |
| Init 或 WriteBack 的发布终态不明 | 对应阶段文档与 `docs/runtime/directory-publishing.md` |

诊断明确指出其他文档时继续读取，但不要预读与本次事实无关的全部 API。实际文档与本文件
不一致时，以实际文档为准并在任务清单记录差异。

## 从整个项目制定方案

创建或恢复任务清单前，先只读了解：

- 用户最终需要什么结果，哪些行为必须保持，在哪里停止；
- 游戏版本、补丁或 MOD 组合，以及运行时真正加载的目录和文件；
- 当前 ATT 项目、来源、配置、保存的运行方案、提取结果、译文和输出；
- 任务范围内玩家可见文本来自哪些数据库、事件、插件、脚本和自定义数据；
- 每类文本如何定位、需要哪些上下文、一个翻译单位包含什么、怎样写回；
- 提取、翻译和写回怎样证明处理的是同一内容；
- 哪些选择已有授权，哪些仍必须由用户决定；
- 主要风险、恢复位置和验证方法。

局部报错只是调查起点。先找出负责该含义的项目能力或配置，再检查全部真实使用位置和后续
影响。不会改变整体路线但仍未确认的事实，写成当前阶段调查 TODO。

### 能力选择

按文本语义和写回关系选择当前发布真正支持的能力：

| 文本情况 | 首选能力 | 需要确认的边界 |
|---|---|---|
| 文档明确覆盖的标准数据库和事件文本 | Builtin | 实际覆盖矩阵、自然顺序和排除字段 |
| MV 第一条消息行中的姓名 | Builtin 配合 MV dialogue rules | 不是独立 owner，只处理文档说明的位置 |
| 确定文件、字段、插件参数或事件参数路径 | Extract Rules | 能否完整表达解码、pattern、写回 recipe 和冲突 |
| 控制符、插件壳或不可改写跨度 | Placeholder | 只保护已形成 Unit 的内容，不新增提取位置，也不修复错误分组 |
| 一个完整 Value 对应一个 Standard 单元 | Extract Lua `replace_standard` | 身份、位置、上下文和单目标写回是否完整 |
| 可拆成独立 collection/unit，ATT 可以管理普通翻译任务 | Managed `ctx.translations` | unit 原子范围、metadata 与最终写回关系 |
| 私有 grammar、跨 unit 原子关系或特殊模型协议 | 低级 Lua 私有协议 | 脚本自行承担身份、协议、事务、状态、恢复和幂等 |
| 已有 Standard 人工译文 | 独立项目 Lua 的 Standard 人工候选 | 使用当前发行版的人工验收接口，不请求模型 |

代码形状相似不表示语义相同。Builtin、Rules、Standard Lua、Managed 和低级协议不得重复
拥有同一文本。Managed 能完整表达时不重写其通用翻译能力；Managed 不能保持项目语义时，
记录缺少的具体能力后再使用低级协议。

任务清单仍只有提取、翻译、写回三个阶段。Init 是独立产品命令，但在清单中属于提取阶段
建立或核对项目、冻结来源和 metadata 的前置 TODO。已有项目不机械重跑 Init；先核对保存
事实和本次真实需要。

## 提取

提取阶段先核对实际 Extract 运行方案。显式 owner 选择、空 Rules、零字节 Lua 和省略参数
可能改变、清除或复用不同项目状态；执行前必须按本次 `docs/runtime/cli.md` 解释，不凭上次
命令外形猜测。

阶段工作包括：

- 核对游戏来源、engine、实际加载位置、项目身份和来源冻结状态；
- 盘点任务范围内全部玩家可见文本，不把当前 Extract 结果当成天然完整；
- 从运行时消费者反查插件参数、自定义数据和脚本中的文本含义；
- 为每类文本选择能够完整表达身份、翻译单位、上下文和写回关系的能力；
- 排除 Builtin、Rules、Standard Lua 和 Managed/私有协议的重复责任；
- 保存高风险正反样本、应命中内容、遗漏、错误命中和明确排除项的检查结果；
- 检查自然顺序、重复提取、来源删除和配置变化后的结果；
- 在没有译文时执行必要的提取—写回比较，确认不会产生无关修改。

Rules、MV dialogue rules、Placeholder、Standard Lua 和 Managed 的声明、清除、复用和快照
行为分别由实际规则、Lua 和 CLI 文档规定。采用文件的路径和内容身份按
[任务产物规范](task-artifacts.md)记录。

完成提取意味着：范围内文本来源、稳定身份、翻译单位、上下文和写回位置都有当前证据；
遗漏和排除有解释；重复执行能得到相同语义结果；后续阶段能读取同一批内容。来源或实际
加载位置不清楚时先解决该事实，不用缩小范围掩盖问题。

## 翻译

发出模型请求前，核对：

- 提取结果和剩余内容；
- 实际 Profile、Client、语言对、Prompt 文件、Terminology、Placeholder 和 Lua 选择；
- 已保存译文、Current 状态、Managed/私有状态和可能失效的结果；
- 用户对模型、供应商、外部服务和费用的授权；
- 任务记录是否启用，以及它能够和不能证明什么。

Prompt 在每次 Translate 中按实际配置重新读取；不能因前一轮使用过同名文件就假定内容
相同。记录本轮实际选择和内容身份，不把请求正文或配置全文复制进任务清单。

### Terminology

正式批量翻译前，必须根据本次任务范围内全部玩家可见文本建立并验证 Terminology：

- MV/MZ 特殊字段和 engine 结构只帮助发现候选，不能代替全文调查；
- 结合真实上下文判断词义、译名、同形异义、角色和场景差异；
- 说明采用和排除的理由；
- 在完整范围检查正确命中、漏掉内容、错误命中及与 Placeholder 的影响；
- 没有值得固定的术语时，记录调查范围、结论和证据。

### 执行结果

模型响应成功不表示译文已经验收或保存。保存 ATT 的真实任务结果、正常未产出、拒绝原因、
剩余内容和数据库确认状态。连续执行没有有效进展时停止，根据实际原因处理，不用重复请求
掩盖问题。

完成翻译意味着：范围内译文满足用户要求并由 ATT 确认保存；没有未解释的剩余内容、拒绝、
质量问题或不确定提交；Terminology、Placeholder、Prompt 和代表性上下文都有当前证据。

### 人工质量检查

`Current` 只说明译文仍符合建立它时的语义，不证明质量合格。质量检查至少覆盖：

1. 原意、上下文关系、隐含主语和叙事事实；
2. 说话者、角色称谓、语气、时态和同一角色的一致表达；
3. Terminology、专名、菜单名、技能名和同形异义；
4. 源语残留、漏译、误译、多译和不应翻译的内容；
5. Placeholder、控制符、行形状、选项槽位和空行；
6. 菜单、帮助文本、对话框和滚动文本的长度与实际布局。

对整个任务范围做可机械复核的检查；对高风险类别完整检查，并按场景抽样做人工语义审查。
任务要求逐条人工审校时覆盖全部内容。记录抽样方法、未审内容和仍有风险的场景，不用少量
样本证明整个项目合格。

### 修订已保存译文

用户指出问题或审校发现问题时，在翻译阶段增加修订 TODO，记录目标身份、旧译文、问题
依据、预期新译文、传播范围和验证方法。先确认译文责任：

- **Standard**：完整读取实际 `translation.md` 与 `lua.md` 中独立项目 Lua 的人工候选
  章节，通过当前产品接口提交、复读权威状态并重新验证 WriteBack。
- **Managed**：先确认实际发布是否提供人工候选接口。没有时报告能力缺口；不得直接改
  ATT 受管表或伪造 Prompt、context、instruction 变化。改由 Standard 或低级协议负责会
  改变提取、状态和写回责任，必须先说明影响并取得授权。
- **低级 Lua 私有协议**：只按脚本拥有的稳定身份和私有状态修订，遵守实际文档中的验收、
  事务和 Current 责任。

Standard 人工候选必须用完整 owner、位置、role、原文和当前项目事实定位；检查候选形状、
Placeholder、去重传播及已有 Current 的覆盖意图。成功调用已经提交，后续脚本失败或取消
不会撤销。随后重新打开权威状态，不为验证额外发出模型请求，并复核写回和游戏内结果。

普通人工补译不得直接 SQL 修改 ATT 受管表。实际发布文档允许的高级数据库修复只在用户
明确授权该高风险操作后使用，并完整遵守现行备份、并发、事务和不变量要求。

## 写回

WriteBack 从冻结来源建立新的完整候选，不在旧 `write_back` 上增量修补。发布根 README
说明 `write_back` 是 ATT 管理的内容树，不是完整可运行游戏包；不得手改它，也不得把任务
清单、报告、截图或其他人工材料放进去。

写回前核对译文状态、来源、身份、写回映射、目标位置，以及是否存在尚未确认的事务、
运行方案或发布终态。

阶段工作包括：

- 按实际文档建立候选并确认最终发布状态；
- 检查完整目录差异、数据格式、脚本、资源和无关内容是否保持；
- 验证相同权威输入重复构建的结果稳定，或解释真实差异；
- 需要实际运行 QA 时，先从用户确认的游戏部署说明或项目事实确定完整游戏基线、
  `write_back` 与加载目录的映射及替换方法，再建立原游戏之外的隔离副本；
- 从该隔离副本的真实加载位置检查关键界面、事件、插件、布局和文本；
- 确认用户要求的最终交付确实包含本轮已验证内容。

差异报告必须位于被比较目录之外。需要保留某一轮输出时，复制到用户认可、不会被后续
Init 或 WriteBack 替换的位置，并记录来源项目、ATT RunId 和内容身份。

组装完整游戏副本不属于 ATT 的发布契约。没有用户确认的完整游戏基线和部署方法时，不
猜测复制或覆盖关系，也不修改原游戏；在验证 `write_back` 本身后停止，并明确说明实际
加载 QA 尚未完成及缺少的事实。

布局返回 `Manual` 时按实际文档把它当作正常诊断处理，并人工检查对应文本；不得把
“成功发布”解释成自动布局已经全部完成。未翻译内容保持原文时，WriteBack 成功也不表示
翻译阶段完整。

ATT 内部 candidate、stage、backup、journal 和锁由产品负责。不得自行创建、移动、改名或
清理；诊断给出恢复位置时只按实际发布文档处理。

完成写回意味着：译文进入正确位置；候选结构和完整差异正确；发布终态已确认；本次要求
的实际加载检查通过；未验证内容和外部组装要求已经说明。

## 修改项目配置与 Lua

只读请求保持只读。执行授权后，可以修改任务范围内、可恢复且不改变用户产品选择的
Rules、Placeholder、Terminology、Prompt、Lua 和其他项目设置。

一个配置修改 TODO 通常应完成：

1. 读取实际发布目录中的对应文档；
2. 查清根因、责任能力、全部真实使用位置和后续影响；
3. 按[任务产物规范](task-artifacts.md#配置promptrules-和-lua)保存允许保留的修改前证据
   和恢复来源；
4. 比较可行方案会保留什么、改变什么；
5. 采用影响明确且能够完整验证的方案；
6. 在全部受影响内容上比较修改前后结果；
7. 为已经失效的提取、翻译或写回结论增加复核 TODO。

只有步骤需要不同授权、独立恢复或跨次交接时才拆分。涉及敏感信息时只引用实际
`docs/runtime/chat-completions.md` 中的唯一规定，不在 Skill 另建清单。

修改 Placeholder 时，对全部实际输入比较新增和丢失的命中、错误命中、未命中、重叠、
保护范围和嵌套情况；再判断哪些已有译文与写回结果失效。不能只验证触发问题的一个字符串。

配置候选移动后必须按其新位置重新解析全部相对路径。仅用于备份的配置不得拿来运行 ATT。
具体保存和命名遵循 [任务产物规范](task-artifacts.md)。

Lua 不是 sandbox。接口选择之外，还要检查主程序实际加载的模块和受管 API 外的文件、
进程、网络、SQLite 副作用。按实际 `lua.md` 读取 VM 权限、阶段快照、动态依赖、事务、
取消和失败后的状态。阶段 Lua 与独立项目 Lua 的读取和保存方式不同，不能相互推断。

## 结果解释与恢复

先按实际发布文档核实状态名称和影响。当前发行文档描述下列常见情况；若本次实际发布不同，
以它为准：

| 观察到的情况 | 应怎样解释和继续 |
|---|---|
| Translate 为 `Partial` 或 `Unavailable`，退出码为 `0` | 是已确认的正常业务结果，但通常不是翻译完成。记录已提交内容、未产出原因和剩余范围。 |
| 零模型任务 | 可能表示全部 Current、无需翻译或没有可执行单元；继续核对 planning-unresolved 和任务范围，不能只看“0”。 |
| planning-unresolved 没有 task ID | 请求尚未启动时没有模型任务记录是正常事实；从规划诊断和权威项目状态调查。 |
| WriteBack 布局为 `Manual` | 是正常布局结果，不是技术错误；发布仍可能成功，相关文本必须人工检查。 |
| 后续任务失败或取消，但前缀已确认提交 | 已确认前缀继续存在。重新读取数据库和剩余任务，不从头重复请求。 |
| 业务结果已经生效，但运行方案未保存 | 分开记录结果状态与方案状态；下次使用显式参数，不依赖省略参数复用。 |
| SQLite 或发布为 `OutcomeUnknown` | 立即停止相关写入和重试，保留现场，按诊断的恢复位置重新观测权威状态。 |
| 项目日志或 task-records 缺失、降级或写入失败 | 它们是诊断材料；缺失不能证明请求未发生，也不改变已经确认的业务结果。 |
| candidate、stage、backup、journal 或输出目录存在 | 存在本身不能证明发布成功。只读实际发布终态和权威项目状态。 |
| Ctrl-C 或进程退出 `130` | 受控收尾可能保留已确认进度；核对最终诊断、数据库和发布状态后再继续。 |
| 命令退出 `1` 但此前可能已有副作用 | 不把失败等同于全部回滚；按诊断分别核对数据库提交、Lua 外部副作用和发布状态。 |

恢复时按顺序处理：

1. 停止依赖不明事实的下游工作和重复外部请求；
2. 在任务清单记录最后权威状态、RunId、诊断、现场位置和未知部分；
3. 不移动或清理 ATT 管理的恢复产物；
4. 读取对应阶段、CLI、SQLite 或目录发布文档；
5. 重新观测数据库、冻结来源和发布终态；
6. 从最早失效阶段建立复核 TODO，只重做现有证据不能继续证明的部分。

## 新事实使旧结论失效

发现新事实后返回最早能修正它的阶段：

- 文本来源、翻译单位、上下文、身份或写回映射有误：返回提取；
- 语言、Terminology、Placeholder、Prompt、模型协议或译文质量要求改变：返回翻译；
- 目标位置、候选结构、布局或实际运行结果有误：返回写回。

未完成任务在原清单追加复核 TODO。已完成但同一交付结论失效时恢复原清单，旧 TODO 和旧
交付记录不改写；新版本、新范围或独立输出使用新清单并引用旧清单。
