# ATT RPG Maker 翻译工作要求

本文补充三阶段的调查重点、完成条件和高风险修改方法。开始任务时完整读取；进入某阶段或
修改项目配置前，再读取相关部分。ATT 的命令、字段、API、状态和错误只由本次实际发布
目录中的产品文档定义，本文不重复这些契约。

## 1. 先从整个项目制定方案

创建任务清单前，先只读了解：

- 用户最终需要什么结果，哪些行为必须保持；
- 游戏版本、补丁或 MOD 组合，以及运行时真正加载的位置；
- 当前 ATT 项目、配置、已有提取结果、译文和候选输出；
- 玩家可见文本实际来自哪些数据库、事件、插件、脚本和自定义数据；
- 每类文本适合由 Builtin、Rules、Managed Lua 或低级 Lua 中的哪一种能力处理；
- 如何在提取、翻译和写回之间定位同一段文本，以及如何证明游戏实际使用了写回结果；
- 哪些选择已有授权，哪些仍必须由用户决定；
- 主要风险、备选方案和完整验证方法。

局部报错只是调查起点，不能自动决定修改范围。先找到负责该含义的配置或组件，再检查它
的全部真实使用位置和后续影响。仍未确认但不妨碍宏观方案的事实，写成当前阶段的调查
TODO；不要据此提前展开后续阶段。

## 2. 提取

按需读取发布目录中的：

- `docs/README.md`
- `docs/rpg-maker/README.md`
- `docs/rpg-maker/init.md`
- `docs/rpg-maker/extraction.md`
- 使用 Rules 或 Placeholder 时的 `docs/rpg-maker/rules.md`
- 使用 Lua 时的 `docs/rpg-maker/lua.md` 和必要的 Cookbook

提取阶段要完成：

- 核对实际游戏来源、引擎、加载位置和 ATT 项目状态；
- 盘点任务范围内全部玩家可见文本，不把当前 Extract 结果当成天然完整；
- 为每类文本选择能够完整表达定位标识、翻译单位、上下文和写回关系的 ATT 能力；
- 避免 Builtin、Rules 和 Lua 重复负责同一文本；
- 保存高风险样本、应命中内容、遗漏内容、错误命中和明确排除项的检查结果；
- 验证重复 Extract 的结果稳定；
- 验证在没有译文时完整执行提取和写回不会产生无关变化。

完成提取意味着：范围内文本来源、用于定位同一内容的标识、上下文和写回位置都有当前
证据，遗漏和排除有解释，后续阶段可以稳定读取同一批内容。发现游戏来源或实际加载位置
不清楚时，先解决该事实；不要用缩小文本范围的方式继续。

## 3. 翻译

按需读取发布目录中的：

- `docs/rpg-maker/translation.md`
- `docs/rpg-maker/prompts.md`
- `docs/rpg-maker/terminology.md`
- `docs/runtime/chat-completions.md`
- 使用独立项目 Lua 时的 `docs/runtime/cli.md`
- 使用 Placeholder 时的 `docs/rpg-maker/rules.md`
- 使用 Lua 时的 `docs/rpg-maker/lua.md`
- 使用独立项目 Lua 人工修订 Standard 译文时的 `docs/rpg-maker/lua-cookbook.md`
- 启用任务记录时的 `docs/rpg-maker/task-records.md`

正式请求模型前，核对提取结果、Profile、Client、Prompt、语言、术语、Placeholder、Lua
选择、已有译文、剩余内容和用户对模型及费用的授权。

术语是正式批量翻译前的必要工作：

- MV/MZ 特殊字段和引擎结构只用于发现候选；
- 检查任务范围内全部玩家可见文本及运行时使用这些文本的代码或数据；
- 结合实际上下文判断词义、译名、同形异义和角色差异；
- 说明采用或排除的理由；
- 在完整语料上验证正确命中、漏掉内容、错误命中和与其他规则的影响；
- 没有值得固定的术语时，记录调查范围、结论和证据。

执行翻译时保存 ATT 的真实结果、剩余内容、拒绝原因和数据库确认状态。模型请求成功不等于
译文已经验收或保存。连续执行没有有效进展时停止，根据产品文档中的实际原因处理，不用
重复请求掩盖问题。

完成翻译意味着：范围内译文满足用户要求并由 ATT 确认保存，没有未解释的剩余内容、
拒绝、质量问题或不确定提交；术语、Placeholder 和代表性上下文有当前证据。

### 人工审校与修订已保存译文

`Current` 只表示译文仍符合建立它时的翻译语义，不证明措辞、语气或上下文质量已经满足
用户要求。用户指出问题或审校发现问题时，在翻译阶段增加修订 TODO，记录目标身份、旧
译文、问题依据、预期新译文、可能传播范围和验证方法。

先从实际项目状态确认译文由谁负责，再选择产品支持的修改路径：

- Standard：读取发布文档中“独立项目 Lua 的人工候选”以及 Lua 人工验收章节，通过独立
  项目 Lua 的 `ctx.standard.open()` 与 `standard:accept(batch)` 提交候选。修改已有 Current
  时设置 `replace_current=true`；补充 missing 或 stale 时保持
  `replace_current=false`。
- Managed：确认本次发布文档是否提供人工候选提交接口。没有时记录能力缺口并停止该项
  修改；不得直接更新 ATT 受管表，也不得改动无关 Prompt、context 或 instruction 来制造
  stale。确实需要改由 Standard 或低级私有协议负责时，先说明提取、状态和写回行为会如何
  改变并取得相应授权。
- 低级 Lua 私有协议：按脚本自己定义的稳定身份定位译文，使用发布文档规定的低级验收
  接口，并在脚本私有表中维护成对状态和事务；只让明确指定的身份跳过旧 Current 复用并
  验收人工候选，不得把私有协议写入 ATT 受管表。

修订 Standard 译文时必须：

1. 从发布文档复制独立项目 Lua 的精确命令形状，不按其他 CLI 的习惯重排全局参数；
2. 使用 owner、完整位置、role 和原文等权威事实定位目标，不按遍历序号、展示文本或旧
   译文猜测身份；
3. 提交前检查只读单元的状态、候选形状、Placeholder token 和 `family_size`，确认同一
   去重族的全部传播位置都应采用该译文；
4. 批量修订使用一次受管 batch；同一去重族不得提交互相冲突的候选或覆盖选项；
5. 记录每项验收结果、规范译文和实际改变的位置数。成功的人工候选调用已经提交，后续
   Lua 失败或取消不能当作数据库未修改；
6. 通过新的只读项目状态确认译文和 Current 状态，不为验证额外触发模型请求；随后重新
   执行受影响的 WriteBack 检查并核对实际游戏结果。

任务记录可以帮助调查模型输入、输出和拒绝原因，但不是译文或提交状态的权威来源。人工
候选不产生托管模型任务记录；任务清单应引用脚本、ATT 返回结果、权威状态复读和写回结果。

## 4. 写回

按需读取发布目录中的：

- `docs/rpg-maker/write-back.md`
- 使用 Lua 时的 `docs/rpg-maker/lua.md`
- `docs/runtime/directory-publishing.md`
- `docs/runtime/project-log.md`

写回前核对译文状态、来源、用于定位同一文本的标识、写回映射和目标位置，以及是否存在
尚未确认的事务、候选目录或发布结果。

写回阶段要完成：

- 按产品文档构建候选内容并确认实际发布结果；
- 检查完整目录差异、数据格式、脚本、资源和无关内容是否保持；
- 验证重复构建的结果稳定，或解释实际差异；
- 在隔离副本中从游戏实际加载位置运行，检查关键界面、事件、插件、布局和文本；
- 确认用户要求的最终输出确实包含已经验证的候选内容。

候选目录存在不等于完成。译文失效时返回翻译；文本定位标识或写回映射错误时返回提取；
写操作结果不确定时保留现场并先确认，不盲目重复。

## 5. 修改项目配置

用户只要求分析、解释或建议时保持只读。用户已经授权翻译、修复或交付时，可以自主修改
任务范围内、可恢复且不改变用户产品选择的 Rules、Placeholder、术语、Prompt、Lua 和
其他项目配置。

一次配置修改通常使用一个 TODO，完成标准应覆盖：

1. 读取实际发布目录中的相关产品文档；
2. 查清根因、负责该含义的组件、全部真实使用位置和后续影响；
3. 保存修改前的配置和检查结果；
4. 比较可行方案会保留什么、改变什么；
5. 采用影响明确且可以完整验证的方案；
6. 在全部受影响内容上比较修改前后结果；
7. 为已经失效的提取、翻译或写回结论增加具体复核 TODO。

只有步骤需要不同授权、独立恢复或跨次交接时才拆成多个 TODO。不能只写“已经修复”，也
不能只凭触发报错的单个样本证明修改安全。

### Placeholder

修改 Placeholder 时，检查所有使用这份配置的文本来源和处理方式，而不是把配置误认为
某一个 Lua 或某一类提取专用。对完整输入比较：

- 新增和丢失的命中；
- 错误命中与未命中；
- 重叠和保护范围变化；
- 报错结构、其他位置独立出现的同类结构、嵌套结构；
- 哪些已有译文和写回结果需要重新验证。

只有完整比较通过后才能继续依赖这项配置。

## 6. 选择 Lua 接口

先区分 Standard 人工候选、Managed 和低级 Lua 私有协议。人工修订已经属于 Standard 的
文本时，使用上一节的独立项目 Lua 接口，不为此另建 Managed 或私有协议。

对于还需要设计提取、翻译和写回关系的非 Standard 文本，先用产品文档确认 Managed API
是否能表达当前文本的定位方式、翻译单位、必须作为整体翻译或提交的内容关系，以及写回
需求。能表达时优先使用 Managed API，减少项目 Lua 自行实现通用流程的工作。

Managed API 不能表达项目需要时使用低级 API，并在任务清单中写清：

- 高级接口缺少什么具体能力；
- Lua 将自行负责哪些协议、并发、状态或验证工作；
- 如何检查这些自定义逻辑的正确性和失败处理。

不要为了使用高级接口而损失项目语义，也不要在高级接口已经满足需求时由 Lua 重写 ATT
的通用能力。

## 7. 新事实使旧结论失效

发现新事实后，先返回最早能修正它的阶段：

- 文本来源、翻译单位、上下文、定位标识或写回映射有误：返回提取；
- 语言、术语、Placeholder、Prompt、模型协议或译文质量规则改变：返回翻译；
- 目标位置、候选结构、布局或实际运行结果有误：返回写回。

保留已经完成的记录，在受影响阶段增加具体复核 TODO；只重做现有证据已经不能证明正确的
内容。更新当前状态和重要决定后再继续，不能静默沿用已经失效的结果。
