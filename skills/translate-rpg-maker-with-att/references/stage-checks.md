# 五个阶段的工作要求

本文件说明解包、提取、翻译、写回和封包各自要完成什么、开始前读哪些文档、保存什么
证据，以及什么情况需要返回前面的阶段。制定整体方案时完整读取；开始某阶段前重新读取
共同步骤、该阶段内容和文档索引。

## 1. 每个阶段共同执行的步骤

1. 读取任务清单、该阶段的下一步和待重新验证的变更。
2. 确认`实际使用的 ATT`和`ATT 文档版本`没有变化。
3. 完整读取本阶段列出的文档；根据实际使用的 ATT 功能补读文档索引中的资料。
4. 把实际读过的 Markdown 文件和章节写入当前“阶段开始前检查”的`参考文档`。
5. 完成开始前检查，确认输入、是否适用、负责本阶段输入和结果的 ATT 功能或组件、依赖、
   用户授权和影响范围。
6. 根据项目情况增加、拆分或替换 TODO。
7. 执行每个 TODO，并立即更新结果和双方相互引用的证据。
8. 完成本阶段的完成检查，再更新阶段任务、阶段总览、下一阶段和全局下一步。
9. 发现问题属于更早阶段时，返回最早负责该问题的阶段。

固定的是阶段任务、开始前检查和完成检查，不是固定的项目执行步骤。文档缺失、不能完整
读取或无法确认与 ATT 程序对应时，开始前检查必须设为 `BLOCKED`，不得继续修改项目。

## 2. 解包

### 阶段目标

得到完整、稳定、可以再次准备的游戏来源，并完成 ATT Init 所需的项目设置。

### 开始前读取

- [文档入口](../../../docs/README.md)
- [RPG Maker 文档入口](../../../docs/rpg-maker/README.md)
- [Init](../../../docs/rpg-maker/init.md)
- [CLI](../../../docs/runtime/cli.md)
- [配置](../../../docs/runtime/configuration.md)

如果游戏包需要外部工具，还要读取该格式和工具的现行资料，并在任务清单中记录来源。

### 开始前检查

- 原始游戏版本、补丁和 MOD 的实际使用顺序；
- 启动器真正读取的目录、包或归档；
- 包格式、所需工具和权限；
- 不可修改的原件与允许处理的工作副本；
- 引擎、语言、输出目标和用户授权；
- 本阶段命令和项目状态判断所依据的文档。

### 执行和证据

- 按已确认的格式和工具处理到新的、可以恢复的位置；
- 用目录清单、哈希或等价方法检查文件是否完整以及实际加载位置；
- 按当前 Init 文档执行并保存 ATT 返回结果、项目状态和失败信息；
- 不覆盖唯一原件，不把“命令成功”当成来源完整的唯一证据。

### 完成检查

- 来源版本、补丁/MOD 顺序和实际加载位置有证据；
- 解包或准备结果完整，可以再次执行；
- 后续阶段使用的确实是这份来源；
- ATT 项目状态符合本任务读取的 Init 文档；
- 原件位置和下一步明确。

版本、来源、根目录、加载顺序或 Init 结果不清楚时，后续阶段不能开始。

## 3. 提取

### 阶段目标

找到任务范围内全部文本来源，为每类文本选择正确的 ATT 功能，并建立能够稳定写回原位置
的身份。

### 开始前读取

- [RPG Maker 文档入口](../../../docs/rpg-maker/README.md)
- [Extract](../../../docs/rpg-maker/extraction.md)
- 使用 Rules 或 Placeholder 时的 [Rules](../../../docs/rpg-maker/rules.md)
- 使用 Lua 时的 [Lua](../../../docs/rpg-maker/lua.md)

### 开始前检查

- 解包来源和 ATT 项目仍然有效；
- 实际加载的数据库、事件、参数、自定义数据、脚本、注释和其他文本来源；
- 每类文本由哪个 Extract owner（Builtin、Rules 或 Lua）负责、使用哪个 ATT 功能、写回哪里；
- 现有处理方和项目状态，以及停用或替换它们会影响什么；
- 高风险文本、明确排除的内容和验证覆盖的方法。

### 执行和证据

- 按文档选择 Builtin、Rules、Managed Lua 或低级 Lua，不在 Skill 中猜字段和调用顺序；
- 使用低级 Lua 时，根据现行文档为脚本需要自行完成的工作增加实现和验证 TODO；
- 保存命中、未命中、错误命中、排除项、高风险样本，以及后续阶段定位同一文本并写回
  原位置所需的标识和映射；
- 检查重复 Extract 是否得到稳定结果；
- 检查没有译文时完整往返不会改变其他数据。

### 完成检查

- 所有范围内高风险文本来源已提取，或有证据说明为什么排除；
- 文本单位、上下文、分组、顺序、身份和写回位置正确；
- 各处理方保存的来源信息可供后续阶段稳定读取；
- 重复 Extract 的结果符合当前文档；
- 未翻译内容往返后没有无关变化。

来源问题返回解包。文本覆盖、身份、分组、上下文或写回映射问题在提取阶段修复。提取方式
变化后，受影响的翻译、写回和封包结果都要重新检查。

## 4. 翻译

### 阶段目标

使用当前提取结果和已经确认的翻译配置，得到通过 ATT 检查并确认写入项目数据库的译文。

### 开始前读取

- [Translate](../../../docs/rpg-maker/translation.md)
- [Prompt 与模型协议](../../../docs/rpg-maker/prompts.md)
- [术语](../../../docs/rpg-maker/terminology.md)
- [Client、重试与敏感信息](../../../docs/runtime/chat-completions.md)
- 使用 Placeholder 时的 [Rules](../../../docs/rpg-maker/rules.md)
- 使用 Lua 时的 [Lua](../../../docs/rpg-maker/lua.md)
- 启用任务记录时的 [task-records](../../../docs/rpg-maker/task-records.md)

`TRN-002` 和 `TRN-004` 分别填写各自实际读取的文件和章节，不能互相引用来代替阅读。

### 开始前检查

- 提取结果、文本身份和本轮输入仍然有效；
- Profile、Client、Prompt、语言、术语、Placeholder 和 Lua 选择有文档依据；
- 模型和费用选择已经得到用户授权；
- 已有译文、剩余内容、不适用内容和失败后下一步明确；
- 每份共享翻译配置的实际使用位置已经找全；
- 项目概况包含全部玩家可见文本，不能把当前 Extract 结果直接当成完整游戏文本。

### 术语检查 `TRN-004`

在正式批量请求模型前：

1. 完整读取术语文档并填写`参考文档`。
2. 使用 MV/MZ 特殊字段、引擎结构和上下文寻找可能重要的候选词；这些信息只提供线索。
3. 检查任务范围内全部玩家可见文本，以及运行时实际读取这些文本的代码或数据。
4. 对每个候选说明不同上下文中的含义、译名依据、采用或排除的理由。
5. 在完整文本上检查最终术语资源的正确命中、漏掉内容、错误命中、歧义和与其他规则的
   相互影响。
6. 保存候选来源、实际例句、判断过程、最终文件和验证证据。没有可用术语时，保存能够
   复核这一结论的调查和验证证据。

发现新的玩家文本来源时返回提取阶段，不能缩小文本范围来完成 `TRN-004`。

### 执行和证据

- 按当前 Translate、Prompt 和所选 Lua 文档执行；
- Managed API 不能表示项目需要时，可以使用低级 API，但要先记录缺少的能力、脚本承担
  的工作和验证方法；
- 保存实际任务、请求结果、每个 ID 的检查结果、数据库写入结果、剩余内容和下一步；
- 连续执行没有有效进展时停止，根据 ATT 的结构化原因返回负责该问题的阶段；
- 质量检查覆盖不同上下文、共享配置影响范围和用户要求。

### 完成检查

- ATT 的完整、部分、不可用、技术失败、取消和写入结果按文档原样记录；
- 根据数据库状态、剩余内容、拒绝原因和确认写入判断完成情况，不用请求成功代替；
- 范围内译文满足用户要求，或者有证据说明具体内容不适用；
- 没有未解释的剩余内容、拒绝或无法确认的写入结果；
- `TRN-004` 为 `DONE`，术语、Placeholder、语言和关键样本都有当前证据。

文本来源、单位或上下文问题返回提取。语言、术语、Placeholder、Prompt、Client 或模型
结果检查方式变化后，翻译、写回和封包都要重新检查。

## 5. 写回

### 阶段目标

把已经确认的译文写到正确位置，构建并验证候选目录，然后按文档完成发布。

### 开始前读取

- [WriteBack](../../../docs/rpg-maker/write-back.md)
- 使用 Lua 时的 [Lua](../../../docs/rpg-maker/lua.md)
- [目录发布与中断后处理](../../../docs/runtime/directory-publishing.md)
- [项目日志](../../../docs/runtime/project-log.md)

### 开始前检查

- 翻译结果符合本次输出要求；部分交付已经得到明确授权；
- 来源、Extract owner、用于跨阶段定位同一文本的标识以及写回映射仍然有效；
- 每类译文的目标位置和验证方法明确；
- 没有尚未确认的数据库事务、候选目录或发布结果；
- 本轮构建和发布行为有当前文档依据。

### 执行和证据

- 按 WriteBack、Lua 和目录发布文档构建、验证和发布；
- 保存输入身份、实际执行顺序、候选位置、完整目录差异和发布结果；
- 检查重复构建、无关数据保持、Lua 映射和失败后继续方式；
- 写操作是否生效不清楚时保留现场，先按文档确认，不盲目重复。

### 完成检查

- 完整目录的允许变化、结构、数据格式、脚本和资源已经检查；
- 重复构建得到相同结果，或差异有证据和解释；
- 在隔离副本中实际启动并检查关键 UI、事件、插件、布局和文本；
- 候选目录、发布文件和保存的运行计划状态明确。

候选目录存在不等于完成。译文失效返回翻译；身份或写回映射问题返回提取；来源问题返回
解包。

## 6. 封包

### 阶段目标

把已验证的候选目录制作成用户要求的完整包、补丁或普通目录，并证明游戏实际加载该交付
内容。

### 开始前读取

- [文档入口](../../../docs/README.md)
- [目录发布与中断后处理](../../../docs/runtime/directory-publishing.md)
- 实际包格式、组装工具、启动器和补丁方式的现行资料

### 开始前检查

- 用户要求的交付形式；
- 原始发行结构、候选目录、启动器加载顺序、归档或加密格式和运行依赖；
- 外部工具、版本、参数、权限和来源；
- 组装过程是否会覆盖原件或已验证候选；
- 如何反向检查包内容并在干净环境运行。

### 执行和证据

- 在新的临时位置组装，不覆盖唯一原件；
- 按真实运行顺序应用已验证内容；
- 保存工具身份、参数、输入输出清单和组装结果；
- 重新解包并比较内容，或用等价方法检查包内文件。

### 完成检查

- 最终文件清单、大小、哈希和生成依据完整；
- 包内内容与已验证候选一致；
- 在干净环境从最终文件启动；
- 实际加载位置、关键文本、插件和必要存档流程通过；
- 最终文件可以再次生成、可以运行且身份明确。

用户明确要求普通目录时，封包阶段任务可以凭证据设为 `N/A`，但开始前检查和完成检查仍要
完成。包格式和组装问题留在封包阶段；其他问题返回负责该事实的最早阶段。

## 7. 前面阶段变化后要重新检查什么

| 新事实或变化 | 返回阶段 | 至少重新检查 |
|---|---|---|
| 版本、来源、加载位置、补丁或 MOD 顺序 | 解包 | 后面全部阶段 |
| 文本来源、Extract owner、翻译单位、上下文、分组、定位标识或写回映射 | 提取 | 翻译、写回、封包 |
| 语言、术语、Placeholder、Prompt、协议或译文检查 | 翻译 | 写回、封包 |
| 写回位置、候选结构、布局、运行结果或发布文件 | 写回 | 封包 |
| 包格式、组装或最终加载位置 | 封包 | 封包 |
| ATT 程序或文档版本 | 最早受影响阶段 | 所有依赖旧行为的后续阶段 |

不要修改旧的完成记录。增加 `CHG-*`，为每个受影响阶段建立新的阶段任务、开始前检查和
完成检查，把它写入`待重新验证的变更`，然后只重做当前项目状态已经不能证明正确的工作。
