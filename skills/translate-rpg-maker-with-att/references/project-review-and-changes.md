# 项目调查与配置修改

本文件说明如何在创建任务清单前了解整个项目、选择 ATT 功能，以及修改 Rules、
Placeholder、术语、Prompt 或 Lua 前必须完成哪些检查。

## 1. 先确认 ATT 程序和文档

开始制定方案前，只读确认：

1. 实际会调用哪个 ATT 可执行文件；
2. 用什么哈希、构建版本对应的 Git 提交 ID 或其他信息确认该程序；
3. 实际读取哪个 `docs` 目录；
4. 用什么 Git 提交 ID 或其他信息确认文档版本；
5. 程序与文档为什么属于同一份现行实现；
6. 本任务需要的文档是否存在并能完整读取。

把结果写入任务清单的 `实际使用的 ATT` 和 `ATT 文档版本`。无法确认时停止修改项目，不要用
Skill、源码、旧对话或试运行猜测产品行为。

每个“阶段开始前检查”都要列出本次完整读过的 `参考文档`。给出 CLI、配置、API、状态或
错误判断之前，应重新读取对应文档，不能只写“同上”。

## 2. 从用户需要的结果检查整个项目

创建任务清单前至少回答：

1. 用户最终需要完整游戏包、补丁、普通目录、诊断结论还是中间输出；
2. 哪个游戏版本、补丁和 MOD 组合是实际来源；
3. 游戏启动时真正读取哪个目录或归档；
4. 哪些行为必须保持不变，哪些情况算失败；
5. 本任务做到哪里停止；
6. 解包、提取、翻译、写回、封包之间分别传递什么；
7. 哪些选择只能由用户决定；
8. 用哪些文件、数据库状态、差异或运行结果证明工作完成。

一个报错字符串只能告诉你从哪里开始调查。制定方案前还要检查：

- 游戏运行时实际读取的全部内容，而不是只看报错文件；
- ATT 项目已经保存的状态，以及本次工作会读取或改变的状态；
- 每种文本来源如何发现、翻译和写回；
- 共享 Rules、Placeholder、术语、Prompt 和 Lua 被哪些文本、ATT 功能或组件使用；
- 修改较早阶段后，哪些后续结果需要重新检查。

## 3. 根据现行文档选择 ATT 功能

完整读取 [RPG Maker 文档入口](../../../docs/rpg-maker/README.md)，再按任务使用它链接的
资料。ATT 支持哪些功能、各功能在哪个阶段可用、具体 API 和状态如何处理，只由这些文档
定义。

对每种文本来源，在任务清单中写清：

1. 哪个 ATT 功能已经负责这类文本；
2. 该功能能否完整表示文本身份、翻译单位、阶段间保存的信息和写回位置；
3. 若不能，缺少的具体能力是什么；
4. 使用低级 API 后，Lua 按现行文档需要自行完成哪些工作；
5. 该选择如何影响项目状态和 `task-records`。

Managed translation API 通常可以减少脚本工作，但它不是强制选择。若它不能表示项目中
必须作为整体翻译或提交的内容关系，或者缺少其他必要能力，可以使用低级 API，并建立
专门的实现和验证 TODO。具体能力边界只从现行 Lua 文档读取。

## 4. 避免重复实现已有能力

写 Rules 或 Lua 前，先检查 ATT 当前已有的能力：

1. 规则、失败行为和使用过程相同，直接使用现有功能；
2. 只有部分相同，使用已有的高层功能，让项目脚本只保留自己的映射；
3. 含义确实不同，才编写独立逻辑。

任务清单中的选择说明要回答：

- 哪个组件负责发现文本、定义翻译单位、检查模型结果和写回；
- 哪个组件负责并发、重试、取消、事务和中断后继续；
- 文本身份在哪个阶段建立，后续如何找到同一内容；
- 某次写操作结果不确定时应该从哪里继续检查；
- 为什么这个方案不会产生两份互相冲突的项目状态。

不要只因为函数名或代码结构相似就判断功能相同，也不要因为 Lua 能写就重新实现 ATT 已有
的稳定功能。

## 5. 哪些修改可以自主完成

用户只要求分析、解释或建议时，保持只读。

用户已经授权执行翻译、修复或交付时，可以自主修改任务范围内、能够恢复且有证据支持的：

- 提取 Rules；
- Placeholder；
- 术语；
- Prompt；
- 项目 Lua；
- 不改变用户产品选择的其他项目配置。

以下内容必须由用户决定或再次授权：

- API key；
- 模型、费用或供应商；
- 源语言和目标语言；
- 外部服务；
- 扩大任务或文件范围；
- 覆盖唯一原件、不可恢复的发布或其他不可逆操作。

## 6. 修改项目配置的步骤

每次实际修改项目配置，都创建一个 `是否修改项目配置：是` 的 `CHG-*`，并完成：

1. 完整读取该配置及受影响行为的现行文档，把文件和章节写入 `参考文档`。
2. 查明原因，不只记录触发报错的一个样本。
3. 找到负责该规则的组件、所有实际使用位置、输入内容和会受影响的后续结果。
4. 保存修改前结果。
5. 比较可行方案会保留什么、改变什么，以及各自的验证成本。
6. 选择影响最小且可以完整验证的方案。
7. 分别建立修改前检查、修改和修改后检查 TODO。
8. 比较所有受影响内容的修改前后结果。
9. 为不再成立的翻译、写回或封包结论建立新的检查 TODO。

不要把文档阅读、修改动作和修改后检查合并成一句“已修复”。范围没有查清、验证失败或写
操作是否生效无法确认时，停止依赖这项配置的后续工作。

## 7. 修改 Placeholder

修改前完整读取 [Rules 文档](../../../docs/rpg-maker/rules.md) 以及它引用的翻译资料。字段、
`scopes` 字段的适用范围、匹配和冲突规则以文档为准，本 Skill 不复制这些产品说明。

实际工作必须包括：

1. 列出会使用这份 Placeholder 配置的所有文本来源、Extract owner 和其他实际使用组件；
2. 保存当前配置在完整输入上的全部命中位置和保护范围；
3. 对每个候选方案比较新增命中、丢失命中、错误命中、重叠和适用范围变化；
4. 同时检查报错结构、其他位置单独出现的同类结构、嵌套结构和其他文本来源；
5. 找出哪些现有译文、写回输出和最终文件需要重新检查；
6. 只有所有受影响内容的比较结果通过后，才继续后续阶段。

例如，删除一条 `${...}` 规则可能解除 `\iw[${...}]` 的重叠，但也可能让其他位置独立出现的
`${...}` 失去保护。只解决一个报错样本，不能证明整项修改安全。

## 8. 建立术语资源

正式批量翻译前必须完成 `TRN-004`，并完整读取
[术语文档](../../../docs/rpg-maker/terminology.md)。

MV/MZ 特殊字段和引擎结构可以帮助发现值得关注的候选词，但不能决定术语范围。必须检查
任务范围内全部玩家可见文本，以及运行时实际读取这些文本的代码或数据：

1. 收集候选词的实际上下文；
2. 区分同形异义和不同角色使用方式；
3. 说明采用某个译名或排除候选的理由；
4. 在完整文本上检查正确命中、漏掉内容、错误命中和与其他规则的影响；
5. 保存最终术语文件的位置和验证证据。

不要把当前 Extract 结果自动当成全部游戏文本。发现漏掉的文本来源时，返回提取阶段补齐。
不要按出现次数、字段名或结构位置机械收录，也不要把全部原文复制成术语。没有值得固定的
术语时，同样要保存完整调查和验证证据，并明确记录没有可用术语。

## 9. 上游变化影响后续结果

发现问题时，返回最早负责该事实的阶段：

| 变化 | 返回阶段 | 还要重新检查 |
|---|---|---|
| 游戏版本、来源、实际加载位置、补丁或 MOD 顺序 | 解包 | 后面全部阶段 |
| 文本来源、Extract owner、翻译单位、上下文、分组、定位标识或写回映射 | 提取 | 翻译、写回、封包 |
| 语言、术语、Placeholder、Prompt、模型协议或译文检查规则 | 翻译 | 写回、封包 |
| 写回位置、候选目录结构、布局、运行结果或发布文件 | 写回 | 封包 |
| 包格式、组装方式或最终加载位置 | 封包 | 封包 |
| ATT 程序或文档版本 | 最早受影响阶段 | 所有依赖旧行为的后续阶段 |

发生这些变化时：

1. 停止新的修改；
2. 增加 `CHG-*` 并记录旧事实、新事实和触发证据；
3. 为每个受影响阶段建立新的阶段任务、开始前检查和完成检查；
4. 把 `CHG-*` 写入相应阶段的 `待重新验证的变更`；
5. 重新阅读相关文档，执行必要返工和检查；
6. 所有新 TODO 都有当前证据后，才能把变更设为 `已完成`。

保留旧 TODO 和旧证据，不要把历史改写成“从未发生过”。只重新执行当前项目状态已经不能
证明正确的工作。
