# 任务清单规则

本文件规定任务清单放在哪里、何时创建、如何更新，以及怎样记录 TODO、证据和计划变化。
新建任务、继续中断的任务、改变计划、分派子 Agent 或准备交付前，必须完整读取。

## 1. 一个任务只用一个文件

- 每个翻译任务只维护一个任务清单，不另建阶段清单、隐藏 TODO 或第二份状态文件。
- 默认路径：
  `<任务目录>/att-tasks/<YYYYMMDD-HHmmss>-<mv|mz>-<项目名>.md`。
- 任务目录应由操作者管理并长期保留。不要把任务清单放进原始游戏目录、ATT 项目目录、
  候选输出、最终输出、临时目录、缓存、日志、`task-records` 或 Skill 安装目录。
- 文件名不允许的字符替换为 `-`；重名时追加 `-02`、`-03`。创建后不再改名，不含 `.md`
  后缀的文件名就是任务 ID。
- 同一个 ATT 项目同时只能有一个未完成的任务清单。继续、修复和补充证据都写回原文件。
- 只有目标确实不同，并且旧任务已经完成、取消或明确交接时，才创建新文件。
- 任务完成或取消后原地保留，不自动删除、移动或写入游戏目录。

## 2. 了解项目后再创建

主 Agent 先只读了解整个项目，再亲自从
[任务清单模板](../assets/task-list-template.md)创建文件。创建前至少要知道用户目标、实际
游戏来源、五个阶段如何衔接、主要风险和验证方法。

任务清单严格保留以下一级内容顺序：

1. 一个一级标题；
2. `整体方案`；
3. `任务信息`；
4. `项目概况与影响范围`；
5. `阶段总览与下一步`；
6. `1. 解包（UNP）`；
7. `2. 提取（EXT）`；
8. `3. 翻译（TRN）`；
9. `4. 写回（WBK）`；
10. `5. 封包（RPK）`；
11. `证据`；
12. `计划和变更记录`；
13. `阻塞、剩余工作和交接`；
14. `最终检查`。

`整体方案`先用普通语言说明完整路线、选择的 ATT 功能、阶段依赖、风险和验证方法。不要先
堆出大量 TODO，再倒推为什么要做。

创建时写出五个阶段的固定 TODO 和 `TRN-004`。项目专属 TODO 只写当前事实能够支持的内容；
进入某个阶段前，再根据最新项目情况细化。

## 3. 记录实际使用的 ATT 和文档

`任务信息` 必须填写：

- `实际使用的 ATT`：可执行文件绝对路径；文件哈希、对应的 Git 提交 ID 或构建版本；
- `ATT 文档版本`：`docs` 根绝对路径；对应的 Git 提交 ID 或目录内容哈希。

程序路径和 `docs` 根必须真实存在。开始修改项目前，Agent 要确认二者属于同一份现行实现。
无法确认时，把当前 TODO 设为 `BLOCKED`，不要试着用源码、旧对话或旧 Skill 猜产品行为。

以下 TODO 或记录必须填写 `参考文档`：

- 当前使用的每个“阶段开始前检查”；
- `TRN-004`；
- 每个修改项目配置的 `CHG-*`。

`参考文档` 要列出位于本任务 `docs` 根下、实际完整读过的 Markdown 文件。每个引用必须带
具体 `#章节`，或者明确写“全文”。文件必须存在；只写“见文档”“同上”、目录名、搜索结果
或聊天结论无效。

ATT 程序或文档版本变化时，不要覆盖旧值假装没有变化。先增加 `CHG-*`，写清旧值、新值、
受影响的 TODO 和重新检查工作，再更新任务信息。

## 4. 固定阶段与 TODO 编号

编号前缀：

| 内容 | 前缀 |
|---|---|
| 解包 | `UNP-*` |
| 提取 | `EXT-*` |
| 翻译 | `TRN-*` |
| 写回 | `WBK-*` |
| 封包 | `RPK-*` |
| 证据 | `EV-*` |
| 计划或项目事实的变化 | `CHG-*` |

每个阶段初始固定：

- `XXX-001`：`任务类型：阶段任务`，表示这一阶段要得到的最终结果；
- `XXX-002`：`任务类型：阶段开始前检查`，检查输入、适用性、依赖、文档和影响范围；
- `XXX-003`：`任务类型：阶段完成检查`，检查结果、证据、遗漏和下一阶段需要的内容；
- `TRN-004`：`任务类型：术语检查`，检查全部玩家可见文本并建立术语资源，或者用证据确认没有
  可用术语。

翻译阶段的新 TODO 从 `TRN-005` 开始，其他阶段从 `XXX-004` 开始。ID 在文件内不能重复，
创建后不能换号或换前缀。

TODO 的目标、所属阶段、完成标准或影响范围实质改变时，把旧 TODO 设为 `SUPERSEDED`，
创建新 ID，并在旧 TODO 的 `替代 TODO` 中列出新项。对应 `CHG-*` 必须把旧 TODO 列入
`受影响范围`、把替代 TODO 列入 `重新检查 TODO`；替代 TODO 必须留在同一阶段、使用更晚
的编号，并且只属于该变更。

## 5. TODO 格式

每个 TODO 使用：

```markdown
- [ ] `TRN-005` `[TODO]` <具体、可以检查的工作>
  - 任务类型：执行
  - 上级 TODO：TRN-001
  - 需要先完成：TRN-002、TRN-004
  - 完成标准：<项目达到什么可观察结果>
  - 负责人：主 Agent
  - 最近执行结果：NotRun
  - 结果和证据：—
  - 下一步：TRN-005
```

`任务类型`只能使用：

- `阶段任务`
- `阶段开始前检查`
- `阶段完成检查`
- `术语检查`
- `执行`
- `调查`

`阶段开始前检查` 和 `TRN-004` 在 `完成标准` 后增加 `参考文档`。因 `CHG-*` 创建的 TODO 还要
填写：

```markdown
  - 所属变更：CHG-001
```

条件状态还要填写：

- `N/A`：`不适用依据：<结论和 EV 引用>`
- `BLOCKED`：`阻塞原因：<事实>`、`已确认情况：<事实>`
- `SUPERSEDED`：`替代 TODO：<一个或多个 TODO ID>`
- `CANCELLED`：`取消依据：<用户决定和 EV 引用>`

TODO 标题要说明实际工作，`完成标准`不能只写“确认正常”。每次执行后立即更新最近执行
结果、结果和证据、仍需完成的内容以及下一步。

已经结束的 TODO 不改写标题、目标、完成标准或当时结果。新事实推翻旧结论时，保留旧
TODO，增加 `CHG-*` 和新的 TODO。

## 6. TODO 状态和最近执行结果

TODO 状态：

| 状态 | 含义 | 勾选框 |
|---|---|---|
| `TODO` | 已确认要做，尚未开始 | `[ ]` |
| `DOING` | 正在执行 | `[ ]` |
| `BLOCKED` | 仍需完成，但现在有明确阻碍 | `[ ]` |
| `DONE` | 达到完成标准，并有证据 | `[x]` |
| `N/A` | 有证据说明对本任务不适用 | `[x]` |
| `SUPERSEDED` | 已由新的 TODO 替代 | `[x]` |
| `CANCELLED` | 用户改变范围或撤销授权 | `[x]` |

`最近执行结果`只能使用：

`NotRun`、`Succeeded`、`Partial`、`Unavailable`、`Failed`、`Cancelled`、
`OutcomeUnknown`。

这些值描述 Agent 最近一次执行 TODO 的结果，不是 ATT 的正式状态名。ATT 的实际结果和
错误要原样保存在证据中。

- `DONE` 和 `N/A` 的最近执行结果必须是 `Succeeded`；
- `CANCELLED` 的最近执行结果必须是 `Cancelled`；
- `OutcomeUnknown` 必须把 TODO 设为 `BLOCKED`，保留现场并先确认写操作是否生效；
- 执行失败但成功完成了“调查”TODO 时，调查本身写 `Succeeded`，观察到的产品失败写入
  证据；
- 阶段开始前检查、阶段完成检查和术语检查不能设为 `N/A`、`SUPERSEDED` 或
  `CANCELLED`；
- 普通 TODO 进入 `DOING` 前，以及任何 TODO 进入 `DONE` 或 `N/A` 前，`需要先完成` 列出的
  任务必须已经为 `DONE` 或 `N/A`。阶段任务可以在其检查尚未完成时保持 `DOING`，但不能
  提前完成。

阶段确实不适用时，仍要完成开始前检查和完成检查；当前阶段任务可以凭证据设为 `N/A`。

## 7. 阶段总览

阶段总览固定使用：

| 阶段 | 当前状态 | 当前阶段任务 | 当前开始前检查 | 当前完成检查 | 当前术语检查 | 待重新验证的变更 | 下一步 |
|---|---|---|---|---|---|---|---|

每行都指向该阶段当前采用的阶段任务、开始前检查和完成检查，而不是永远指向初始的
`XXX-001/002/003`：

- `当前阶段任务` 的类型必须是 `阶段任务`，其依赖必须包含当前开始前检查和当前完成检查；
- `当前开始前检查` 的类型必须是 `阶段开始前检查`，并填写当前文档；
- `当前完成检查` 的类型必须是 `阶段完成检查`；它必须依赖当前开始前检查，以及本阶段所有
  仍然有效的术语检查、执行和调查 TODO；
- 翻译行的 `当前术语检查` 必须指向当前有效的 `术语检查` TODO；其他四行填写 `—`；
- `当前状态` 必须等于当前阶段任务的状态；
- 阶段为 `DONE` 或 `N/A` 时，当前开始前检查和当前完成检查都必须为 `DONE`，同阶段不能
  还有未完成 TODO，`下一步` 必须指向当前完成检查；
- 阶段尚未完成时，`下一步` 指向本阶段一个尚未完成的 TODO；
- 阶段总览指向的 `下一步` TODO，其自身 `下一步` 也指向自己；全局下一步和交接部分的
  `下一步` 必须一致。

新事实使已经完成的阶段需要重新检查时，不修改旧 `DONE`。为这个阶段新建阶段任务、
开始前检查和完成检查，在三个 TODO 中填写 `所属变更`，更新总览指针，并把阶段状态改回
`TODO`、`DOING` 或 `BLOCKED`。

若新事实使当前术语检查不再有效，还要在同一个 `CHG-*` 下新建 `任务类型：术语检查` 的
TODO，并更新翻译行的 `当前术语检查`。旧术语检查和旧证据作为历史保留。

`待重新验证的变更` 填写当前尚未完成的 `CHG-*`；没有时写 `—`。全局 `下一步` 必须与最早
一个尚未完成阶段的下一步一致。全部阶段完成后，全局下一步指向封包阶段当前完成检查。
除解包外，每个阶段当前采用的开始前检查必须依赖前一阶段当前采用的完成检查。

## 8. 证据

每条证据使用：

```markdown
### EV-001

- 记录时间和类型：2026-07-28 23:51 +08:00；文件
- 来源：绝对路径、命令、日志事件、查询、哈希、输出文件或用户决定
- 观察结果：实际看见的事实
- 支持或否定：TRN-004、CHG-001、FINAL-GOAL
- 适用范围：这条证据能够证明哪些内容
- 当前是否适用：是
```

- 保存准确位置和观察结果，不复制大段日志；
- 不写入敏感值；敏感信息范围只引用
  [Chat Completions 文档](../../../docs/runtime/chat-completions.md)；
- 退出码、Agent 自述、子 Agent 自述和任务清单本身不能单独作为项目结果证据；
- EV 支持 TODO、`CHG-*` 或最终检查时，双方都必须引用对方；
- 证据不再能证明当前项目时，保留原观察，把字段改为
  `当前是否适用：否（CHG-001）`。对应变更必须把受影响的旧 TODO 列出来并建立新的检查
  TODO。

最终检查使用以下固定名称：

- `FINAL-GOAL`：用户目标；
- `FINAL-OUTPUT`：最终文件；
- `FINAL-PRESERVE`：必须保持的行为；
- `FINAL-CONFIG`：配置修改检查。

## 9. 计划发生变化时

计划、TODO 结构、ATT 程序、文档版本或项目事实发生变化时，增加：

```markdown
### CHG-001

- 时间：2026-07-28 23:55 +08:00
- 处理状态：待处理
- 是否修改项目配置：否
- 触发证据：EV-001
- 原计划或判断：……
- 新计划和原因：……
- 其他方案及影响：……
- 受影响范围：TRN-001、TRN-002、TRN-003；翻译阶段
- 重新检查 TODO：TRN-005、TRN-006、TRN-007
- 下一步：TRN-006
```

`受影响范围` 至少列出一个已有 TODO。`重新检查 TODO` 必须覆盖每个受影响阶段，并包含该
阶段新的阶段任务、开始前检查和完成检查；这些 TODO 的 `所属变更` 都要包含本 `CHG-*`。

同一阶段前一个变更处理完之前，不再创建另一个影响该阶段的变更。这样可以明确当前总览
应该指向哪组 TODO。

有 TODO 尚未完成时，`处理状态` 必须是 `待处理`，变更必须出现在每个受影响阶段的
`待重新验证的变更` 中。所有重新检查 TODO 都以当前证据完成后，把状态改为 `已完成`，并从
阶段总览移除该 `CHG-*`。最终检查会遍历全部变更，不能靠在总览中漏写来跳过。

## 10. 修改项目配置时

Rules、Placeholder、术语、Prompt、Lua 或其他项目配置发生实际修改时，把
`是否修改项目配置`写为`是`，并增加：

```markdown
- 参考文档：<docs 根下实际读过的 .md#章节>
- 原因：……
- 使用该配置的位置和影响范围：……
- 修改前检查 TODO：TRN-008
- 修改 TODO：TRN-009
- 修改后检查 TODO：TRN-010
```

三个 TODO 必须：

- 是为这个 `CHG-*` 新建的项目专属 TODO，不能复用固定 TODO 或其他变更的 TODO；
- 都只能填写 `所属变更：CHG-001`，并全部列入 `重新检查 TODO`；
- 使用不同 ID；
- 修改前检查和修改后检查使用 `任务类型：调查`，修改使用 `任务类型：执行`；
- 修改 TODO 依赖修改前检查 TODO；
- 修改后检查 TODO 依赖修改 TODO；
- 最终都必须为 `DONE/Succeeded`，并有当前仍适用的证据；不能用 `N/A` 或其他结束状态跳过。

若任务中有配置修改，`最终检查` 中的 `配置修改检查` 必须列出全部配置 `CHG-*` 和支持
`FINAL-CONFIG` 的当前证据。只有确实没有配置修改时才能写“无配置修改”。

## 11. 中断和多 Agent

继续任务时：

1. 完整读取任务清单和它引用的证据；
2. 核对 ATT 程序、文档版本和项目实际状态；
3. 发现变化时增加 `CHG-*` 和新的检查 TODO；
4. 检查中断时的 `DOING` 是否产生写操作；无法确认时设为
   `OutcomeUnknown`/`BLOCKED`；
5. 从全局`下一步`继续，不重复当前证据已经证明的工作。

主 Agent 是唯一写入者。委派前创建 TODO ID；子 Agent 只返回该 TODO 的观察、实际改动、
证据、结果和不确定性。主 Agent 核对项目后亲自更新任务清单。不要创建锁文件、额外 JSON、
子 Agent 分表或其他平行状态文件。

## 12. 最终检查

交付前必须满足：

- 实际使用的 ATT 与文档版本仍然对应；
- 五个阶段的当前阶段任务均为 `DONE` 或有证据的 `N/A`；
- 各阶段当前开始前检查和当前完成检查均为 `DONE`，翻译阶段当前术语检查也为 `DONE`；
- 没有 `TODO`、`DOING`、`BLOCKED`；
- 每个已完成或不适用的当前 TODO 都有双方互相引用、当前仍适用的证据；
- 所有 `CHG-*` 的处理状态都是`已完成`；
- 阶段总览中没有待重新验证的变更；
- 所有配置修改完成修改前检查、修改和修改后检查；
- 用户目标、最终文件、必须保持的行为和配置修改检查都有对应的当前证据；
- 范围外风险已经明确说明。

运行：

```powershell
uv run --no-project python "<本 Skill 目录>/scripts/validate_task_list.py" "<任务清单>" --final
```

校验脚本只能检查结构、文件引用和相互引用，不能证明 Agent 真的完整阅读了文档，也不能
证明观察内容真实。主 Agent 仍然负责核对项目本身。
