# 全局规划与变更控制

本文件定义创建整体方案、选择 ATT 机制和修改共享配置前的判断门。新建账本、宏观方案
变化、机制升级或修改 Rules、Placeholder、术语、Prompt、Lua 时完整读取。

## 1. 从用户结果建立全局视角

创建账本前至少回答：

1. 用户最终需要完整包、补丁、loose tree、诊断结论还是阶段性候选；
2. 哪个游戏版本、补丁/MOD 组合和运行时加载根构成真实来源；
3. 成功、失败、必须保持的行为和停止线分别是什么；
4. 解包、提取、翻译、写回、封包之间如何交接；
5. 哪些事实已经由项目状态建立，哪些必须调查，哪些只能由用户选择；
6. 哪些共享资源会影响多个 Owner、kind、文件或阶段；
7. 用什么项目证据证明覆盖、翻译、写回和最终交付成立。

局部错误样本只能作为调查入口，不能直接成为方案边界。先找语义所有者和全部现实消费者，
再决定最早责任阶段。

## 2. 机制选择

读取 [RPG Maker 调查与机制选择指南](../../../docs/rpg-maker/README.md)，按现实消费选择：

- Builtin 已准确覆盖时复用 Builtin。
- 静态、确定、可由路径和规则稳定定位且可逆写回时使用 Rules。
- 一对一接入 Standard 位置语义时使用 Lua Standard。
- Lua 负责私有发现和写回映射、单位可独立翻译时默认使用 Managed：
  `replace → translate/open → open`。
- 只有 Managed 无法表达私有 grammar、跨 unit 原子关系、特殊模型协议或私有恢复状态时，
  才采用低级 `ctx.translation`、`ctx.llm`、`ctx.db`。
- 人工 Standard 候选通过 `ctx.standard` 验收和提交，不用 SQL 绕过受管语义。

选择低级 Lua 时，账本必须写明为什么高级契约不足，以及脚本自己承担的：

- 稳定身份与跨阶段交接；
- 模型输入输出协议与逐项验收；
- 并发、重试、取消和错误传播；
- 事务、幂等、提交终态和恢复；
- 私有状态与 ATT 受管状态的边界。

宿主不会自动降级，也不会把低级 `ctx.llm` 变成 Managed。

## 3. 复用审计

写 Rules 或 Lua 前先检查当前 ATT 能力：

1. 语义、规则、不变量和生命周期一致时直接复用；
2. 只有部分职责一致时，让项目脚本复用相应高级接口并保留私有映射；
3. 语义不同才保留独立低级协议。

不要因为“Lua 能写”就把 ATT 已拥有的去重、临时 ID、JSON、`<why>`、并发、重试、验收、
state、增量提交或 task-records 重写一遍。也不要因为 Managed 存在就禁止低级接口。

## 4. 授权边界

只读分析、解释和建议不授权写配置或项目。

用户已经授权执行翻译、修复或交付时，可以自主修改任务范围内、可恢复且有证据支持的：

- Extract Rules；
- Placeholder；
- 术语；
- Prompt；
- 项目 Lua；
- 其他不改变用户产品选择的项目语义工件。

以下事项必须由用户选择或再次授权：

- API key；
- 模型、成本或供应商；
- 源/目标语言；
- 外部服务；
- 任务或文件范围扩大；
- 覆盖唯一原件、不可恢复发布或其他不可逆副作用。

## 5. 配置变更门

每次实际配置修改都在账本创建一个 `配置变更：是` 的 `CHG-*`，并完成：

1. 记录根因，不只记录触发错误的样本。
2. 识别语义所有者、所有现实消费者、Owner、kind、scope、真实输入和下游状态。
3. 建立修改前基线。
4. 比较候选方案会保留和损失的行为、维护成本与验证成本。
5. 选择全局代价最小且可验证的方案。
6. 建立独立的修改、修改前验证和修改后验证 TODO。
7. 对完整受影响集合执行差分或等价全量验证。
8. 记录验证结果，并为所有失效下游结论建立重验 TODO。

范围未证实、验证失败或副作用终态不明时，阻止依赖该配置的后续阶段。

## 6. Placeholder 专项门

修改前完整读取 [Rules 现行规格](../../../docs/rpg-maker/rules.md) 和
[Translate 现行规格](../../../docs/rpg-maker/translation.md)。

按实际 kind 枚举：

- Standard Builtin；
- Rules；
- Lua Standard；
- Managed；
- 低级 `translation.prepare(kind, original, ...)` 的真实 `original`。

对现行与候选规则比较：

- 每条规则产生的实际保护跨度；
- 候选新增保护；
- 候选丢失的独有保护；
- Custom/Custom 重叠；
- Custom/Builtin 重叠；
- scope 改变影响的 kind；
- 受影响翻译 state 与需要重跑的阶段。

省略 `scopes` 的含义只从现行规格读取，不得假设它属于某个 Lua 文件或 Owner。

错误示范：只因 `\iw[${...}]` 中外层与内层规则重叠，就删除 `${...}` 规则并直接续跑。
这没有检查其他位置独立存在的 JavaScript 插值，不能证明安全。候选方案必须同时保护
外层完整控制符和真实独立插值，并以全量跨度差分证明不重叠、不漏保。

## 7. 变化与下游失效

把问题归到最早责任阶段：

- 来源版本、加载根、发行结构：解包；
- 漏收、误收、错组、kind、shape、context、recipe、Claim、身份或映射：提取；
- Profile、Prompt、Client、语言、术语、Placeholder、候选验收：翻译；
- 目标映射、候选结构、布局、发布：写回；
- 包格式、组装、运行时加载最终制品：封包。

上游改变后，不删除旧证据或倒改旧 `DONE`。追加 `CHG-*`，指出哪些旧结论失效，创建
新的重验 TODO，并更新阶段总览的最新有效验收。不要机械清库或重做仍由 current 权威状态
证明有效的工作。
