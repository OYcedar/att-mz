# 用 ATT 完成 RPG Maker 翻译

## 任务清单是必需的

负责整个任务并向用户交付结果的执行者是任务负责人。任务负责人必须亲自创建并持续更新
一个 Markdown 任务清单。只执行其中一项受托工作的协作者不得修改任务清单，只向任务
负责人返回结果和证据。

任务清单用于记录整体方案、当前工作、真实结果、重要决定和完成依据。通过它应能看出工作
是否覆盖完整、为什么改变方案、遇到问题后应从哪里继续。ATT 的数据库、日志、
`task-records` 和输出文件记录产品实际发生的事情；任务清单引用这些事实，但不替代它们。

清单的固定阶段只有：

1. 提取
2. 翻译
3. 写回

不要增加固定的前置或后置阶段，也不要为不适用的工作预建 TODO。项目确实需要的额外工作
直接写成当前项目的普通 TODO。
人工审校、修订已保存译文和处理 Current 但质量不满意的结果都属于翻译阶段，不增加第四
阶段。

## 只使用实际发布目录中的 ATT 资料

解释任何 ATT 行为之前，先确定本任务实际会调用的 `att.exe` 绝对路径。该文件的父目录
就是本任务唯一的 ATT 发布目录。产品文档只从这个目录读取：

- `docs/README.md` 及其链接的现行文档；
- 默认的 `config.toml` 和 `prompts/`。

用户另行指定配置时，按产品文档解析该配置及其 `prompts.root`，只使用明确解析出的实际
Prompt 目录，不搜索其他候选位置。任务清单记录 ATT 发布目录、程序标识、实际程序、产品
文档、配置和 Prompt 目录的绝对路径。Skill 自身目录只用于读取本 Skill 的模板和工作要求，
不能作为产品文档位置。

发布目录缺少本任务需要的程序、文档或 Prompt 时，停止新的项目修改并报告缺少的内容；
已有任务清单时同时记录阻塞。不得转而查找 ATT 源码仓库、Git 历史、`target/` 构建目录，
不得要求用户下载源码或自行使用 Cargo 编译，也不得用旧对话或试运行猜测产品行为。

## 开始或继续任务

1. 完整读取 [工作要求](references/workflow.md)。
2. 从实际发布目录完整读取 `docs/README.md`，再读取本次操作需要的产品文档。
3. 先做只读调查，了解用户目标、实际游戏来源和加载位置、引擎、ATT 项目状态、现有配置、
   玩家可见文本来源、已有译文、输出要求和主要风险。
4. 从整个项目形成宏观方案，说明提取、翻译、写回如何衔接，以及如何证明最终结果。仍未
   确认但不会改变宏观路线的事实，写成当前阶段的调查 TODO。
5. 在稳定的任务工作目录中寻找同一 ATT 项目的未完成任务清单。找到时完整读取并与项目
   实际状态核对；没有时，任务负责人亲自按
   [任务清单模板](assets/task-list-template.md)创建
   `<任务工作目录>/ATT-翻译任务-<项目名>-<YYYYMMDD>.md`；同名文件已存在时追加简短
   序号，不覆盖旧清单。
6. 只展开当前阶段的真实 TODO。后续阶段只保留简短的等待说明，进入该阶段时再根据最新
   事实展开。

任务清单不要放进原始游戏、候选输出、最终输出、临时目录、日志目录、`task-records` 或
Skill 安装目录。相同任务只维护一个文件，完成后原地保留。

## 编写和更新 TODO

每个阶段至少应让人看出三件事：输入和范围已经核实、实际工作已经完成、结果已经验证。
根据项目规模决定 TODO 数量；能由同一项工作自然完成并验证时可以合并，存在不同风险、
授权、恢复点或证据时再拆分。

TODO 只使用 Markdown 复选框：

```markdown
- [ ] <具体工作>
  - 完成标准：<能够观察和检查的结果>
```

完成后立即改为：

```markdown
- [x] <具体工作>
  - 完成标准：<原有标准>
  - 结果：<简短结论>
  - 证据：<文件、数据库查询、ATT 输出、日志位置或运行结果>
```

规则如下：

- 执行项目修改或外部请求前，先确认任务清单中有对应 TODO。
- 任务开始、完成、部分完成或阻塞时立即更新清单，不在工作结束后凭记忆补写。
- 只在任务信息的“当前状态”中记录当前阶段、当前 TODO、下一步和阻塞；不要在每个 TODO
  重复负责人、状态、下一步或依赖表。
- 命令退出码、目录存在、日志存在或口头声明不能单独证明完成。记录实际结果及其位置。
- 大段日志、请求正文和截图保存在原位置；任务清单只写结论和可定位的证据。
- 尚未开始的 TODO 可按新事实直接修改或删除。已经完成的记录不改写；若其结论失效，
  增加一个具体的重新检查 TODO，并在“重要决定”中简要说明原因和影响。
- 只有目标、范围、输入来源、授权、项目配置或已验收结果发生实质变化时才记录重要决定，
  不为日常操作建立编号、替代关系或变更图。

## 项目配置、术语和 Lua

用户授权执行翻译、修复或交付时，可以修改任务范围内且可恢复的 Rules、Placeholder、
术语、Prompt、项目 Lua 和其他项目配置。修改前必须阅读实际发布目录中的相关产品文档，
查清原因、所有实际使用位置和影响范围，保留修改前结果，并在完整受影响内容上比较修改
前后结果。通常在一个 TODO 内记录原因、修改和验证；只有实际工作需要独立授权、恢复或
交接时才拆分。

修改 Placeholder 不能只验证触发问题的一个字符串。必须检查所有会使用这份配置的真实
文本来源，比较修改前后的命中、漏掉内容、错误命中、重叠和保护范围。更详细的调查要求见
[工作要求](references/workflow.md)。

正式批量翻译前，必须根据全部玩家可见文本建立并验证术语资源。MV/MZ 特殊字段和引擎
结构可以帮助发现候选词，但不能代替对全部文本及其实际使用位置的检查。没有值得固定的
术语时，也要记录调查结论和证据。

使用 Lua 或人工修订已保存译文前，读取发布目录中的 RPG Maker、翻译与 Lua 文档，并按
译文责任选择接口：

- Standard 译文使用产品提供的独立项目 Lua `ctx.standard.open()` 与
  `standard:accept(...)` 人工候选接口；
- Managed 译文只使用产品文档明确提供的托管能力；没有人工替换接口时报告能力缺口；
- 低级 Lua 私有协议只修改脚本自己负责的私有状态，并自行承担文档规定的状态和事务责任。

不得用 SQL 直接修改 ATT 受管翻译表，也不得伪造 Prompt、context、instruction 或其他
语义变化来强制译文失效。具体选择、修订和验证要求见
[工作要求](references/workflow.md#人工审校与修订已保存译文)；API、参数和错误行为只以
本次发布目录中的产品文档为准。

不得自行改变 API key、模型、供应商、费用选择、源语言、目标语言、外部服务或用户要求
的范围，不得覆盖唯一原件或执行不可恢复的操作。缺少这些决定时停止并向用户说明。

## 中断、阻塞和协作

继续任务或接手任务时，先完整读取任务清单，再核对实际 ATT 发布目录、项目状态和证据。
只继续当前证据仍然支持的工作。

任务负责人是任务清单的唯一写入者。委派工作前先建立具体 TODO；协作者只返回观察结果、
实际改动、证据位置、不确定性和建议。任务负责人核对项目事实后亲自更新任务清单。

以下情况立即停止依赖该事实的后续工作，更新“当前状态”并向用户报告：

- 产品文档、必要资源或用户决定缺失；
- 实际输入、写操作结果或数据库提交状态无法确认；
- 配置影响范围尚未查清或修改后验证失败；
- 连续执行没有有效进展；
- 继续操作会扩大范围、提高费用或造成不可恢复的改变。

## 完成任务

只有以下条件全部满足，才能把任务写为完成：

- 本次约定范围涉及的阶段都有当前证据；完整游戏翻译必须覆盖提取、翻译和写回；
- 范围内没有未完成或阻塞的 TODO；
- 完整游戏翻译没有未解释的玩家可见文本遗漏、未翻译内容或写回差异；
- 本次范围包含最终可运行输出时，输出已在实际加载位置通过必要检查；
- 所有项目配置修改都完成了完整影响检查和修改后验证；
- “最终交付”写明输出、验证结果、未验证内容和剩余风险。

最终回复以任务清单和实际证据为依据，说明交付结果、改动、验证、未验证内容和风险。若
项目因阻塞停止，应明确报告阻塞事实和恢复所需条件，不把部分进度写成完成。
