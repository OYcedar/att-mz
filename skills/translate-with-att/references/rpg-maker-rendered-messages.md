# RPG Maker 动态消息的最终显示消费者

源字段已有当前译文，但战斗结果、姓名或其他动态消息仍显示原文时，使用本页。先按来源修复，
只有真实加载链路无法由现有规则完整回填时，才考虑范围明确的游戏侧显示适配。

## 比较实际消息，而不是推测来源

截图可以确定待定位的显示结果，不能可靠给出全角、半角标点、控制码或插值前的原始字节。
核对已加载的译本、当前模板和运行时完整消息；整句与原版模板不同，不应直接推定为旧存档。
全新存档也复现时，停止沿用该解释，检查当前生成与显示链路。

原生 MV/MZ 的 `Game_Message.add` 把传入文本追加到 `_texts`，`allText` 只以 LF 拼接该数组，
不会重新读取姓名或消息模板；可对照 [MV 公开源码](https://github.com/rpgtkoolmv/corescript/blob/master/js/rpg_objects/Game_Message.js)。
遇到“入队已译、读出却含原文”的记录，分别保存 `add` 入参、调用完成后的队列快照、
`allText` 返回值和转义后的文本，定位差异首次出现的位置，再检查实际插件覆写与队列修改。
队列中的字符串未变时，原生 `allText` 不会自行改写译文。某个读取边界的修正有效，只能证明
该处输出得到改善，实际改写者仍需另行定位。

按当前游戏的实际覆写顺序追踪生成者、消息队列、合并读取、转义插值、文字状态和绘字调用。
标准 MZ 链路常涉及 `Game_Message.add/allText`、`Window_Message.startMessage`、
`createTextState`、`convertEscapeCharacters` 与 `Bitmap.drawText`；MV、插件自有窗口、
直接画布绘字和图片资源应分别核对。某条路径没有被观察到，就保留其验证限制。

完整消息与单次绘字输入要分开记录。MZ 的文字缓冲会在控制字符或消息更新边界刷新，MV 的
普通字符绘制也可能逐字调用 `Bitmap.drawText`；一次调用未必包含整句。核对依据包括
[MZ 1.1.0 的窗口实现](https://github.com/stak/rmmz-corescript/blob/master/rmmz_windows.js)与
[MV 的窗口基类](https://github.com/rpgtkoolmv/corescript/blob/master/js/rpg_windows/Window_Base.js)，
目标版本及活动插件仍以实际脚本为准。

## 混合字段、标点和姓名转义

检查原版／当前姓名、队伍模板和消息模板的实际组合，不只测试一条人工选出的完整原句。
组合输出必须仍由当前 ATT 字段和既有术语绑定产生；无法与原版模板对应的实际消息，单独提取到
Generic，按自然 ID 使用已验收输出。

若确有全角、半角或等价 Unicode 形式导致查找失配，可仅在私有显示映射的键上规范化，并检查
碰撞及不应命中的反例。不得因此改变 ATT 原文、自然 ID、技术键、模型输入或保存的译文。
已经是 ATT 结果的文字保持原样；不能把它再次匹配到另一条标点或措辞不同的结果。

姓名可能经 `\N[n]`、`\P[n]` 或插件代码在转义处理时插入。只在队列入口匹配，可能看不到
最终姓名；只改角色姓名 getter，也可能遗漏绕过该 getter 的文字。根据已确认的消费者检查转义
处理后的完整输入。颜色、字号、等待及其他控制语义按当前引擎、插件和
[Placeholder 合约](../../../docs/translation/placeholders.md)保留，图标与未解析变量不能任意
当作零宽内容删除；含控制码的修复应核对顺序、数量、边界和对应行为。

## 插件覆写与有限显示适配

子类可能拥有自己的 `createTextState`，或在加载时捕获旧基类方法。仅替换基类原型不证明消息
窗口使用了新实现；核对实际类、捕获关系及加载顺序。直接绘字也可能绕过消息队列。需要适配时，
在能够取得完整消息的位置处理已登记文本，再让修正后的文字进入既有排版与绘制流程。
仅在 `Bitmap.drawText` 中更换实参，会让上层已计算的宽度、游标推进或文字状态仍基于旧文字，
也可能匹配不到已被拆分的整句。适配器应保留控制语义、样式和调用契约，让测量与绘制使用
同一实际文本；不用全文替换或游戏名、资源名的模糊匹配覆盖未知内容。

显示适配及其格式验收属于游戏侧边界，不能声称 ATT 已原生管理该运行时协议，也不能把这个
局部补丁作为所有 RPG Maker 游戏的默认实现。明确维护者、来源绑定、安装和恢复方式；整体
WriteBack、字体或资源合并后，核对适配器仍在实际消费者使用的位置。

## 取证与验收边界

结构验证应复现旧失败，并覆盖不同字段组合、标点宽度、姓名插值、控制码、已译文字、未登记
消息，以及插件捕获旧方法的情形。使用实际引擎与插件实现，必要环境根接口可隔离。测试数、
current 数、哈希或直接输入已登记译文的测试，不是实机恢复证明。

实玩取证遵守任务发起者指定的操作范围。需要被动记录时，仅记录当前反馈场景的加载来源、
输入／输出及调用栈，限量写入明确的工作目录，捕获诊断失败以免阻断游戏；不附带自动启动、
跳场景或操作存档。避免把含非 ASCII 路径的代码嵌套转义或整体替换反斜杠；路径从可靠的原生
值逐层构造，并独立验证实际输出位置。发生诊断错误时恢复临时改动，不能把错误窗口作为
原游戏异常或翻译失败的证据。

分别记录字段／部署验证、实际运行字符串链路与人工画面确认。人工确认修好后，保留该范围
及最后已证实的更正点，不把仍未知的中间改写者写成已确定根因。完整验收边界见
[人工实机验证](../../../docs/guides/acceptance.md#6-人工实机验证)。
