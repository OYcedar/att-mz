# Unity TMP 字体修复与 MOD 交付经验

## 适用结构与验证范围

适用于 Unity 游戏已具备目标语言文本，但个别 TextMeshPro（TMP）界面显示方框，且需要选择
静态字体资源修复或运行时字体插件的任务。普通 `UnityEngine.UI.Text`、图片字和真正漏译的
文本应回到各自消费者调查，不直接套用 TMP 后备字体方案。

真实材料已验证缺字日志与字体资源的对应关系、内置中文源字体覆盖、静态资源修改后的重读、
差分重建与原文件恢复。运行时插件已完成针对目标游戏程序集的编译与模拟对象逻辑检查；
这些证据不证明 Unity 中实际加载、渲染、描边和布局正常，也不证明任何平台已经审核通过。
本条目不表示 ATT 已实现 Unity 原生提取、资源回填或插件生成。

上述验证只覆盖当时的目标构建。下文 Windows IL2CPP 类型树恢复路径依据 UnityPy 实现，当前
材料未提供该路径的目标游戏实测记录；具体解析与序列化往返需在目标构建上验证。

## 从显示问题定位消费者

- 截图出现方框时，先查看当前游戏日志。TMP 缺字警告可同时给出 Unicode、字体资产名称和
  文本对象名称；用这三项关联实际界面、字体和后备链，不先重翻已有文本或全局替换字体。
- 区分“运行时字符串已有目标语言字符，但当前字体找不到 glyph”与“字符串本身仍是原文、
  乱码或替换符”。前者进入字体修复，后者继续追溯文本来源、编码和写回。
- 记录当前游戏构建、Unity 版本、Mono/IL2CPP、已有加载器及文本组件。菜单正文、章节标题
  和特效文字可能使用不同字体；某个界面显示正常不代表其他消费者共用同一后备链。

## 检查 TMP 后备字体

- 先检查目标字体的 `fallbackFontAssetTable`、全局 TMP Settings 和已有内置中文字体；
  能复用内置字体时，保留原主字体与其他后备项，只补充已确认缺失的关系。
- 静态字体检查 character/glyph table 和 atlas；动态字体同时检查 atlas population mode、
  `sourceFontFile`、源字体字符映射和 atlas 配置。动态字体的初始字符表为空，不足以说明它
  不支持中文；源字体覆盖完整目标字符集，也仍不等于运行时能成功生成和显示所有 glyph。
- 核对材质与 TMP Settings 的 `matchMaterialPreset`。该选项影响后备字形的材质选择，不能
  据此承诺原描边、阴影和行高已经保持；这些效果仍交给人工在原场景复核。

接口语义参照 Unity 的 [TMP_FontAsset 文档](https://docs.unity3d.com/Packages/com.unity.textmeshpro@3.0/api/TMPro.TMP_FontAsset.html)
和 [TMP_Settings 文档](https://docs.unity3d.com/Packages/com.unity.textmeshpro@3.0/api/TMPro.TMP_Settings.html)。
文档版本仅用于解释字段，具体成员、类型和可写性仍以目标游戏程序集为准。

## 静态资源修复

- 在隔离副本上使用与目标 Unity 版本相符的资源读取工具。MonoBehaviour 类型树缺失导致
  读取失败时，不把失败当作“没有字体资产”；按运行时选择同一游戏构建的类型信息来源。
  Mono 使用 `Managed` 程序集；Windows IL2CPP 使用 `GameAssembly.dll` 与
  `<游戏名>_Data/il2cpp_data/Metadata/global-metadata.dat`。加载方法参照
  [UnityPy 类型树生成实现](https://github.com/K0lb3/UnityPy/blob/master/UnityPy/helpers/TypeTreeGenerator.py)。
- 大型资源文件先按类型及 MonoBehaviour 头部名称筛选候选，再生成类型树和完整反序列化。
  对所有组件无差别展开，可能把字体调查变成整份游戏数据的昂贵解析。UnityPy 可用
  `parse_monobehaviour_head()` 做候选筛选，但正式读写仍需完整类型信息。
- 跨资源引用同时核对外部文件表和对象标识。`m_FileID` 的含义属于当前资源文件，不能把
  某个文件中的编号直接复制到另一文件；相同对象编号也不是跨文件唯一身份。
- 保存前验证未修改对象的序列化往返；保存后重新解析修改对象，解析实际后备目标，并比较
  非目标对象的原始数据。区分容器布局变化与对象内容变化，不能只用文件存在或整体哈希变化
  证明语义正确。暂存资源若不在原目录，重读时显式提供匹配的依赖或类型信息，避免把依赖缺失
  误认为补丁损坏。
- 写入前校验原件和备份，写入后校验安装产物。差分方案还需分别验证正确原件重建、重复安装、
  不匹配输入在替换前被拒绝，以及卸载恢复。补丁只允许适用的输入，游戏更新后重新调查。

## 用户选择运行时插件时

运行时字体修复与静态资源替换是不同交付方式。只有任务范围包含运行时插件时才采用加载器；
它不承担自动翻译，也不应被描述成静态汉化成品。

- 按实际加载器版本、Mono/IL2CPP 和游戏程序集选择依赖；BepInEx 的不同运行时入口不能互换。
  检查目标 TMP 字符查找前的调用点和真实签名，再选择 hook，不照搬其他游戏的方法参数。
- 只处理已确认的字体或消费者，保留已有后备项，防止重复和循环引用。运行时 clone 的名称或
  身份匹配要有实际消费者证据，不扩成所有文字的全局字体替换。
- 中文字体可能晚于目标文字加载。按需寻找后备字体；需要重试时限制重复扫描，并在成功后让
  等待中的文字重新生成。不要每帧扫描全部资源；场景切换、失效对象和不再活动的文字也要处理。
- 停用或卸载时只移除本插件添加的引用和 hook，保留其他插件及原有后备链。游戏资产不写盘，
  不把关闭游戏后消失的内存修改描述为永久资源修复。
- 从静态版切换前，恢复本轮已确认的有效原件；仅删除 DLL 不会撤销旧静态补丁。若当前文件已
  更新或被其他 MOD 修改，先重新定位差异，不覆盖未知状态或把旧版备份写回新版游戏。

## 封包、审核与人工验收

- 根据交付方式说明准确目录、依赖、支持版本、覆盖范围、升级与卸载动作；不把作者机器已有
  BepInEx 当成下载者也已安装。面向中英使用者发布时，说明、日志和发布文案保持一致。
- 源码编译成功、逻辑模拟通过、安装文件校验通过、实机显示正常和平台审核通过分别报告。
  人工检查原问题界面、其他语言、场景切换、首次字体加载、描边、裁切和布局；未完成项明确列出。
- 发布前核对平台当前规则。独立安装 EXE 和插件 DLL 都可能需要人工审核；改成 BepInEx 不保证
  免审。隔离提示可能涉及文件类型、扫描告警或压缩结构，通用提示不足以确定具体原因，更不能
  把本地功能测试当成病毒扫描结论。
- Nexus 隔离时保留被隔离文件和版本记录，按其审核入口提供 MOD 链接、对应源码与编译步骤。
  使用正常可扫描的压缩结构；不要加密、改后缀或嵌套打包来规避检查。公开完整游戏资源还需确认
  其分发许可，不能把完整资源替换包当作审核问题已经解决。

平台要求以 [Nexus 隔离说明](https://help.nexusmods.com/article/117-why-has-my-mod-been-quarantined)
和[文件提交规则](https://help.nexusmods.com/article/28-file-submission-guidelines)为准，发布时重新核对。
