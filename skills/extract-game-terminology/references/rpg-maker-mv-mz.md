# RPG Maker MV/MZ 术语抓取参考

本参考用于从 RPG Maker MV/MZ 游戏中发现术语候选。它不把数据库字段直接等同于术语，
也不假设所有游戏都保持编辑器的默认目录、文件内容或插件结构。

## 先确认实际部署

1. 确认游戏确实使用 MV 或 MZ，并记录游戏版本、补丁与 MOD。
2. 找到运行时实际读取的数据根、脚本与插件配置；打包器、自定义加载器和插件可能改变
   默认位置或增加其他来源。
3. 区分玩家可见内容、编辑器名称、内部 ID、调试文本和未使用资源。
4. 保留文件路径、数据库 ID、地图或事件位置，以及能解释含义的上下文。

无法证明游戏会读取或显示的内容只作为待查候选，不直接进入术语表。

## 按信息密度检查标准数据

### 系统与类别名称

优先查看 `data/System.json`。其中的游戏标题、货币、元素、技能类型、武器类型、防具
类型、装备类型、参数名、命令名和消息模板可能包含游戏专有名称或游戏内有明确定义的词。

这些数组和字段同样可能只是常规界面词。先用教程、技能说明、状态说明和实际界面确认其
专门含义；不要把“攻击”“防御”“物品”等默认或普通词自动收入。

### 实体数据库

按实际存在的文件检查：

- `data/Actors.json`：角色名、昵称、简介；
- `data/Classes.json`：职业或身份名称；
- `data/Skills.json`：技能名、说明和使用消息；
- `data/Items.json`、`data/Weapons.json`、`data/Armors.json`：物品与装备名称及说明；
- `data/Enemies.json`：敌人名称；
- `data/States.json`：状态名称、说明性消息；
- 其他由当前游戏或插件实际读取的数据库文件。

把名称字段当作高密度候选源，把描述和消息当作定义与上下文证据。数据库中的每个 `name`
都不是术语：普通物品类别、常见动物、数字变体、占位名和内部测试项需要按通用收录标准
排除。

### 地图、事件与叙事文本

检查 `data/MapInfos.json`、实际 `data/MapNNN.json`、`data/CommonEvents.json` 和当前游戏
使用的其他事件数据，重点寻找：

- 地图显示名与世界地点；
- 对话、选择项、滚动文本和人物介绍；
- 教程、规则说明、任务与图鉴内容；
- 改名、称号、组织、事件和时代的首次说明；
- 脚本或插件命令参数中实际显示的字符串。

`MapInfos.json` 的名称和事件编辑器中的备注可能只供开发者识别。应通过地图显示名、传送
文本、界面或对话证明玩家看到的名称。地图事件还能说明同一个候选在剧情里指向什么，
不要只从孤立名称定译。

## 检查插件与自定义系统

查看 `js/plugins.js` 中实际启用的插件及其参数，再按需要检查对应的 `js/plugins/*.js`、
外部配置和插件数据文件。

插件参数可能把结构化对象或数组再次编码成字符串。先按插件实际读取方式解码，再找玩家
可见的系统名称、属性、资源、状态和机制说明。不要把参数键、JavaScript 标识符、插件
命令名或源码注释本身当作术语；只有运行时显示或明确规定游戏概念的内容才进入候选。

自定义战斗、养成、任务、合成、卡牌或其他系统往往同时在以下位置留下证据：

- 系统界面标签；
- 教程与帮助；
- 技能、物品或状态说明；
- 插件参数中的显示名称；
- 剧情对话中的简称或世界观说法。

把这些证据合在一起判断身份和定义，避免只凭一个短标签猜测。

## 建立三份相互关联的记录

### 1. 结构化候选表

从名称密集字段收集原文、文件、数据库 ID、字段和相邻描述。保留自然顺序与来源，不先
删除看似普通的词，以便后续用规则说明排除原因。

### 2. 使用位置索引

在全部实际语料中回查候选及其表记变体，记录出现次数与上下文。次数只用于定位重要位置
和发现变体；一次出现的关键角色名仍可能需要收录，高频普通词仍然不应收录。

搜索时同时注意：

- 平假名、片假名、汉字、拉丁字母等表记变化；
- 大小写、空格、全半角和标点差异；
- 姓名全称、简称、称号和旧称；
- 文本控制符或插件包装分隔出的可见正文；
- JSON 字符串内的转义与插件参数中的嵌套编码。

只有证据证明属于同一身份时才合并变体。

### 3. 定义与决定表

为候选寻找教程、说明、首次登场和实际效果，写明游戏内身份或定义，再应用通用 Skill 的
收录判断。推荐至少区分：

- 接受：身份或定义明确，且固定写法确有价值；
- 拒绝：普通词、无一致性收益、未使用内容或错误候选；
- 待确认：身份、作用域、官方写法或含义仍缺证据。

不要把待确认项静默变成正式术语。

## 常见判断示例

| 候选 | 证据 | 判断 |
|---|---|---|
| 某角色、国家或组织的名称 | 数据库名称与剧情指向同一实体，存在多种合理译法 | 收录 |
| “意志” | 教程把它定义为独立属性，技能与界面反复引用 | 可收录 |
| “破防” | 战斗说明定义了触发、状态或效果，其他位置必须保持同名 | 可收录 |
| “虚空” | 指向一个命名世界或明确设定概念 | 收录；若只是普通“空无”则拒绝 |
| “药草”“森林”“攻击” | 只有普通词义，没有游戏专门身份或定义 | 拒绝 |
| 官方要求原样保留的品牌名 | 当前作品的权威材料规定固定拼写 | 收录并保留原样 |

## 完成检查

- 标准数据库、地图事件、公共事件、实际启用插件和外部文本来源都已按范围检查；
- 每个接受项都有文件与上下文证据，而不只有数据库字段名；
- 表面普通但由游戏明确定义的词没有因词性被漏掉；
- 普通名词没有因高频、名称字段或界面位置被误收；
- 编辑器专用名、内部 ID、注释、未使用资源和插件实现标识已经排除；
- 同形异义、简称、表记差异和嵌套编码经过复查；
- 接受、拒绝和待确认项的理由清楚，最终术语表只包含接受项。
