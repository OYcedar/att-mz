# 通用游戏术语规则

本文件只规定什么值得成为术语、如何选择固定写法、保存什么证据以及怎样验收最终结果。
Formic、ATT 或其他工具的输入输出格式不改变这些判断。

## 分清术语判断与下游格式

先确认游戏版本、源语言、目标语言、实际语料范围、已有官方译名，以及最终由谁消费术语表。
先形成与工具无关的术语结果，再读取下游系统的现行文档，把已确认条目转换成它支持的字段。
不要让 TOML、CSV、JSON 或某个工具的匹配字段反过来决定收录范围，也不要凭记忆猜测下游
格式。

术语表不是普通词典、分词结果、词频表、完整命名实体列表或全文翻译。它保存的是游戏中
确实需要统一的命名决定。

处理小说、剧本或其他非游戏文本时，把“游戏内”换成“当前作品或语料内”：只收录作品
特有名称和在作品中有明确定义的词，并继续使用相同的一致性与权威形式判断。

## 使用两项必要判断

仅在以下两项同时成立时收入最终术语表：

1. **游戏内身份或定义成立**：表达指向游戏专有名称，或者在游戏内具有明确、稳定的专门
   含义；
2. **固定写法确有价值**：统一写法能够实际减少歧义或不一致，或者已有外部权威要求必须
   保持某个名称、拼写或形式。

可以把判断写成：

```text
收录 = （游戏专有名称 或 游戏内有明确定义的词）
    且（存在合理译法分歧 或 统一后能减少歧义/不一致 或 有权威形式约束）
```

“两个合格译者独立翻译时是否可能给出不同但都说得通的译法”是判断第二项的主要信号，
但不是唯一信号。官方名称、不可翻译的品牌名、必须保持的大小写、符号、罗马字或其他
固定拼写，即使译法看似明确，也可以成为术语。

游戏专有名称包括有特定身份的角色、地点、组织、种族、神祇、称号、事件、时代、世界、
专属物品或技能。游戏内有明确定义的词还包括被规则、教程、界面或剧情赋予专门含义的
属性、资源、状态和机制；“意志”“破防”“虚空”这类表面普通的词，只有在当前游戏中
确实指向固定属性、机制或世界时才进入候选。

排除以下内容：

- 没有游戏特定身份或定义的普通名词、动词、形容词和常见界面词；
- 只因高频、首字母大写、位于 `name` 字段或被实体识别器标出而产生的条目；
- 两个译者通常会自然得到同一结果，且没有官方形式约束的普通表达；
- 缺少上下文、无法确认身份，或只能靠猜测补全含义的字符串；
- 只在一句话中成立、无法安全推广为固定写法的临时措辞。

词频和结构化字段只能帮助发现候选，不能证明它是术语。专有名称也不是自动收录项；若
没有一致性收益或形式约束，同样删除。

## 从实际语料抓取

### 1. 确认语料与权威来源

- 找到游戏实际运行时读取的文件、版本、补丁和 MOD，不用目录名或编辑器残留代替运行
  事实。
- 记录已有官方本地化、开发者材料、系列前作、用户指定译名和不可改写清单。区分官方
  事实、社区惯例与待确认建议。
- 明确哪些内容玩家可见；内部 ID、脚本变量、编辑器备注和未使用资源不能自动进入术语
  范围。

### 2. 建立带位置的候选集

从多个来源取候选，而不是只扫一种字段：

- 结构化数据库中的名称、分类、系统枚举和描述；
- 对话、旁白、任务、图鉴、教程和帮助文本；
- 技能、物品、状态与机制说明；
- 插件、配置、脚本资源和外部文本包中实际显示的内容；
- 官方材料中明确绑定到当前游戏实体或概念的名称。

为每个候选保留文件、记录 ID、字段或行号以及至少一段有效上下文。统计次数、字符形态、
共同出现词和重复位置可用于扩大搜索，但不要直接生成最终条目。模型或实体识别工具给出的
结果也只是候选，必须回到语料核实。

### 3. 恢复身份、定义和使用范围

查找候选的首次介绍、规则说明、教程、描述和后续用例，回答：

- 它具体指向谁或什么；
- 它是唯一实体、类别名称，还是游戏定义的机制；
- 相同写法在别处是否仍是同一含义；
- 大小写、全半角、词形、简称和别名是否属于同一术语；
- 玩家是否需要借助统一写法识别跨场景的同一概念。

同形字符串存在多个含义时，不要强行建立全局映射。先分开身份和证据；只有下游系统支持
所需作用域时才导出带作用域的规则，否则保留为待人工处理项。

### 4. 决定固定写法

按当前任务可用的权威程度选择译名：

1. 用户指定且适用于当前版本的名称；
2. 当前作品的官方名称或固定拼写；
3. 同系列官方材料中确认指向同一对象的名称；
4. 游戏内定义、发音、构词关系和整套命名体系；
5. 在上述证据约束下提出的译名建议。

不要把社区常用写法冒充官方名称，也不要用系列中相似但身份不同的对象套用译名。需要
保留原文、品牌形式、大小写或符号时，把原样形式记为要求，不必为了“有译文”而改写。
缺少官方译名不等于没有术语价值：身份或定义已经成立时，根据发音、构词、语境和当前
命名体系提出固定写法，并明确标成建议，而不是因为“非官方”就删除。只有现有证据无法
负责地区分候选译法时才标成待确认，不编造确定结论。机制细节尚未全部解释，也不自动
否定已经由语料证明的专门身份；把已知定义和未知部分分别记录。

### 5. 合并变体并导出

只把已经证明确属同一身份的简称、词形、旧称或表记差异合并。近义词、翻译后的表达和
偶然包含相同子串的词不是源文变体。记录适用版本与范围，避免把一个 MOD 或支线的私有
名称误用于整个游戏。

工作记录至少保留：

| 字段 | 内容 |
|---|---|
| 原文表达 | 语料中的规范写法 |
| 固定写法 | 要求采用的目标语或原样拼写 |
| 身份或定义 | 它在游戏中具体代表什么 |
| 类别 | 名称、属性、资源、状态、机制等 |
| 证据 | 文件、定位信息和必要上下文 |
| 原文变体 | 已确认属于同一身份的其他写法 |
| 收录理由 | 译法分歧、一致性收益或权威形式约束 |
| 范围与状态 | 适用版本、内容范围，以及确认或待确认状态 |

保留候选阶段的拒绝理由，避免后续仅因高频或字段位置再次加入。交付给下游系统时只导出
已确认条目，并按该系统实际支持的语义取舍字段；中立工作记录本身不冒充可直接导入文件。

## 验收术语表

交付前逐项检查：

- 每个条目都能指出游戏内身份或明确定义；
- 每个条目都能说明统一写法的实际价值或权威形式约束；
- 普通名词、高频词、句子片段和无证据推测已经移除；
- 固定写法与证据来源一致，官方、社区和建议状态没有混写；
- 别名与变体没有合并不同身份，同形异义没有被错误全局化；
- 对全部原文变体做过回查，重要出现位置没有遗漏；
- 对短词、重叠词和子串命中检查过误用风险；
- 最终条目数量保持必要且精简，每项都经得起删除质询。

发现遗漏时补充候选与证据；发现条目无法满足收录判断时删除，而不是用更宽泛的说明保留。
