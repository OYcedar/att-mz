# RPG Maker 规则编写指南

本文说明 ATT 当前 RPG Maker 实现中的三类规则文件：MV 对话姓名投影、Extract Rules
和 Placeholder Rules。它们都使用严格 TOML，正则都采用 PCRE2 UTF/UCP，但解决的是三种
不同问题，不能互相替代。

RPG Maker 是当前游戏领域，ATT 目前只支持 MV 与 MZ。除 MV 对话姓名投影外，本文其余
能力同时适用于 MV 与 MZ。精确的资产、事务与失败语义分别以[提取现行规格](extraction.md)
和[翻译现行规格](translation.md)为准。

## 1. 先分清要表达的事实

| 文件 | 使用位置 | 要表达的事实 | 不负责 |
|---|---|---|---|
| MV 对话姓名投影 | `mv extract --builtin --dialogue-rules FILE` | 标准 MV 对话第一条 `401` 中哪一段是 Speaker | 寻找任意插件文本、保护翻译控制符 |
| Extract Rules | `mv|mz extract --rules FILE` | 哪个已知来源、确定路径或事件参数中的哪段文本应成为标准资产 | 猜测任意字符串是否可见、定义模型占位符 |
| Placeholder Rules | `mv|mz translate ... --placeholders FILE` | 已提取文本中的哪些协议片段不能让模型改写，或哪层外壳应冻结 | 新增提取目标、修正错误的文本分组 |

判断时先问清问题发生在哪一层：

- 玩家可见文本已经被 Builtin 提取，只是 MV 把姓名写进了第一行正文：使用 MV 对话姓名
  投影；
- 玩家可见文本根本没有成为标准资产，但能由当前 Rules 的来源与路径准确定位：使用
  Extract Rules；
- 文本已经正确提取，但其中含插件控制序列、标签或其他不可翻译协议：使用 Placeholder
  Rules；
- 真实关系需要动态键枚举、过滤、跨节点判断、多目标同步投影或自有事务：当前声明式
  规则无法完整表达，再参考[可信 Lua 现行规格](lua.md)。

复杂或数量多并不自动意味着需要 Lua。只要来源、语义边界和写回关系仍能由当前规则
完整表达，声明式规则通常更容易审查。

## 2. 从游戏事实推导规则

规则应从运行时消费关系反推，而不是从“看起来像自然语言”的字符串开始。通常需要
确认四件事：

1. 哪个窗口、事件解释器或已启用插件会读取这个值；
2. 权威值实际位于哪个数据文件、事件参数或插件参数；
3. 整个值都可翻译，还是只有其中一段是自然语言；
4. 写回时哪些字节可以变化，哪些协议外壳、分隔符和嵌套 JSON 边界必须保留。

插件源码很适合回答这些问题：从绘制文本、创建窗口或执行插件命令的位置反查参数名、
事件 code 和解析函数，再到 `data/*.json`、Map/CommonEvents/Troops 或 `js/plugins.js`
核对实际值。插件文件存在不代表它已启用，字段含自然语言也不代表它会显示给玩家。

一条规则最好只描述一个已经确认的稳定协议。可同时准备代表性命中值和形似但不应命中
的反例；锚点、分隔符和作用域应来自该协议，而不是为了提高命中数量而放宽。

## 3. 共同的书写约定

三类文件的根都必须显式声明相应数组。零字节文件、只有注释的文件、未知字段和重复
字段都不是合法的“什么也不做”。权威空文件分别写成：

```toml
# MV 对话姓名投影、Extract Rules、Placeholder Rules 都使用这个根名。
rule = []
```

`rule = []` 的具体效果取决于文件类型：它会清空 MV 姓名定义、停用并清理 Rules owner，
或清空自定义占位符；固定的 RPG Maker 控制符保护不会因此消失。

正则推荐写成 TOML 单引号字面字符串，让反斜杠原样到达 PCRE2：

```toml
pattern = '\A(?<text>正文)\z'
```

这里 TOML 不处理 `\A` 和 `\z`。若要匹配游戏文本中的一个字面反斜杠，PCRE2 本身仍需
写两个反斜杠，例如下式匹配 `\SE[Bell]` 这一类文本：

```toml
pattern = '\\SE\[[^]]+\]'
```

命名捕获是 ATT 的协议字段，不只是正则写法：

- MV 姓名投影必须有且只有一个 `speaker` 命名捕获；
- Extract Rules 的 `pattern` 必须有且只有一个 `text` 命名捕获；
- Placeholder Rules 可以没有命名捕获；若有，则必须有且只有一个 `text`。

未命名捕获可以用于分组。不要添加 `label`、`priority`、`required`、`translate`、版本号
或其他当前格式没有的字段。

## 4. MV 对话姓名投影

### 4.1 适用条件

MZ 的标准消息命令在 `101.parameters[4]` 有原生 Speaker，Builtin 会直接处理。MV 没有
这个字段；有些游戏把姓名标记或纯姓名写在标准消息块第一条
`401.parameters[0]` 中。姓名投影只为后一种情况建立 Speaker/Body 关系。

它只检查标准 `101 + 连续 401*` 对话块的第一条 `401`。不会扫描任意字符串，也不会作用
于选择项、滚动文本或插件自有消息系统。

### 4.2 文件格式与最小例子

每条规则只有 `pattern`：

```toml
[[rule]]
pattern = '(?i)\\n<(?<speaker>[^>]*?)(?::)?>'
```

这个假设例子表示第一行可能以字面 `\n<姓名:>` 标记开头或包含重复的同名标记。若某个
游戏把姓名作为独立的完整第一行，更窄的规则可以是：

```toml
[[rule]]
pattern = '\A(?<speaker>[^\r\n]+)\z'
```

第二个例子只有在运行时消费者已经证明“该位置的完整第一行就是姓名”时才成立；不能
把它当作通用 MV 规则，否则普通正文第一行也会被误判为 Speaker。

### 4.3 投影语义

一个第一行最多只能由一条规则拥有。同一条规则可以在该行产生多个不重叠匹配，但其中
所有非空 `speaker` 必须逐字相同。ATT 把：

- 完整匹配中 `speaker` 之外的部分冻结为 Literal；
- 非空 `speaker` 建立为一个 Speaker 单元；
- 从行首到最后一个完整匹配结束处作为姓名前缀；
- 最后一个完整匹配之后的后缀作为该行 Body，并与后续 `401` 合成完整正文单元。

因此正则的完整匹配边界和 `speaker` 捕获边界同样重要。若完整匹配越过了真实姓名外壳，
其中落入 `speaker` 的部分会成为 Speaker，其余部分会冻结为 Literal；无论哪一种都不会
再成为该行 Body，ATT 也不会猜测真实意图。纯姓名第一行不会制造空 Body；后续 `401`
仍属于同一对话正文。

每条非空规则都必须在当前冻结来源中至少捕获一次非空 Speaker。规则可以捕获空姓名
外壳，但空值不建立 Speaker，也不能满足这项要求。这个约束意味着文件只应包含当前
游戏真实存在的协议，不适合预先堆放“以后也许会用到”的模式。

### 4.4 生命周期与常见失效

`--dialogue-rules` 只属于 `mv extract`，并且必须同时选择 `--builtin`。提供文件时，文件
完整替换项目中的 MV 姓名定义；省略参数会复用项目已保存的定义，不表示清空。定义与
Builtin 资产快照在同一事务中提交，失败时旧定义和旧 Builtin 快照保持不变。
对话规则文件的固定读取上限是 1 MiB；更大的文件会在解析前被拒绝。

常见失效包括：

- 文件没有显式 `rule`，或使用了 `text` 等错误命名捕获；
- 某条规则在当前来源没有非空命中；
- 两条规则都命中同一个第一行，即使各自匹配的跨度不重叠；
- 同一条规则在一行捕获了两个不同的非空姓名；
- 完整匹配为零宽、捕获未参与，或匹配/捕获没有落在有效 UTF-8 字符边界；
- 用宽泛的“整行姓名”正则覆盖普通正文；
- Extract Rules 又选择了同一物理 `401` 字符串，与 Builtin 争用目标。

验证时不仅要看到 Speaker 出现，还要检查同组 Body 是否从正确位置开始、姓名控制外壳
是否逐字冻结、形似但畸形的标记是否仍作为普通正文，以及代表性的无姓名对话是否不受
影响。相同来源与定义下重复 Extract 应收敛为不变。

## 5. Extract Rules

### 5.1 适用边界

Extract Rules 适合“来源已知、路径确定、最终落到字符串”的额外载体。每条规则必须且
只能选择一种来源：

| 来源字段 | 实际扫描范围 | 额外要求 |
|---|---|---|
| `file` | `data/` 中一个安全的精确 `.json` 基名，或全部规范 Map 文件 | 必须有 `path` |
| `plugin` | `js/plugins.js` 中名称精确相同且 `status = true` 的插件参数对象 | 必须有 `path`，第一步选择参数名 |
| `code` + `parameter` | Map、CommonEvents、Troops 事件列表中指定非负 code 的参数下标 | 两字段必须同时存在；`path` 可选 |

事件 code 没有附带硬编码含义。应从该游戏当前插件或事件解释器确认 code 和参数结构，
而不是因为某个常见插件曾使用相同数值就直接套用。

### 5.2 完整字段

```toml
[[rule]]
file = "CustomData.json"  # 与 plugin、code 互斥
# plugin = "EnabledPlugin"
# code = 357
# parameter = 3           # 只可与 code 同用
path = '[].name'          # file/plugin 必填，code 来源可省略
decode_json = false       # 可选，默认 false
pattern = '<label>(?<text>.*?)</label>' # 可选
```

当前字段只有 `file`、`plugin`、`code`、`parameter`、`path`、`decode_json` 和 `pattern`。
`file` 不能写 `data/CustomData.json`、父目录或任意通配符；`Map*.json` 是唯一支持的文件
通配形式，`.json` 后缀大小写也必须精确。

### 5.3 路径语法

路径不是 JSONPath，只支持四种确定步骤：

```text
Field.SubField       对象字段；普通名只含 ASCII 字母、数字、下划线且不能以数字开头
[3]                  固定数组下标
[]                   展开数组中的全部非 null 元素
["exact.key"]        精确对象键，可表达点号、空格等普通字段语法不接受的字符
```

这些步骤可以组合：

```text
[].Name
A[3].B
[][0]["exact.key"].Name
```

不支持 `$`、递归下降、过滤器、对象键通配或对象键正则。字段不存在或固定下标越界时，
该分支不产生目标；需要对象却遇到其他类型、需要数组却遇到其他类型，或最终值不是
字符串时会失败。

当路径还需要继续深入而当前值是字符串时，ATT 会把该字符串作为 JSON 自动解码一层，
并把解码边界记入可逆写回 recipe。`decode_json = true` 的作用不同：它要求路径终点先是
字符串，再把这个最终字符串额外解码一次；解码后的最终值仍必须是字符串。例如插件
参数本身保存的是 JSON string 字面量时可以使用它。不要因为看到反斜杠就盲目开启；
普通自然语言字符串不是嵌套 JSON。

### 5.4 最小来源例子

从自定义数据数组提取完整字段：

```toml
[[rule]]
file = "CustomData.json"
path = '[].displayName'
```

从已启用插件的一个嵌套参数中提取标题；若参数值是序列化对象，路径继续深入时会自动
解码：

```toml
[[rule]]
plugin = "JournalDisplay"
path = 'entries[].title'
```

从事件命令参数中提取完整字符串：

```toml
[[rule]]
code = 356
parameter = 0
```

从同类命令的字符串中只提取协议前缀之后的可见正文：

```toml
[[rule]]
code = 356
parameter = 0
pattern = '\ADisplayNotice\s+(?<text>.+)\z'
```

这些名称与协议都是假设，用来展示当前格式；实际规则必须从目标游戏的消费者和数据
结构推导。

### 5.5 整串与局部 `pattern`

省略 `pattern` 时，最终非空白字符串整体形成一个翻译单元。存在 `pattern` 时，必须有
且只有一个 `text` 命名捕获；完整匹配中捕获之外的内容以及未匹配区域都冻结为 Literal。
同一最终字符串中，一条规则可以按来源顺序产生多个互不重叠的非空 `text` 单元。

完整匹配不能是零宽，`text` 必须参与且本身不能是零宽；范围必须处于完整匹配内并对齐
UTF-8 字符边界。空白捕获不建立单元。每条规则在当前来源的全部目标中合计至少产生一个
非空单元，否则整个 Rules 候选失败。

两条规则不能拥有同一个最终物理字符串，即使它们想捕获其中不同片段。需要从同一值
提取多个片段时，应由一条正则的多次匹配表达；规则顺序只用于诊断编号，不是优先级。

### 5.6 常见失效与验证

常见失效包括：

- 把 `file` 写成磁盘路径，或使用 `*.json`、`Map??.json` 等不支持的通配；
- 插件源码存在，但 `plugins.js` 中未启用、名称大小写不符或参数结构不同；
- 把路径写成 JSONPath，或假定 `[]` 能枚举对象键；
- 混淆自动的中途 JSON 解码与终点 `decode_json`；
- `pattern` 没有唯一 `text` 命名捕获，捕获可为空、重叠或从不命中；
- 用多条规则切同一个物理字符串，造成目标冲突；
- 宽泛选择 `note`、脚本或配置对象中的全部字符串，把路径、ID、代码和开发文本当作
  玩家可见文本；
- 规则能命中当前样本，却无法说明译文如何无损回到同一嵌套边界。

一次成功 Extract 只证明当前定义可解析、可匹配并可物化，不单独证明选中的内容都应
翻译。验证应同时覆盖：

- 正向样本确实由运行时消费者显示；
- 预期的同类载体没有漏收；
- 路径、资源身份、控制外壳等反向样本没有误收；
- 每个单元、逻辑组、物理目标和 recipe 的关系符合真实语义；
- 未翻译写回能够逐字保留原值，翻译写回只改变声明的 `text` 槽；
- 相同来源与规则重复 Extract 收敛，错误候选不覆盖旧 Rules 快照。

可以通过项目数据库、审计、候选树或隔离游戏副本取得这些证据；数据库能够证明 ATT
保存了什么，运行时消费者或实际界面才能证明玩家会看到什么。

## 6. Placeholder Rules

### 6.1 适用边界

Placeholder Rules 作用于已经提取的标准文本，在发送模型前把不可改写片段替换为 ATT
token，并在验收后恢复。它不能让缺失的文件字段或插件参数进入提取结果。

ATT 已内建保护当前标准 RPG Maker 控制符，包括带数字参数的 `\V[]`、`\N[]`、`\P[]`、
`\C[]`、`\I[]`、`\PX[]`、`\PY[]`、`\FS[]`，以及 `\G` 和受支持的单字符控制符。插件
新增的 `\SE[...]`、自定义标签或其他协议只有在真实语料中存在且当前内建规则未覆盖时，
才需要自定义规则。

### 6.2 文件格式、作用域与两种语义

每条规则只有两个字段：必填的 `pattern` 和可选的 `scopes`。省略 `scopes` 表示全局；
显式数组不能为空、不能重复，也不接受 `"all"`。当前合法作用域只有：

| scope | 标准文本类别 |
|---|---|
| `database_entry` | 数据库条目 |
| `system` | System 文本 |
| `map` | Map 级文本 |
| `event_dialogue` | 对话 |
| `event_choices` | 选择项 |
| `event_scrolling_text` | 滚动文本 |
| `event_command` | 事件命令规则提取的文本 |
| `plugin_parameter` | 插件参数规则提取的文本 |

没有命名捕获时，完整匹配都受保护，不送模型改写：

```toml
[[rule]]
scopes = ["event_dialogue", "event_choices"]
pattern = '\\SE\[[^]]+\]'
```

有唯一 `text` 命名捕获时，`text` 保持可翻译，完整匹配中它前后的外壳受保护：

```toml
[[rule]]
scopes = ["plugin_parameter"]
pattern = '<name>(?<text>.*?)</name>'
```

第二种写法中 `<name>` 与 `</name>` 会恢复为原值，只有中间内容可以变化。`text` 的含义
不是“要保护的内容”，恰好相反，它标出协议外壳内部仍应翻译的自然语言。

### 6.3 匹配与冲突语义

完整匹配必须非零宽并位于有效 UTF-8 字符边界；`text` 必须参与、位于完整匹配内并对齐
字符边界。自定义规则零命中是合法的，这与 MV 姓名投影和 Extract Rules 不同。零命中
也不证明规则正确，仍需用实际作用域中的代表值验证。

任何涉及自定义规则的跨度重叠都会使该文本单元规划失败，包括自定义规则互相重叠，
以及自定义规则覆盖了内建控制符。没有“先写的优先”或“更长的优先”。因此不要再用
一个宽规则包住已经由 Builtin 保护的 `\C[2]` 等控制符。

提供 `--placeholders FILE` 时，文件完整替换项目当前自定义占位符资源；省略参数复用
数据库中的当前资源。`rule = []` 只清除自定义规则。翻译 state 记录的是该文本单元实际
应用到的占位符绑定，而不是整份规则文件：无关规则变化不会使该单元失效，产生完全相同
绑定的规则调整也不会改变其 state；实际绑定变化后，旧译文才不能继续视为当前结果。

### 6.4 常见失效与验证

常见失效包括：

- 使用未知 scope、空 `scopes`、重复 scope 或虚构的 `"all"`；
- 把 TOML 转义和 PCRE2 转义混为一层，实际没有匹配字面反斜杠；
- 误以为 `text` 是受保护片段，结果把协议外壳送进模型；
- 全局规则过宽，在不相关类别中误保护普通文字；
- 自定义规则彼此重叠，或与内建 RPG Maker 控制符重叠；
- 整段保护了本应翻译的自然语言，导致该单元没有可翻译内容；
- 希望 Placeholder Rules 补回 Extract 漏掉的载体。

验证时选择规则声明作用域内的真实正向样本，以及其他作用域和形似自然文本的反向样本。
确认送入翻译的内容仍含应该翻译的语义，模型返回后协议字节逐字恢复，token 没有丢失、
复制或跨严格对齐槽移动，最终候选只改变允许变化的自然语言。若失败来自提取分组或物理
目标错误，应修正提取事实，而不是继续扩大占位符正则。

## 7. Builtin、Rules 与 Lua 的停止线

Builtin 拥有已经确认的 RPG Maker 标准字段、消息、选择、滚动文本和控制符语义。规则
适合补充游戏或插件公开且稳定的局部协议，不应重复拥有 Builtin 已经覆盖的物理目标。

Extract Rules 的表达上限是“从支持的单一来源沿确定路径到一个最终字符串，再整体翻译
或捕获一个 `text` ABI 的多次匹配”。Placeholder Rules 的表达上限是“在一个已提取
字符串和一个已知语义作用域内，保护完整匹配或 `text` 外壳”。MV 姓名投影则只解释
标准对话第一行。

如果现实材料要求跨字段决定是否翻译、把一个译文同步写到多个位置、按动态对象键或
条件筛选、维持插件自有身份与事务，继续增加声明式正则会丢失真实关系。此时 Lua 是可选
扩展面，而不是必须经过的阶段。反过来，若当前格式已经能完整表达来源、语义单元、冻结
外壳和可逆写回，就没有必要为了形式统一改用 Lua。

最终判断不以规则数量、命中数量或命令退出码为准，而以四类证据共同成立为准：玩家
可见性、提取覆盖与排除、翻译协议保持、写回可逆性。
