# RPG Maker 系统提示词编写指南

本文面向编写或修改 RPG Maker Standard Translate system Prompt 的作者。它解释 ATT
实际发送给模型的输入，以及模型响应必须满足的机器协议。本文首先关心的不是译文是否
优美，而是响应能否被 ATT 解析、关联到正确单元并通过结构验收。

本文描述当前已经实现的协议。当前 Prompt 资源路径、任务消息和响应解析器发生变化时，
必须同步更新本文；不能只修改 Prompt 文案并假定解析器会自行适应。

## 1. 先区分四种问题

| 问题层级 | 典型问题 | ATT 结果 |
|---|---|---|
| Prompt 资源 | 文件缺失、不是 UTF-8、内容全为空白 | 请求模型前明确失败 |
| 响应信封或 JSON | JSON 前后有解释文字、顶层不是对象、JSON 语法错误 | 当前 TaskBlock 整体不可用，所有预期 ID 都未完成 |
| 单个 ID 的 wire 或候选结构 | ID 缺失或重复、值不是字符串数组、行数或空槽错误、ATT token 错误 | 只拒绝受影响的 ID；其他合法 ID 仍可验收 |
| 翻译质量 | 措辞生硬、语气判断不佳、术语选择不理想 | 可能仍能通过机器验收，但译文质量较差 |

因此，“必须输出 JSON”“每个 ID 恰好一次”“按标注形状返回”和“保留 ATT token”不是
改善翻译质量的建议，而是协议要求。Prompt 没有明确约束这些内容时，模型可能生成看似
合理、但 ATT 无法消费的响应。

这里的“整体不可用”或“单个 ID 被拒绝”是结构化翻译结果，不一定表现为进程崩溃或非零
退出码。调用方必须继续区分任务的 `Complete`、`Partial` 和 `Unavailable`。

## 2. 模型实际收到什么

每个 Standard TaskBlock 只发送两条消息：

1. `system`：当前外部 Prompt 文件的完整正文；
2. `user`：ATT Planner 自动生成的 Markdown 任务载荷。

当前 Prompt 从以下精确路径读取：

```text
<prompts.root>/rpg_maker/<source>--<target>.md
```

文件必须是非空白 UTF-8 文本。当前加载器不会替换 `{{source_language}}`、
`{{target_language}}` 或其他模板变量；写入文件的内容会原样成为 system message。当前也
没有默认文件、父语言、大小写变体或目录首项回退。

这段路径只是在记录当前加载器事实，不表示后续外置预设仍应按源语言和目标语言做排列
组合。后续 Prompt i18n 的目的，是让提示词作者用自己的语言阅读和微调同一份语义契约；
它与游戏的源语言、目标语言是两件事。在通用母版和变量替换真正实现前，作者仍不能把
尚未支持的模板变量写进生产 Prompt。

user message 不是 JSON，也不是 ATT 的内部领域对象。它只携带模型完成本次翻译所需的
术语、语境、待翻译内容、临时 ID 和输出形状。语言对、文件路径、owner、内部 kind、
传播目标和去重原因不会重复写入 user message，因此当前 system Prompt 自己必须建立
明确的翻译方向。

## 3. 如何阅读 user message

当前 Planner 生成的标题、字段标签和形状说明使用中文。翻译内容本身的语言由项目与
system Prompt 建立，不能根据这些中文协议标签推断。

一个任务通常形如：

```markdown
术语：

- 星港 → 星港

## 对话

说话人：米蕾雅

正文 [1]（自由断行）：

> 第一行⟦ATT_ICON_WHOLE_0000⟧
> 第二行

## 选项

选项 [2]（3 项，逐项对应）：

> 返回
>
> 前进
```

### 3.1 只有带 `[ID]` 的内容需要输出

`正文 [1]` 和 `选项 [2]` 是活动翻译条目。模型必须为 ID `1` 和 `2` 返回译文。

没有 `[ID]` 的 `说话人：米蕾雅` 只是语境，不得为它增加 JSON key。无 ID 语境可能是
源文，也可能是 ATT 已有或复用的目标语言译文，所以 Prompt 不应声称 user message 中的
所有自然语言都是源语言。

ID 只在当前 TaskBlock 中有效，从 `1` 连续编号；下一个 TaskBlock 会重新从 `1` 开始。
它不是数据库 ID、资产 ID 或跨请求稳定身份。输出时只按本次 user message 中实际出现的
ID 建立 key。

### 3.2 术语和分组不产生输出

`术语：` 只在当前活动内容实际命中术语时出现，格式为 `原词 → 译法`。同一条术语即使
命中多次也只列一次，并保持术语资源顺序。ATT 会对 Markdown 标点添加显示用反斜杠；
这些反斜杠不是术语正文。

`## 对话`、`## 选项` 等标题用于表达相关语境，也不产生 JSON key。采用术语和理解分组
通常影响翻译质量；为术语、标题或无 ID 语境擅自创建输出 key，则会产生未知 ID 诊断。

字段标签不是封闭枚举。除说话人、正文、选项、滚动文本、名称、昵称、简介、说明等常见
标签外，ATT 也可能直接显示原字段名。Prompt 应以“是否带 `[ID]`”和括号中的形状标记
判断输出责任，不能只识别一份写死的标签列表。

### 3.3 Markdown 外壳不是原文

多行、逐项对应和自由断行内容使用 `> ` 作为 Markdown blockquote 前缀；前缀不属于
原文。空槽显示为只含 `> ` 的一行。单行内容直接出现在冒号后，不使用 blockquote。

模型应理解这些结构，但输出不能复制标题、标签、`[ID]`、形状说明或 `> ` 前缀。它只
返回 ID 到译文字符串数组的映射。

## 4. 四种输出形状

每个带 ID 的条目都会直接标明形状。输出数组必须以标记为准：

| 输入标记 | JSON 数组要求 | 额外硬限制 |
|---|---|---|
| `单行` | 恰好一个字符串 | 源槽非空时，译文不能是空串或纯空白 |
| `N 行，逐行对应` | 恰好 `N` 个字符串 | 与源行逐槽对应，并保持空槽位置 |
| `N 项，逐项对应` | 恰好 `N` 个字符串 | 与源项逐槽对应，并保持空槽位置 |
| `自由断行` | 数量可以改变 | 整个数组至少有一个非空白字符串 |

所有数组元素都必须是 JSON 字符串，并且字符串解码后不能包含 CR、LF 或 NUL。需要输出
多行时，必须拆成多个数组元素；把换行写进一个字符串，即使 JSON 语法有效，也会使该 ID
被拒绝。

严格对齐的空槽还有两个容易写错的规则：

- 源槽为空白时，对应输出必须是精确空字符串 `""`，不能是 `" "`；
- 源槽非空时，对应输出不能是空字符串或纯空白。

对于上一节的示例，ID `2` 必须返回三个字符串，第二项必须是 `""`。自由断行不要求
保持原行数；要求它逐行对应反而会把 Prompt 写得比真实协议更严格。

非空白仍不代表一定可用。去除 ATT token 等受保护片段后，候选还必须包含非空白的自然
语言文本；只返回 token 或其他不透明片段也会被拒绝。

## 5. 最终 JSON wire

ATT 解析的是 Chat Completions 响应中的 assistant `message.content`，不是供应商 HTTP
响应的外层 JSON。system Prompt 应要求模型直接输出一个 JSON 对象，形状固定为：

```json
{
  "1": ["第一段译文", "第二段译文"],
  "2": ["第一项译文", "", "第三项译文"]
}
```

硬性要求如下：

1. 顶层必须是 JSON object，不能是数组，也不能再包一层 `translations`；
2. key 必须是本次输入中出现的十进制正整数 ID 字符串；
3. ID 不能带正号、空格或前导零，例如 `"+1"`、`" 1"`、`"01"` 都非法；
4. 每个预期 ID 必须恰好出现一次，不能缺失、重复或增加未知 ID；
5. 每个 value 必须是字符串数组，不能是字符串、数字、对象或 `null`；
6. JSON 必须符合严格语法，不能使用注释、尾逗号、单引号或多个连续 JSON 值；
7. JSON 前后不能附加解释、总结、道歉、标题或其他自然语言；
8. 最终 JSON 后不能再输出任何内容。

解析器会容忍响应首尾空白、开头的单个 BOM，以及唯一一层独占首尾行的无标记、`json`
或 `JSON` Markdown 围栏。但这是接收端的有限容错，不是 Prompt 应依赖的输出格式。
Prompt 应始终要求裸 JSON，不能主动要求代码围栏。

下面这些响应会使整个 TaskBlock 无法解析：

```text
翻译结果如下：{"1":["译文"]}
```

```json
[{"1":["译文"]}]
```

```json
{"1":["译文"],}
```

```text
{"1":["译文"]}
完成。
```

一旦响应信封或 JSON 根无法解析，ATT 不会从自然语言中猜测、截取或修复某个 JSON
片段，也不会把协议失败伪装成网络错误进行重试。

## 6. ATT token 是机器保护标记

user message 中可能出现形如以下内容的 token：

```text
⟦ATT_ICON_WHOLE_0000⟧
⟦ATT_NAME_BEGIN_0001⟧
⟦ATT_NAME_END_0002⟧
```

它们代表 ATT 暂时保护、验收后再恢复的原始片段。Prompt 必须要求模型：

- 逐字保留每个 token 的大小写、字符、编号和完整边界；
- 不得删除、复制、改写、拆开或创造 token；
- 不得把 token 翻译成自然语言；
- 不得输出输入中不存在的未知或残缺 `⟦ATT_...` 内容。

严格对齐条目按对应槽分别校验 token，因此 token 不能跨行或跨项移动。自由断行条目按
整个 ID 校验 token 多重集，token 可以随译文重排移动到该 ID 的另一输出行。当前验收
不要求允许范围内的 token 保持原相对顺序，所以 Prompt 不应把“所有 token 必须留在原
字符位置”描述成解析器事实。

解析器能在少数无歧义场景中把模型输出的原始控制片段正规化回 token，但这只是接收端
恢复能力，不是 Prompt 契约。Prompt 作者必须要求模型保留所见 token，不能依赖恢复逻辑。

## 7. JSON 可解析仍不等于候选可用

下面的问题不会破坏整个 JSON 根，但会让对应 ID 未完成：

| 输出问题 | 对应 ID 的结果 |
|---|---|
| ID 缺失 | `Missing` |
| 同一 ID 出现多次 | `Duplicate` |
| value 不是数组，或数组中含非字符串 | 形状无效 |
| 单行或严格对齐数组长度错误 | 行数不匹配 |
| 字符串含 CR、LF 或 NUL | 结构行无效 |
| 空槽位置错误，或非空槽只返回空白 | 空白形状不匹配 |
| ATT token 丢失、重复、损坏、未知或跨严格槽移动 | Placeholder/ATT token 验收失败 |
| 只含 ATT token、控制片段或空白，没有自然语言文本 | 自然语言文本缺失 |
| 译文字符串内部含 BOM | BOM 验收失败 |
| 同时混用 ATT token 与其原始控制片段，无法唯一恢复 | Placeholder 正规化歧义 |
| 译文仍有源语言残留 | 源语残留验收失败 |

非法或未知 ID 会形成协议诊断并被忽略；它们不能代替缺失的正确 ID。只要同一响应中的
其他 ID 完整合法，那些 ID 仍然可以被接受，因此任务可能得到 `Partial`。如果没有任何
预期 ID 通过，则任务为 `Unavailable`；全部通过才是 `Complete`。

响应最外层开头的单个 BOM 可以被信封解析器剥离；JSON 字符串内容中的 BOM 不属于这项
容错，会拒绝对应候选。空对象 `{}` 虽然是合法 JSON object，但缺少全部预期 ID，最终仍
会得到 `Unavailable`。

以下例子中，JSON 本身语法正确，但 ID `1` 会被拒绝：

```json
{"1":"译文"}
```

```json
{"1":["第一行\n第二行"]}
```

如果输入标记为 `选项 [1]（2 项，逐项对应）`，以下响应也会拒绝 ID `1`：

```json
{"1":["只返回了一项"]}
```

这些都不是“译得不够好”，而是模型输出没有满足 ATT 的可消费契约。

## 8. 哪些内容主要影响翻译质量

在 wire、形状和候选验收都成立后，下列要求主要用于提高翻译质量：

- 正确理解分组内各段之间的语境；
- 利用无 ID 的说话人或名称判断指代；
- 采用给定术语；
- 判断人物关系、语气、情绪和敬语程度；
- 使用符合目标语言习惯的自然表达。

术语采用不由 JSON parser 机械判断；忽略术语通常是质量问题。源语言残留和 ATT token
错误是例外，它们有明确的候选验收，可能直接拒绝对应 ID。

Prompt 作者应同时写好翻译要求和机器协议，但必须清楚二者的后果不同。不能用大量翻译
风格说明淹没最终 JSON、ID、行形状和 token 规则。

## 9. 当前不支持思考输出

当前响应解析器只接受 JSON 信封。下面这种“思考输出要求 + JSON”结构当前会因为 JSON
前存在额外内容而使整个 TaskBlock 不可用：

```text
<why>
思考过程……
</why>
{"1":["译文"]}
```

因此，在思考输出开关及对应信封解析正式实现前，不能在生产 Prompt 中要求模型输出
`<why>...</why>`。仅在 system Prompt 后追加相关指令，而不先修改响应解析器，不会得到
“多一段可忽略文本”，而会直接破坏现行 JSON 协议。

未来若实现该能力，必须先明确并测试 `<why>` 信封的提取边界，再把提取后的剩余内容交给
同一 JSON 与逐 ID 验收流程；届时应直接更新本节，不能让文档同时声称两套现行协议。

## 10. Prompt 作者的最低检查清单

提交 Prompt 前，至少确认它明确要求模型：

- 按 system message 已建立的方向翻译；
- 只翻译带 `[ID]` 的内容，把无 ID 内容、术语和标题仅作语境；
- 为输入中的每个 ID 恰好返回一次结果，不增加其他 key；
- 输出裸 JSON object，key 为 ID 字符串，value 为字符串数组；
- 按 `单行`、`逐行对应`、`逐项对应` 或 `自由断行` 分别处理数组；
- 严格保留逐行/逐项空槽；
- 不在单个字符串中写 CR、LF 或 NUL；
- 按对应形状精确保留所有 ATT token；
- 不输出解释文字、Markdown 围栏、思考过程或 JSON 之后的内容。

检查 Prompt 时应至少使用以下代表性输入：无术语、存在术语、无 ID 语境、单行、自由
断行、带空槽的严格对齐、含多个 ATT token。只用一个单行字符串测试，无法证明 Prompt
理解了完整协议。

任务输入的规划事实和结果状态见[翻译现行规格](translation.md#5-任务规划与模型消息)，
ATT token 的来源与恢复规则见[规则编写指南](rules.md#6-placeholder-rules)，术语资源见
[术语表制作指南](terminology.md)，HTTP 外层响应与 assistant content 的关系见
[Chat Completions 运行根](../runtime/chat-completions.md)。出于隐私与密钥边界，ATT 不把
完整 Prompt、messages、原文、译文或模型正文写入普通项目日志。
