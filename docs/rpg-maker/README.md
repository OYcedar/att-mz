# RPG Maker 调查与决策指南

本文面向能够读取游戏材料、插件源码、ATT 配置与项目状态，并能自行执行和验证操作的
使用者。它提供面对未知游戏时通常较短的判断路线，不规定固定步骤、工具顺序或必须
生成的中间工件。精确命令、字段、数据形状和失败语义由链接的现行规格定义。

## 范围与领域关系

RPG Maker 是本文讨论的产品领域，ATT 当前只实现其中的 **MV** 与 **MZ**。`mv`、`mz`
分别选择该领域内的命令入口、游戏目录布局和工作区身份；不要据此推断其他 RPG Maker
版本已经实现，也不要把 MV、MZ 与 RPG Maker 当成三个并列领域。

Init、Extract、Translate 与 WriteBack 存在真实状态依赖，但不是要求每次从头执行的
机械流水线。先确认当前用户结果和已有项目状态，再进入真正需要的部分。现实材料推翻
假设时，返回事实来源修正判断即可。

## 从消费行为反向寻找事实

调查游戏时，最可靠的起点不是递归搜索所有自然语言字符串，而是玩家实际看到文本的
运行时消费者：

```text
界面 / 事件解释器 / 启用插件
            ↓ 读取
字段 / 事件参数 / 插件参数 / Note / 嵌套 JSON
            ↓ 形成
玩家可见语义及其分组
            ↓ 对应
一个或多个精确写回位置
```

静态搜索适合发现候选和补漏，但不能单独证明字符串应被翻译。对每类候选同时寻找：

- 正证据：值确实进入玩家可见窗口、消息、菜单或其他运行时消费者；
- 排除证据：插件未启用、分支不可达、内容只供开发者阅读，或字符串其实是代码、资源
  身份、协议外壳；
- 漏收证据：实际界面出现文本，但已知提取资产中没有对应语义单元；
- 误收证据：项目数据库存在单元，但游戏不会把它作为自然语言展示。

“像自然语言”不等于“应翻译”。同样，某个路径能命中字符串，也不等于已经证明它是
完整、可逆的翻译单元。

## 初始化：取得项目真正需要的事实

首次 Init 需要项目名、游戏根，以及五项持久项目事实：源语言、目标语言和三类布局
宽度。已有项目可以省略单项以复用数据库当前事实；这不表示 ATT 会重新推断它。

| 输入 | 性质 | 建议寻找的位置 | 验证重点 |
|---|---|---|---|
| 项目名 | 任务选择 | 用户目标、项目命名约定 | 是否准确标识本工作区；同名 MV/MZ 可共存 |
| 游戏根 | 调查事实 | 核心脚本与 `data/js` 或 `www/data/js` 布局 | 传入的是游戏根，不是猜测修正后的子目录 |
| 源语言 | 调查事实 | 玩家可见正文、选项、数据库说明、启用插件文本 | 排除插件注释、开发文本和少量混合语言干扰 |
| 目标语言 | 使用者选择 | 当前任务 | 不从界面语言、文档语言或游戏内容猜测 |
| 对话宽度 | 调查事实 | 消息窗口、启用插件覆盖、字体、padding、头像缩进 | 代表性最窄场景能否容纳所选全角字符数 |
| 滚动文本宽度 | 调查事实 | 滚动文本窗口及其插件覆盖 | 是否与普通消息窗拥有不同可见区域 |
| 帮助说明宽度 | 调查事实 | Help 窗口、物品/技能说明布局 | 实际说明窗口和字体设置是否一致 |

这些事实分别通过 `--source-language`、`--target-language`、
`--dialogue-max-fullwidth-chars`、`--scrolling-text-max-fullwidth-chars` 与
`--help-description-max-fullwidth-chars` 提交；项目名和游戏根使用 `--name` 与 `--path`。
精确命令形状及首次/已有项目的必填差异见[初始化现行规格](init.md#1-命令与游戏目录)。

### 确认版本与游戏根

- MZ 游戏根直接包含普通 `data/`、`js/` 与 `js/rmmz_core.js`；
- MV 游戏根直接包含普通 `www/`，其下包含 `data/`、`js/` 与 `js/rpg_core.js`；
- 不要把 MV 的 `www/` 当作 CLI 要求的游戏根，也不要让脚本自动探测另一版本后静默
  改写用户输入。

### 判断源语言

优先抽查已经证实会显示的长正文、选项和说明，并观察各类载体是否一致。文件名、系统
locale、插件作者注释、脚本标识符或少量角色名只能提供线索。若游戏具有语言切换，应
继续找出当前发行内容实际选择哪一套语言，而不是只统计字符数量。

### 推导三类宽度

三类宽度分别调查。先定位真正消费文本的窗口类，再检查当前启用插件是否覆盖窗口尺寸、
padding、字体、头像区域或换行逻辑。宽度随分辨率、场景或插件命令动态变化时，记录
适用条件并选择能够解释的保守事实；不要把一个看似精确的数字伪装成所有界面的真值。

通常可以从这些位置建立第一批证据：MZ 的 `js/rmmz_windows.js`，MV 的
`www/js/rpg_windows.js`，以及 `plugins.js` 中已启用插件对应的源码。沿
`Window_Message`、滚动文本窗口、`Window_Help`、窗口矩形、padding、字体、头像缩进、
`drawTextEx` 与换行覆盖继续追踪；若插件替换或别名包装这些方法，以最终启用的调用链为
准。配置值表示 ATT 排版使用的“每行最大全角字符数”，不是直接抄一个像素宽度。可以用
实际字体和代表性控制符把候选值换算并放入最窄的真实窗口检查，再根据结果修正。

Init 成立的证据不仅是命令成功，还包括冻结来源、metadata 与预期一致，以及相同事实下
重复 Init 能够收敛。精确契约见[初始化现行规格](init.md)，配置路径与工作区见
[生产配置规格](../runtime/configuration.md)。

## 提取：先建立文本载体地图

通常值得检查的现实材料包括：

- RPG Maker 标准数据库对象及真正被窗口消费的字段；
- Map、CommonEvents、Troops 中实际执行的消息、选择、滚动文本及其他事件命令；
- `js/plugins.js` 中状态为启用的插件，而不是插件目录中存在的全部源码；
- 启用插件通过参数、插件命令、事件参数、Note/meta 或自有 JSON 读取的内容；
- 运行时条件、分支与 locale 选择最终让哪一个值进入界面。

调查时同时记录玩家可见语义、逻辑分组、物理载体和写回位置。对话 Speaker 与 Body、
一个完整选项组、一个完整滚动文本块可能各自跨越多个物理字段；不要因为物理位置分散
就把一个语义原子拆开。

## 选择 Builtin、Rules 或 Lua

这不是必须逐级执行的升级流程，而是对现实语义表达能力的判断。

### Builtin 通常已经足够

- RPG Maker 标准数据库文本；
- 标准消息、选择项和滚动文本；
- MZ 原生 Speaker；
- MV 第一条正文中的说话人能够由姓名投影完整、可逆地表达。

先对照 [Builtin 与标准资产模型](extraction.md#3-builtin-与对话差异)，不要因为文件属于
标准目录就假定其中所有字符串都受支持。

### Rules 通常已经足够

- 来源能明确表示为一个文件、启用插件参数或事件 `code + parameter`；
- 受支持的确定路径可以到达最终字符串；
- 必要时只需从最终字符串捕获一个 `text` 跨度；
- 嵌套 JSON 能逐层解码并按相反边界写回；
- 每个物理目标归属清楚，原文和译文都能用同一 recipe 可逆重建。

精确能力见 [Extract Rules TOML](extraction.md#5-extract-rules-toml)。Rules 的命中数量不
是覆盖证明；还要抽查真实消费者、误收、漏收和写回边界。

当前三类规则文件的选择、字段和验证方法见[规则编写指南](rules.md)。

### 出现这些事实时再考虑 Lua

- 需要递归、过滤、动态对象键或跨文档关系；
- 一个语义事实依赖多个物理节点，或译文必须同步投影到多个位置；
- 是否翻译取决于跨节点状态或游戏私有运行协议；
- 需要 Rules 契约之外的自有身份、事务、持久状态或恢复语义；
- 静态路径虽然命中字符串，却不能表达完整分组和可逆写回。

复杂并不自动意味着需要 Lua。如果 Builtin 或 Rules 能完整表达真实语义，继续使用它们
更直接。Init 没有 Lua；Extract、Translate 和 WriteBack 的 Lua 也是各阶段独立选择，
某一阶段使用 Lua 不会自动要求后续阶段使用。完整技术边界见
[可信 Lua 现行规格](lua.md)。

## 证明提取覆盖，而不只证明命令成功

可按风险选择抽查范围，但结论至少应能解释：

- 代表性已提取单元为何是玩家可见文本，分组、上下文和目标为何正确；
- 已知高风险载体为何被覆盖或排除；
- Speaker/Body、`102/402`、滚动文本和嵌套 JSON 是否保持完整语义；
- 不同 owner 或规则是否竞争同一物理目标；
- 重复 Extract 是否收敛，失败 owner 是否保持旧快照。

使用者可以直接查询 `project.db` 的 owner、group、unit、target 和 recipe。数据库能够证明
持久化关系，不能单独证明运行时可见性；玩家是否真的看到文本仍由消费者或实际界面
建立。数据与完成语义见[文本提取现行规格](extraction.md)。

## 直接检查或修改项目数据库

`project.db` 是使用者可直接控制的项目状态，不要求所有调查和修复都绕回 CLI。直接查询
适合核对 metadata、owner 快照、逻辑组、语义单元、物理目标、译文和 state；直接 DDL
或 DML 也可以用于明确的修复或自有扩展。ATT 不为通用 SQLite 工具自动取得项目租约，
因此写入前应先确认没有同项目命令并发运行，并根据副作用风险保留可恢复副本或事务边界。

直接修改受管表后，应重新证明相应不变量，而不是把“SQL 已提交”当作业务完成。例如，
译文与 translation state 必须成对存在或成对为空；owner 的来源/资产指纹、group、unit、
target 和 recipe 必须仍描述同一快照；来源是否可见、译文是否合格仍需由对应消费者和
验收语义证明。发现不一致时，先判断冻结来源、提取资产、译文或数据库哪一个是权威事实，
再选择重提取、重翻译、精确修复或恢复副本，不盲目重算校验值掩盖漂移。

项目表关系见[初始化现行规格](init.md#3-当前项目数据库)，SQLite 连接与事务的运行边界见
[SQLite 运行时](../runtime/sqlite.md)。

## 不使用 Lua 的翻译

Builtin 与 Rules 建立的标准资产直接交给 Standard Translate，无需为了调用模型增加
Lua。开始前确认：

- 项目 metadata 中的权威语言对；
- 配置精确命中的 Profile 及其引用的 Client；
- 对应源语言模块；
- `<prompts.root>/rpg_maker/<source>--<target>.md` 的精确 Prompt；
- 真实语料是否需要术语或自定义占位符；
- 模型服务的并发、超时、限流、重试与 parameters 约束。

配置没有默认 Profile、默认 Prompt、父语言或大小写回退。使用者应根据当前环境修改实际
配置，而不是复制一份万能模板。Prompt 必须与当前 ID 到字符串数组 wire、上下文规则、
行形状和 ATT token 保护一致。

术语候选的取得、上下文消歧和 TOML 写法见[术语表制作指南](terminology.md)；从命令反推
配置分区及验证配置选择的方法见[配置编写指南](../runtime/README.md)。

验证时区分进程技术成功、任务 `Complete`、`Partial`、`Unavailable`，以及每个单元的
译文/state 是否成对成立。退出码为零不等于全部单元已经翻译。精确配置见
[生产配置规格](../runtime/configuration.md)，模型协议与提交语义见
[翻译现行规格](translation.md)。

## 不使用 Lua 的写回

WriteBack 每次从冻结 `source` 建立新候选，不在旧 `write_back` 上增量修改。输出是项目
工作区中的 RPG Maker 内容树，不是原游戏，也不是完整可运行游戏包。未翻译单元保留
原文是正常结果；WriteBack 消费 Extract 已物化的 recipe，不重读 Rules TOML，也不重新
运行正则。

根据用户需要和风险，检查：

- 变化是否只发生在已确认目标；
- 未知 JSON 成员、未知命令字段和不透明文件是否保持；
- 控制符、占位符、Literal 外壳和嵌套 JSON 边界是否仍然合法；
- Speaker/Body 关系以及 `102` 选项与同层 `402` 标签是否同步；
- 相同来源和项目状态下重复 WriteBack 是否得到相同内容；
- 部署到隔离游戏副本后，代表性窗口、插件协议和三类宽度是否成立。

运行时验证暴露漏收、误收或错误语义边界时，应回到消费者调查和 Extract 修正事实，
而不是直接修补候选输出。候选、布局和发布的精确契约见[写回现行规格](write-back.md)。

## 判断路线正在走偏

- 实际界面有文本而项目中没有对应单元：重新调查消费者和载体；
- 项目中出现大量未启用、不可达或开发者文本：收窄提取范围；
- Rules 能命中但无法证明可逆写回：不要把命中误称为覆盖；
- Translate 成功退出但仍有 unresolved：阅读任务诊断，不修改数据库伪造完成；
- WriteBack 拒绝 source、recipe 或资产指纹：判断来源是否漂移，必要时重新 Extract；
- 现实协议确实超出 Builtin/Rules：只在需要的阶段进入 Lua 技术文档。
