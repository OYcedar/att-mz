# RPG Maker 调查与机制选择指南

本文解释如何从真实游戏材料确认 RPG Maker MV/MZ 的项目事实、文本载体与机制边界，
以及如何证明提取和写回关系成立。精确命令、字段、数据形状、保存运行方案和失败语义
由链接的现行规格定义。

## 范围与领域关系

RPG Maker 是本文讨论的产品领域，ATT 当前只实现其中的 **MV** 与 **MZ**。`mv`、`mz`
分别选择该领域内的命令入口、游戏目录布局和工作区身份；不要据此推断其他 RPG Maker
版本已经实现，也不要把 MV、MZ 与 RPG Maker 当成三个并列领域。

调查结论必须来自当前发行内容的实际消费者、权威说明或可复现观察。文件名、目录外观、
字符统计和未启用插件只能提供候选线索，不能单独建立产品事实。

## 从消费行为反向寻找事实

调查游戏时，从玩家实际看到文本的运行时消费者反向追踪来源：

<!-- att-example: illustrative -->
```text
界面 / 事件解释器 / 启用插件
            ↓ 读取
字段 / 事件参数 / 插件参数 / Note / 嵌套 JSON
            ↓ 形成
玩家可见语义及其分组
            ↓ 对应
一个或多个精确写回位置
```

静态搜索适合发现候选和补漏，但不能单独证明字符串应被翻译。对每类候选同时寻找：

- 正证据：值确实进入玩家可见窗口、消息、菜单或其他运行时消费者；
- 排除证据：插件未启用、分支不可达、内容只供开发者阅读，或字符串属于代码、资源
  身份、协议外壳；
- 漏收证据：实际界面出现文本，但已知提取资产中没有对应语义单元；
- 误收证据：项目中存在单元，但游戏不会把它作为自然语言展示。

“像自然语言”不等于“应翻译”。某条路径能够命中字符串，也不等于已经证明它构成
完整、可逆的翻译单元。

## 确认版本与游戏根

- MZ 游戏根直接包含普通 `data/`、`js/` 与 `js/rmmz_core.js`。
- MV 游戏根直接包含普通 `www/`，其下包含 `data/`、`js/` 与 `js/rpg_core.js`。
- MV 的 `www/` 不是 ATT 要求的游戏根。不得自动探测另一版本后静默改写使用者给出的
  版本或路径。

同一个目录中出现相似文件不足以推翻这些结构证据。打包器、启动器或多份内容树造成
歧义时，继续追踪实际可执行文件最终加载的脚本与数据目录。

项目名用于标识 ATT 工作区；源语言、目标语言和三类布局宽度是项目需要持久保存的独立
事实。目标语言来自当前汉化目标，不能由界面语言或文件内容替使用者决定。项目身份、
冻结来源和 metadata 的精确契约见[初始化现行规格](init.md)；运行方案及其复用条件只由
[运行时与 CLI 现行规格](../runtime/cli.md)定义。

## 判断源语言

优先抽查已经证实会显示的长正文、选项和说明，并观察各类载体是否一致。文件名、系统
locale、插件作者注释、脚本标识符或少量角色名只能提供线索。游戏具有语言切换时，继续
确认当前发行内容实际选择哪一套语言，不能只统计字符数量。

混合语言材料应按实际消费者判断：需要翻译的玩家文本可以建立源语言证据，开发用注释、
资源标识和协议字面量不参与结论。

## 推导三类宽度

对话、滚动文本和帮助说明分别由不同窗口与布局约束消费，必须分别调查。先定位真正消费
文本的窗口类，再检查启用插件是否覆盖窗口尺寸、padding、字体、头像区域或换行逻辑。

通常可以从这些位置建立第一批证据：MZ 的 `js/rmmz_windows.js`，MV 的
`www/js/rpg_windows.js`，以及 `plugins.js` 中已启用插件对应的源码。沿
`Window_Message`、滚动文本窗口、`Window_Help`、窗口矩形、padding、字体、头像缩进、
`drawTextEx` 与换行覆盖继续追踪；插件替换或包装这些方法时，以最终启用的调用链为准。

宽度事实表示 ATT 排版使用的“每行最大全角字符数”，不是直接抄录像素宽度。使用实际
字体、控制符和代表性文本在最窄真实窗口中验证候选值。宽度随分辨率、场景或插件命令
变化时，记录适用条件并选择能够解释的保守事实，不把单一数字伪装成所有界面的真值。

## 建立文本载体地图

值得检查的现实材料包括：

- RPG Maker 标准数据库对象及真正被窗口消费的字段；
- Map、CommonEvents、Troops 中实际执行的消息、选择、滚动文本及其他事件命令；
- `js/plugins.js` 中状态为启用的插件，而不是插件目录中存在的全部源码；
- 启用插件通过参数、插件命令、事件参数、Note/meta 或自有 JSON 读取的内容；
- 运行时条件、分支与 locale 选择最终让哪一个值进入界面。

对每类载体同时记录运行时消费者、玩家可见语义、逻辑分组、物理位置和写回位置。对话
Speaker 与 Body、完整选项组、完整滚动文本块可能跨越多个字段；物理位置分散不构成
拆分语义原子的理由。

## 选择 Builtin、Rules 或 Lua

选择依据是真实关系的表达能力，而不是复杂度标签或固定升级顺序。

### Builtin 的责任边界

Builtin 覆盖 RPG Maker 已确认的标准数据库文本、标准消息、选择项、滚动文本、MZ 原生
Speaker，以及可由姓名投影完整且可逆表达的 MV Speaker。先对照
[Builtin 覆盖矩阵](extraction.md#3-builtin-覆盖矩阵)，不要因为文件位于标准目录就
假定其中全部字符串都受支持。

### Rules 的责任边界

以下事实同时成立时，Rules 通常足够：

- 来源能够表示为一个文件、启用插件参数或事件 `code + parameter`；
- 受支持的静态确定路径能够到达最终字符串；
- 必要时只需从最终字符串捕获一个 `text` 跨度；
- 嵌套 JSON 能逐层解码，并按相反边界写回；
- 每个物理位置归属清楚，原文和译文能够由同一 recipe 可逆重建；
- 能够建立准确且互不冲突的 Mutation Claim。

精确能力、字段和工件验证见[规则文件现行规格与编写指南](rules.md)。Rules 的命中数量
不是覆盖证明；仍需检查真实消费者、误收、漏收、分组和写回边界。

例如原值 `<Help:炎之剑的说明>` 有三种不同意图：Rules 省略 `pattern` 时整串是一个
Unit；显式 `(?<text>...)` 时只有捕获正文是 Unit，外壳成为 recipe Literal；保持整串
Unit 再用 Custom Placeholder 时，只保护 Unit 内的外壳，不改变提取身份。若 `<Help:...>`
还涉及 occurrence、多值同步、条件 grammar 或私有事务，则由阶段 Lua 解析、验收并重建
完整 Value，不能要求 Host 根据尖括号外观猜测协议。

### Lua 的责任边界

可信 Lua 有两个不同入口。已有人工候选要补入**现存 Standard 单元**时，使用独立项目
`lua` 命令的 `ctx.standard`：核心按普通 Standard 的完整身份、Lines、源上下文、
Placeholder、语言、去重和 Current 语义验收并原子提交，脚本不读取或构造 state，也不
直接 SQL 修改受管翻译表。

只有现实关系超出 Builtin、Rules 或 Placeholder 的表达能力时，才考虑 Extract、
Translate、WriteBack 的阶段 Lua。若 Lua 只需声明 collection、原子 unit 和写回关系，
优先使用 `ctx.translations`：ATT 负责全局去重、模型协议、并发、state、checkpoint 和
任务记录，Lua 在 WriteBack 仍明确拥有目标映射。典型场景包括：

- 需要递归、过滤、动态对象键或跨文档关系；
- 一个语义事实依赖多个物理节点，或译文必须同步投影到多个位置；
- 是否翻译取决于跨节点状态或游戏私有协议；
- 需要 Rules 契约之外的身份，但每个 unit 可以独立、原子地翻译和提交；
- 静态路径能够命中字符串，却无法表达完整分组和可逆写回。

私有 grammar、跨 unit 原子关系、特殊模型协议或自有恢复状态超出 Managed 契约时，再由
Lua 显式组合 `ctx.translation`、`ctx.llm` 与 `ctx.db`；Host 不自动降级。复杂不自动意味着
需要低级协议。每个启用 Lua 的阶段都必须拥有独立、现实的理由，并明确协议所有者、事务
和幂等边界。独立项目脚本也必须按完整身份定位候选、审查去重传播范围并保持可重复执行。
完整能力见[Lua 技术参考](lua.md)；先查看
[Managed 三阶段示例](lua-cookbook.md#2-managed-三阶段翻译)，再按需参考 Cookbook 中的
低级协议。

选择 Lua 同时意味着允许可信程序装载外部模块，并通过标准库直接访问文件、环境和进程。
调查时必须按[Lua 技术参考的 VM 与路径契约](lua.md#2-vm连接与-ctx)确认真实模块解析环境、
实际动态依赖和受管 API 外副作用；不得假定目标位于项目根内，也不得把直接访问误认为受
ATT 事务、取消或发布管理。

## 证明覆盖与可逆写回

覆盖结论至少应能解释：

- 代表性已提取单元为何是玩家可见文本，分组、上下文和目标为何正确；
- 已知高风险载体为何被覆盖或排除；
- Speaker/Body、`102/402`、滚动文本和嵌套 JSON 是否保持完整语义；
- 不同 owner 或规则的 Mutation Claim 是否竞争同一物理资源；
- recipe 是否能从冻结来源可逆重建写回目标；
- 重复 Extract 是否收敛，失败 owner 是否保持旧快照；
- 从冻结来源生成的候选是否只改变已确认位置并保持未知内容。

数据库中的持久化关系能够证明位置、分组、状态和 Claim 之间是否一致，不能单独证明
运行时可见性。玩家是否看到文本仍由实际消费者或隔离游戏中的界面建立。提取数据和
完成语义见[文本提取现行规格](extraction.md)，候选及写回边界见
[写回现行规格](write-back.md)。

## 高级数据库边界

`project.db` 可用于只读核对 metadata、Standard owner 快照、逻辑组、语义单元、recipe、
Claim 冲突摘要、译文和 state，也可以核对 Managed owner、collection、unit 与成对
translation/state。完整逻辑 Claim 由 Standard group kind、location 和 recipe 重建；
Managed 不建立 Claim。持久化摘要不是完整 Claim 清单，不能用其行数代替覆盖判断。

外部 SQLite 工具不会自动取得 ATT 项目租约。直接修改受管表属于明确授权下的高级修复，
不是普通调查步骤，也不是人工补译入口；人工译文必须通过 `ctx.standard` 交给语义所有者。
其他确需直接修复受管表的情况，先确认没有同项目命令并发运行，建立可恢复副本，在事务
中修改，并在提交前后重新证明当前 schema 与业务不变量。受管 schema 不是稳定扩展 API；
自有扩展应使用可信 Lua 保证的私有命名空间。

直接 SQL 成功不等于业务结果成立。Standard 译文与 translation state、owner 指纹、
group、unit、recipe、完整逻辑 Claim 和持久化摘要必须继续描述同一快照；Managed 的
来源/manifest、collection/unit 与 translation/state 也必须一致。来源可见性和译文质量
仍由对应消费者与验收语义证明。发现不一致时，先确定冻结来源、提取资产、译文或数据库
中哪一方拥有事实，不通过盲目重算校验值掩盖漂移。

项目表关系见[初始化现行规格](init.md#3-当前项目数据库)，SQLite 连接、事务和失败边界见
[SQLite 运行时现行规格](../runtime/sqlite.md)。
