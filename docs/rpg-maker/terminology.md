# RPG Maker 术语表制作指南

本文说明如何为 RPG Maker 当前支持的 MV 与 MZ 游戏制作术语表。重点是从真实游戏
材料中找出值得稳定约束的概念，并写成当前 `Terminology TOML`；它不是字段翻译清单、
提取规则或占位符规则。

精确解析和翻译契约见[翻译现行规格](translation.md)。本文给出判断方法，具体调查范围、
取舍顺序和辅助工具可以随游戏结构调整。

## 1. 先明确术语表实际做什么

Standard Translate 会在每个活动语义单元的原文中查找 trigger。某条术语命中后，当前
请求才会出现对应的：

```text
源文术语 → 目标译名
```

命中采用区分大小写的字面子串，不是正则表达式。一个任务没有命中任何术语时，不生成
术语区。实际命中的术语也会参与对应译文的 translation state；术语译名变化后，受影响
的旧译文不会被静默当作仍然有效。

因此，术语表适合约束“在正文、说明或对话中再次出现时应保持统一”的概念，例如角色、
地点、组织、种族、关键敌人、核心物品、核心技能和重要系统概念。它不负责：

- 决定哪些游戏字段进入翻译；这是 Builtin、Extract Rules 或 Lua 的职责；
- 保存每个结构化字段的最终译文；这些译文属于项目中的标准语义单元；
- 保护控制符、标签或协议外壳；这是内置保护和 Placeholder Rules 的职责；
- 按文件、角色或场景选择不同译名；当前术语契约没有 scope、优先级或多译名。

## 2. 从哪些材料建立候选

较有价值的候选通常来自已经确认会被玩家看到的载体，而不是对所有 JSON 字符串做去重。
可以从冻结来源、Extract 后的标准语义单元、已有译文和运行时消费者中交叉寻找。

| 候选来源 | 值得观察的关系 | 常见候选 |
| --- | --- | --- |
| 说话人与角色数据 | 同一名字如何出现在姓名、称号、对话称呼和人物介绍中 | 角色名、稳定称号、阵营名 |
| 地图与系统文本 | 地图显示名、任务文本和对话是否指向同一地点或制度 | 地名、组织、世界观概念 |
| 技能与状态 | 名称、说明和战斗消息是否表达同一概念 | 核心技能、重要状态、体系名称 |
| 物品与装备 | 名称、说明、获得提示和剧情提及是否互相印证 | 关键道具、装备系列、材料名 |
| 对话与长说明 | 概念出现的说话人、语气、指代和情节作用 | 专名含义、关系称呼、语境敏感词 |
| 已启用插件的可见文本 | 插件参数或命令最终由哪个窗口消费 | 插件引入的玩家可见概念 |

这些类别只是调查入口，不是收录配额。具体字段是否玩家可见、是否已经被提取，以及原文
属于自然语言还是机器协议，仍应回到当前游戏的实际消费行为确认。

结构化字段适合快速提供“有哪些名字和概念”的候选池；对话、说明和事件上下文更适合
回答“它究竟指什么、应如何译、是否需要统一”。只看名称容易得到机械音译，只看正文又
可能漏掉稳定的规范名称，两类证据可以互相修正。

### 从标准结构快速取得候选和上下文

Builtin 已经确认的标准字段可以作为高效入口，但“候选字段”与“最终术语”仍是两回事：

| 候选 | 可一起阅读的上下文 |
| --- | --- |
| `Actors.name`、`Actors.nickname` | `Actors.profile`，以及该角色作为 Speaker 时的对白 |
| `Classes.name` | 角色职业、技能和说明中的实际用法 |
| `Skills.name` | `description`、`message1`、`message2` |
| `Items/Weapons/Armors.name` | 各自的 `description` 及剧情中的提及 |
| `Enemies.name` | 战斗消息、剧情称呼和相关状态 |
| `States.name` | `message1` 到 `message4` |
| Map 的 `displayName` | 当前地图中的事件、任务与地点称呼 |
| System 的 `elements`、`skillTypes`、`weaponTypes`、`armorTypes`、`equipTypes` | 对应技能、装备和说明中的实际语义 |

MZ 的标准 Speaker 来自消息命令 `101.parameters[4]`，紧随的连续 `401` 正文提供人物语境。
MV 没有这个标准字段，应先由当前游戏的姓名投影确认第一条 `401` 中真实的姓名协议，再
使用项目已提取的 Speaker/Body 关系；不要把 MZ 的位置直接套给 MV，也不要把任意第一行
都当成姓名。

这些上下文主要用于理解和消歧，不需要随术语一起写入 TOML。一个名称周围的整段 profile、
description 或对白可以决定译法，但通常不应因此变成另一条长术语。

## 3. 字段译名不等于正文术语

结构化字段的译文回答的是“这个完整字段最终显示什么”，术语表回答的是“模型在其他
原文中遇到这个概念时，应采用什么统一译名”。当前 ATT 没有要求把全部字段译文再复制成
一份外部映射；字段本身会作为标准语义单元翻译和写回。

一个完整字段可能包含：

- 标题、等级、编号或分类前缀；
- 引号、括号、控制符或插件协议外壳；
- 多个专名的组合；
- 一整句说明或菜单提示。

完整字段仍可能需要自然地整体翻译，但不代表它适合作为一个正文术语。术语通常应清洗为
原子、干净、可复用的概念。例如，一个虚构字段 `【蒼月団・北支部】` 可以整体获得符合
界面的字段译文；正文术语更可能只需要 `蒼月団 → 苍月团`，而不是把括号、支部修饰和
整段包装都作为 trigger。若一个字段组合了两个独立专名，可以分别判断它们是否值得收录。

以下内容即使已经获得字段译文，通常也不必进入术语表：

- 完整动作句、长说明或一次性剧情句；
- 仅用来写回界面的编号变体、数值增减标签和临时状态文案；
- 调试项、内部菜单项、文件名、资源路径、代码、ID 和配置值；
- 只出现一次且不会帮助正文理解或统一口径的普通字段；
- 控制符、标签边界及其他机器协议。

反过来，低频并不自动等于不重要。只出现少数几次但承担关键身份、伏笔或世界观含义的
专名，仍可能值得约束。判断依据是译名稳定性和语义价值，不是机械频次阈值。

## 4. 确定一条术语的三个字段

当前格式的一条术语只有 `term`、`translation` 和可选的 `triggers`：

```toml
# 以下名称为虚构示例。
[[term]]
term = "蒼月団"
translation = "苍月团"
triggers = ["蒼月団", "蒼月の団"]
```

### `term`

`term` 是展示给模型的规范源文概念。它宜使用干净、可辨认的源文形式，不携带文件位置、
字段类别、说明备注或协议包装。同一 `term` 在整份文件中只能出现一次。

### `translation`

`translation` 是该概念在目标语言中的统一译名。可以结合姓名写法、人物关系、物品说明、
技能效果、剧情语境和已有字段译文判断，不宜只依据读音机械转写。若正文术语与某个已确认
字段拥有完全相同的源文概念，两处目标译名通常应保持一致。

这不是要求模型在任何语法环境下机械替换字符串。译名仍需在目标句中满足语法、称谓和
语气；术语表提供的是概念口径。

### `triggers`

`triggers` 决定何时把这一条发送给模型。省略时固定等于 `[term]`：

```toml
[[term]]
term = "蒼月団"
translation = "苍月团"
```

显式提供 `triggers` 会完整替换默认集合，而不是在 `[term]` 上追加。因此，仍希望规范
`term` 自身命中时，应把它也写进数组。

适合增加 trigger 的情况包括同一概念存在稳定的完整写法、简称或文字变体，并且这些形式
都应指向同一译名。trigger 宜尽量精确；过短的通用词、单个字母或常见后缀容易在无关
上下文中误触发。

不同字符串即使互相包含也可以同时命中，文件顺序不构成优先级或“最长者胜出”。若同时
命中的两条术语给出冲突口径，模型会收到矛盾提示。因此，嵌套 trigger 应当语义兼容，
而不是用顺序尝试覆盖另一条规则。

## 5. 当前 TOML 契约

术语文件的根必须显式声明 `term`。多条术语使用多个 `[[term]]`：

```toml
[[term]]
term = "蒼月団"
translation = "苍月团"

[[term]]
term = "星紋石"
translation = "星纹石"
triggers = ["星紋石", "星紋の石"]
```

不使用任何术语时，权威空文件是：

```toml
term = []
```

当前解析边界要求：

- `term` 与 `translation` 必填、非空白，且不能带首尾空白；
- `triggers` 省略时使用 `[term]`，显式提供时必须是非空字符串数组；数组中的每个 trigger
  都必须非空白且不能带首尾空白；
- 所有 `term` 全局唯一，所有 trigger 也全局唯一；
- trigger 区分大小写，按字面子串匹配，不解释为正则；
- 未知字段、重复字段、重复身份、零字节文件和仅含注释的文件都会被拒绝；
- 当前契约没有 scope、priority、备注字段、版本字段或多译名字段。

TOML 注释可以记录人工判断，但不会成为项目持久化的术语数据。不要为了保存说明而增加
自定义字段。

Translate 提供 `--terms TERMS_TOML` 时，这份文件完整替换项目数据库中的术语资源；省略
`--terms` 会复用项目当前快照，不会自动清空。需要移除已有术语时，应显式提供
`term = []` 的完整文件。

## 6. 用上下文消歧，而不是扩大规则

译名不确定时，优先寻找能改变语义判断的上下文：

- 这个词由谁说、用来称呼谁；
- 名称旁的说明、效果、图标或分类表达了什么；
- 地图、物品、技能、状态与剧情是否重复引用同一概念；
- 相同写法是否在不同载体中承担不同含义；
- 插件或窗口代码最终怎样展示该值。

当前术语表没有按角色、文件、事件或场景划分 scope。一个短词在不同上下文需要不同译名
时，不能靠条目顺序解决。可选判断包括：

- 找到能够稳定区分含义的更完整字面写法，用更精确的 trigger；
- 把真正独立且原文也可区分的概念写成不同条目；
- 若无法可靠区分，则暂不收录，让完整上下文决定译法，再在结果审核中检查一致性。

同一 trigger 不能同时分配给两个条目。为了“尽量命中”而加入含糊简称，往往比缺少该条
术语更容易误导翻译。

## 7. 判断术语表是否过度收录

术语表条目数接近全部结构化字段的唯一原文数时，通常值得重新抽查。它可能已经从正文
概念词表退化为字段全集镜像。可以随机检查若干条并询问：

1. 这个原文会自然出现在对话、说明、任务文本或其他正文中吗？
2. 如果不提供这条，是否存在真实的一致性或理解风险？
3. 目标译名能否跨出现位置稳定复用？
4. trigger 是否会在无关文本中命中？
5. 这条实际是概念，还是一整个字段、协议壳、编号变体或一次性句子？

只有被触发的术语才会进入具体请求，所以术语总量不会原样塞进每个 Prompt；但宽泛、
重复或无价值的 trigger 仍会给相关请求增加噪声和字符开销，也可能造成不必要的译文状态
变化。精简的目标不是追求条目少，而是让每条都能解释其现实用途。

## 8. 验证术语表

语法通过只证明文件符合契约，不能证明术语选择正确。可根据风险组合以下证据：

- 正向样本：代表性原文确实包含预期 trigger，概念和目标译名与上下文一致；
- 反向样本：常见同形词、协议文本和无关字段不会被过短 trigger 误命中；
- 跨载体一致性：角色名、数据库名称、对话称呼和说明中的同一概念没有互相冲突；
- 请求证据：在可观察模型请求的环境中，术语只出现在实际命中的任务中，且没有矛盾条目；
- 结果证据：译文在句子中自然使用统一口径，而不是生硬替换或破坏目标语言语法；
- 状态证据：修改已命中术语的译名后，相关旧译文被重新判断；未命中的无关条目不应成为
  该语义单元的术语依赖；
- 写回证据：结构化字段和正文最终口径一致，同时控制符、包装和布局仍由各自机制保持。

发现问题时，应先判断来源：候选本身不该收录、译名理解错误、trigger 太宽、存在无法表达
的语境歧义，还是相应文本根本没有被正确提取。术语表只修正术语口径；不要用它掩盖提取
遗漏、占位符错误或写回边界错误。
