# ATT 翻译任务材料规范

这份规范管的是操作者自己创建的东西：任务清单、输入副本、备份、证据和 QA 材料。
ATT 的项目数据库、日志、任务记录、候选和发布恢复文件归 ATT 管理，原样留在原地，
不要手工修改或移动。

清单的工作阶段来自[翻译项目指南](translation-project.md)，失败、取消和状态恢复按
[诊断与恢复指南](diagnosis-and-recovery.md)记录，全量检查与交付证据按
[验收指南](acceptance.md)组织。任务材料只引用这些产品事实，不重新定义它们。

## 1. 选择安全的任务根

优先选用户明确指定、能长期保存的位置，并和以下目录保持距离：

- 原游戏与实际加载目录；
- ATT 发布目录和 Skill 安装目录；
- ATT 发布目录下固定的整个 `projects/`；
- ATT 项目的 `write_back`、`logs`、`task-records` 和恢复目录；
- 最终交付目录和系统临时目录。

可以按以下方式组织，但目录名称不是产品契约：

```text
<任务根>/
  ATT-翻译任务-<项目标识>-<YYYYMMDD>[-NN].md
  artifacts/
    inputs/
    backups/
    evidence/
    qa/
    scratch/
```

用到哪个子目录建哪个；找旧清单时去该去的地方找，别为它扫描整块磁盘。

## 2. 一项任务只有一份清单

- 同一目标的未完成工作继续原清单；
- 同一交付返修时保留旧记录，追加复核 TODO；
- 新游戏版本、新范围或独立输出使用新清单，并引用旧清单；
- 多份清单同时匹配时停止选择，说明身份差异；
- 任务负责人是清单唯一写入者，协作者只写被分配的材料。

TODO 使用稳定编号，例如 `EX-01`、`TR-03`、`WB-02`。完成前先写下可观察的完成标准，
完成后立即记录结果和证据；只做了一部分，就让它保持未勾选。

项目选择与最终验收也是任务工作，不得只记录 Extract、Translate、WriteBack 三个命令。
一个游戏包含多个项目时，同一清单保存跨项目所有权表和联合交付结果，每个项目的运行
状态仍分别记录。

## 3. 材料名称和证据

任务材料使用：

```text
<TODO-ID>-<purpose>-<YYYYMMDD-HHMMSS>[-<RunId-or-sha256-short>].<ext>
```

已被完成 TODO 引用的文件保持原样：不覆盖、不改名、不删除。证据至少记录：

- 绝对路径或 ATT RunId；
- 文件 SHA-256，或数据库查询的项目身份与观察时间；
- 使用的输入、配置、Prompt 或 Lua；
- 它证明的具体事实；
- 它属于权威项目状态、ATT 诊断还是人工 QA。

恢复记录同时写明进程终态、阶段业务结果、状态影响、恢复位置和已读规格，不能只写
“失败后重试”。验收记录写明完整集合、检查数量和未验证项，不能只附几个样本或截图。

文件存在、日志写有“成功”、截图在手，单独都证明不了数据库提交、目录发布或游戏
实际加载；证据要落到权威状态上。

## 4. 配置和翻译资源

- 配置记录实际命令 cwd、固定的 `<att-dir>/config.toml` 绝对路径与 SHA-256，不复制凭据。
- Rules、术语和 Placeholder 保存本轮采用输入的逐字副本与 SHA-256。
- Prompt 修改可能影响多个项目，修改前检查全部使用者和授权。
- Lua 每次记录脚本绝对路径、SHA-256、参数、ATT 结果和提交后权威状态。
- Generic 还要记录外部 JSONL 根、Extract 输入指纹、外部转换工具的身份，以及来源路径到
  JSONL 相对文件、Group、Unit 和写回位置的映射规则。分组发生变化时，同时记录依据和
  影响范围。

`write_back` 会被后续运行替换。想长期保存某轮输出，就把它复制到 ATT 工作区之外，
并记录项目身份和 WriteBack RunId。

## 5. 协作和清理

委派时把话说全：TODO、只读或可写范围、唯一输出路径、是否允许运行 ATT 或发出模型
请求、预期证据和停止条件。每位协作者各写各的路径，互不交叉。

清理只碰 `scratch/` 中未被 TODO、决定或交付记录引用的内容；动手前先确认解析后的
绝对目标确实位于当前任务根内。其他材料默认保留。
