# RPG Maker 外部定义与规则审查

> 状态：输入格式方向已经确认，生产实现尚未切换。本记录保存设计依据与真实样本
> 验证，不替代当前描述已落地行为的现行规格。实现时必须一次性更新 CLI、解析器、
> 校验、测试、示例和现行规格，并把本记录中仍然有效的结论合并到相应规格后删除本记录。

## 1. 已确认的输入格式方向

ATT 自有、以结构化数据表达并由人类或 Agent 直接编写的声明式定义资源统一采用
UTF-8 TOML。当前纳入这一方向的是 RPG Maker 提取规则、术语表、占位符规则，以及
MV 等引擎因插件协议而需要的事件文本解释规则。

选择 TOML 的依据是资源所有权和主要编写方式。PCRE2 可以使用 TOML literal string
避免 JSON 双重反斜杠转义，这是直接收益，但不是把所有含有“规则”含义的数据一概
改成 TOML 的理由。各类定义仍由自己的现实消费者和不变量塑造，不因为采用相同语法
而合并成同一种 schema、同一个文件或同一条处理流程。

以下内容继续使用其协议或权威来源要求的格式：

- RPG Maker 的 JSON 源资产及插件中的嵌套 JSON；
- LLM 请求、响应及透传的严格 JSON `parameters`；
- JSONL 审计、可恢复发布 journal 和其他机器协议；
- SQLite 中用于稳定持久化与哈希的规范 JSON；
- 使用自身语言的 Prompt 文本和可信 Lua 程序。

TOML 只停留在外部输入边界。边界完整解析输入、拒绝未知或重复字段并建立承载不变量
的领域类型；业务模块不接收或重新解释 `toml::Value`。需要持久化的定义由受信领域
类型生成规范机器表示，外部 TOML 与内部规范 JSON 属于不同责任边界，不构成双格式
兼容。

格式切换实行严格单版本原则：外部文件只接受届时现行的 TOML 契约，不保留 JSON /
TOML 双读、按扩展名或内容探测、旧字段别名、迁移、回退或降级。空定义、缺失字段、
未知字段、重复声明和顺序是否具有语义，必须由每类定义的最终规格显式确定，不能依赖
Serde 默认行为偶然形成。

## 2. 本轮真实样本验证的问题

本轮继续使用 `测试集` 中 4 个 MV 和 3 个 MZ 游戏验证以下问题：

1. 事件命令的 `code`、参数位置和 PCRE2 命名捕获是否足以表达插件名字框协议；
2. 可逆写回需要由外部声明哪些事实，哪些配方应由 ATT 从实际捕获跨度自动物化；
3. 标准事件列表、插件参数、Note / Comment、插件命令和额外字段应由内建能力、声明式
   规则或 Lua 中的哪一方负责；
4. 现有提取规则、占位符规则和术语资源是否要求用户重复表达 ATT 已经知道的事实；
5. 哪些候选字段只有假想用途，应从当前外部契约删除。

## 3. 验证方法与可复现脚本

测试集保持只读。验证程序及其规则文件位于被 Git 忽略的
`tmp/rpg-rule-audit/`，使用项目同一 Rust 工具链和 `pcre2` crate，不用另一种正则
实现近似代替 PCRE2。程序完整扫描测试集中的 4 个 MV 游戏和 3 个 MZ 游戏，执行：

旧 `att-mz` 项目只作为领域知识和搜索线索，不作为当前设计的权威来源。本文中的能力
边界、统计和取舍均重新以当前项目源码、真实游戏数据及插件实际消费代码求证；旧项目的
固定 code、文件分区或数据模型没有被直接继承。

1. 以 `deny_unknown_fields` 的受限结构严格解析 TOML，拒绝空定义和未知字段；
2. 以 UTF / UCP 模式编译 PCRE2，并在本机启用 JIT；
3. 遍历标准数据库、Map、CommonEvents、Troops、事件命令、Note、Comment 和
   `plugins.js`；
4. 对任意 `code + parameter` 指向的直接字符串应用规则，记录完整匹配与命名捕获的
   字节跨度；
5. 在同一进程内仅使用物化后的跨度模拟重建原文，再替换 Speaker 并重新匹配；
6. 统计插件参数中的递归 JSON 字符串、非标准 `data/*.json`、命令形状和原生名字框；
7. 用单元测试覆盖 TOML literal string、严格字段校验、重复捕获、重建和重解析。

复现命令如下：

```powershell
cargo test --manifest-path tmp/rpg-rule-audit/Cargo.toml --locked --offline
cargo clippy --manifest-path tmp/rpg-rule-audit/Cargo.toml --locked --offline -- -D warnings
cargo run --manifest-path tmp/rpg-rule-audit/Cargo.toml --locked --offline -- `
    'D:\att\测试集' 'D:\att\tmp\rpg-rule-audit\rules.toml'
```

原型刻意只验证命令参数定位、同进程跨度物化和可逆重建。它没有实现通用结构路径的
反向重编码，也没有验证配方持久化、跨进程交接或真实 WriteBack；这些属于实现阶段的
完成门槛。它更不能仅凭正则往返成功就断言某个捕获在游戏运行时是可翻译显示文本；
这项语义必须继续通过插件源码和相邻数据的现实读写关系验证。

## 4. 样本事实与方法可行性

### 4.1 MV / MZ 的稳定内建骨架

四个 MV 游戏的 `101` 都是四参数消息头，三个 MZ 游戏则通常把原生名字框放在
`101.parameters[4]`。七个游戏的 `401` 都属于某个消息块，没有发现孤立 `401`。

| 引擎与游戏 | `101` 消息块 | `401` 正文行 | 原生 Speaker 非空 | 原生 Speaker 空 / 缺失 |
|---|---:|---:|---:|---:|
| MV / kimochi | 447 | 1,227 | 不适用 | 不适用 |
| MV / SSPV0315 | 77,629 | 150,368 | 不适用 | 不适用 |
| MV / Succubus Academy | 6,360 | 10,849 | 不适用 | 不适用 |
| MV / Princess Honeytrap | 24,091 | 71,174 | 不适用 | 不适用 |
| MZ / ぼくとサキュバス | 17,345 | 59,943 | 0 | 17,302 / 43 |
| MZ / テイルズ・テイルス | 3,571 | 7,435 | 2,152 | 1,419 / 0 |
| MZ / ロリマゾ… | 2,680 | 5,590 | 2,059 | 621 / 0 |

因此，标准事件列表发现、`101 + 401*` 对话块、`102` 选择项、`105 + 405*` 滚动文本、
`320 / 324 / 325` 角色字段以及标准数据库字段都属于稳定的引擎知识，应由 MV / MZ
共享能力内建；外部规则不应重复写 Map、CommonEvents、Troops 的列表长路径。`402`
保存的是选择项的分支副本，不应再次形成独立译文；事件标签和资源文件名也不能因其是
字符串就自动送去翻译。

真实 MZ 还揭示了当前实现缺陷：`ぼくとサキュバス/data/Map017.json` 的
`$.events[12].pages[0].list[8]` 是合法四参数 `101`，测试集中共有 43 个这种消息头；
当前 `src/att_mz/extract/builtin.rs` 无条件读取第五个参数。公共对话模型应接收由引擎
适配器提供的可选原生 Speaker，缺失和空字符串都表示没有原生名字框。

### 4.2 命令内局部投影可以精确、可逆

原型使用两条最小规则：

```toml
[[rule]]
code = 401
parameter = 0
pattern = '(?i)\\n<(?<speaker>[^>]*?)(?::)?>'

[[rule]]
code = 401
parameter = 0
pattern = '◆(?<speaker>[^\r\n]*?)ｔ'
```

全量结果如下：

| 协议 | 命中字段 | 完整匹配 | 原文重建失败 | 模拟翻译后重解析失败 |
|---|---:|---:|---:|---:|
| MV `\n<name>` | 62,660 | 62,662 | 0 | 0 |
| MZ `◆nameｔ` | 10,591 | 10,591 | 0 | 0 |

这 73,251 个字段覆盖了不能靠简单字符串前缀处理的情况：同字段重复标记、空 Speaker、
Speaker 内控制符、标记前已有控制符或空白、标记位于消息块中段，以及一个缺少 `>` 的
畸形近似值。畸形值保持未命中，没有被规则猜测修复。原型按字节跨度拼装外壳和替换
文本，不使用带替换语法的正则 replacement string，因此译文中的 `$`、反斜杠等字符
不会变成替换指令。

MV 的直接证据包括：

- SSPV 有 61,951 个字段、61,953 个 `\n<name>` 标记；两个字段各含两个标记，另有
  一个空 Speaker；
- Princess 有 709 个精确命中，另有一个缺少结束 `>` 的近似值；
- `SSPV0315/www/data/Map065.json` 的
  `events[9].pages[0].list[272].parameters[0]` 同字段重复两次名字框；
- `SSPV0315/www/data/Map097.json` 的
  `events[42].pages[0].list[3886].parameters[0]` 在名字中包含颜色和字体控制符；
- `プリンセス・ハニートラップ/www/data/CommonEvents.json` 的
  `[724].list[156].parameters[0]` 在名字框标记前还有其他控制符。

结论是：对于“一个已知命令的一个直接字符串参数内，静态定位一个显示 Speaker”这一
窄职责，`code + parameter + PCRE2 pattern` 足够。外壳、精确跨度、重复与冲突检查、
还原配方和译后验证都应由 ATT 固定承担，不应继续变成外部字段。

### 4.3 机械可逆不等于语义可翻译

`ぼくとサキュバス` 的 10,591 个 `◆nameｔ` 虽然全部通过重建，但插件源码证明
`name` 是运行时查找键，而不是应直接翻译的显示名：

- `js/plugins/MessageAutoReplace.js` 用 `replaceList[].targetText` 构造正则，再以
  `replaceList[].text` 替换显示文本；
- `js/plugins/PlayVoice.js` 用 `voiceList[].nameStr` 匹配首行并选择语音计数器；
- 1,802 条 code 357 的 `parameters[3].voiceIDs` 还在嵌套 JSON 中保存同类
  `nameStr`。

安全的简单方案是冻结 `401` 中的标记、`targetText`、`nameStr` 和语音 ID，只翻译
`replaceList[].text`。如果产品要求把这套协议正式投影成 Speaker 叶，就必须同时理解
并关联多个来源，应交给 Lua；不能给简单规则继续增加联动、身份、优先级或同步字段。

这项反例建立了重要不变量：规则作者选择的捕获必须是该来源真正拥有的显示文本。
“捕获组名为 `speaker`”只能声明投影意图，不能替代对运行时身份的验证。

### 4.4 Speaker 协议不都局限在一个字符串内

另外两个 MV 样本给出了简单规则的停止线：

- kimochi 的 171 / 447 个消息块把固定名字 `バニー淫魔` 放在第一条 `401`，正文从
  下一条 `401` 开始。游戏专用的精确姓名规则可行，但“短首行都是姓名”需要消息块
  上下文，不能仅看当前字符串猜测。
- Succubus Academy 用 code 355 的 `$n="物書き/mal"` 建立后续消息状态；有 916 个
  `101` 与这类前置赋值相关，还存在清空、只切换样式、脸图、动态 actor / enemy 名称。
  PCRE2 可以捕获字面量，却没有定义状态持续、分支、循环、公共事件调用和向后续消息
  附着的语义。

因此“允许任意 code”是有意且正确的定位能力，但任意 code 本身不产生统一业务语义。
跨命令状态应由一个确有现实消费的窄块级能力承担，或直接交给 Lua；不能把
`code + parameter + pattern` 描述成任意事件脚本解释器。

### 4.5 结构路径和嵌套 JSON 是必要复杂性

七个样本的启用插件参数中，原型分别发现下列可继续解码的 JSON 字符串容器：

| 游戏 | 可解码 JSON 字符串容器 |
|---|---:|
| MV / kimochi | 0 |
| MV / SSPV0315 | 437 |
| MV / Succubus Academy | 6 |
| MV / Princess Honeytrap | 93 |
| MZ / ぼくとサキュバス | 2,072 |
| MZ / テイルズ・テイルス | 78 |
| MZ / ロリマゾ… | 3 |

具体可见文本证明它们不是为了未来预留：

- Princess 的 `SceneCustomMenu.Scene1.WindowList[2].CommandList[0].Text` 需要连续解码
  5 层 JSON 字符串才到达 `はい`；
- SSPV 的 `YEP_QuestJournal` 有 34 个非空 `Quest N` 参数和 505 个 Title、From、
  Description、Objectives、Rewards 等可见叶；
- MZ 的 `Ayatam_HighQualityQuestSystem` 单个 Quest 数据库就有 224 个名称、正文、
  目标、委托人和帮助文本叶；
- Princess 的 `Mano_InputConfig.GamepadIsNotConnected` 最终叶本身仍是 JSON 编码的
  标量字符串，插件源码确实对它调用 `JSON.parse`。

所以小型结构路径、固定与任意数组下标、沿路径逐层解码、反向重编码和精确写回配方都
应保留。当前实现只在路径尚需继续时解码字符串，不能自然选择“最终叶仍是 JSON 编码
标量”的情况；精确参数名也会让 `Quest 1` 到 `Quest 48` 大量重复。后者是否增加一种
受限批量键选择，仍需在最终 schema 设计时与直接交 Lua 的成本比较；不应因此引入完整
JSONPath、递归搜索、过滤表达式或通用条件 DSL。

### 4.6 外部规则确实需要覆盖其他局部来源

样本还证明了以下现实消费：

- SSPV 有 4,926 条非空 `code 356: GabText ...`，另有 13 条 `Gabtext` 大小写变体，
  合计 4,939 条；Princess 有 24 条 `code 356: D_TEXT ...`。它们适合命令局部
  PCRE2，而同 code 的资源和控制命令必须留在规则之外；
- `ぼくとサキュバス` 有 105 条 `DTextPicture::dText`，其中 95 条含日文，适合
  code 357 参数对象内的精确结构路径；code 657 只是编辑器注释，不应提取；
- SSPV 的非标准 `Disciplines.json`、`Recipes.json` 有可见 `[].Name`，精确文件加路径
  足够安全，强制 Lua 过重；
- Succubus Academy 的 Note 含多行 `<SG説明:...>` 与 `<DESC:...>` 可见内容，适合
  文件、路径和 PCRE2；专用 `<name:value>` 匹配语言没有必要；
- MPP ChoiceEX 的 31 个 `108 + 408*` 选择帮助块（MV 28 个、MZ 3 个）必须先识别
  块头，不能把所有开发注释一并翻译；
- code 122、355、655 中确有 JS 字符串，但也混有拼接、条件、日志、资源 ID 和代码。
  在没有 JS 字符串 codec 时，正则无法安全处理引号与反斜杠，应交 Lua。

同样，大量“看起来像日文”的内容实际是图片文件名、气泡枚举、插件参数 ID、跳转标签
或语音键。外部规则的价值正是让作者精确选择已验证的来源；项目不应提供“递归提取所有
日文字符串”的自动模式。

### 4.7 面向最终游戏翻译的效力

规则系统是否有效，不能只看它能表达多少格式，而应看它是否以较少作者负担覆盖主要
玩家可见文本，同时避免破坏运行时身份。按这一标准，本轮得到的可复现基线是：

| 高价值翻译入口 | 全测试集数量 | 建议责任方 |
|---|---:|---|
| 标准消息块 | 132,123 | Builtin / 共享对话能力 |
| 标准消息正文行 | 306,586，孤立项 0 | Builtin / 共享对话能力 |
| 标准选择项 | 13,175 | Builtin / 共享事件能力 |
| 标准滚动文本行 | 171 | Builtin / 共享事件能力 |
| MZ 原生非空 Speaker | 4,211 | MZ 适配器 + 共享对话能力 |
| MV 内嵌名字框字段 | 62,660 | 一条命令局部规则 |
| kimochi 精确首行 Speaker | 171 | 窄的消息块规则或游戏 Lua |
| `GabText` / `D_TEXT` | 4,939（含 13 条大小写变体）/ 24 | 两条命令局部规则 |
| `DTextPicture::dText` | 105，其中 95 条含日文 | 一条插件命令结构路径 |
| 已确认 SG Note 值 | 288 | 文件 + 路径 + PCRE2 |
| ChoiceHelp 块 | 31 块、69 条续行 | 块级能力或 Lua |
| 非标准 JSON 可见 `Name` | 39 | 精确文件 + 路径 |

插件参数规则还有更高的单规则收益：SSPV Quest 参数中已确认 505 个可见叶，MZ Quest
数据库中已确认 224 个可见叶；Princess 的一个菜单路径可以穿过 5 层编码到达最终按钮
文案。结构路径和嵌套 JSON codec 因而直接决定一个游戏是只能翻译主对话，还是连任务、
菜单、帮助和插件 UI 也能完整翻译。

这个结果支持“非常有效”，但有效的原因不是把所有难题都丢给用户：

1. 数量最大的标准对话、选项和滚动文本不需要规则，开箱即覆盖；
2. 一个局部规则可以覆盖几十到数万处同一插件协议，作者只写 ATT 无法知道的选择事实；
3. 精确来源选择避免把资源名、跳转标签、语音键和编辑器注释误翻；
4. 复杂但低通用性的跨命令或代码语义仍有 Lua 出口，不会为了保持 schema 简单而永久
   丢失这些文本；
5. 最终实现应在 Extract 时物化捕获跨度和逐层 JSON 解码配方，使后续翻译和 WriteBack
   不再依赖外部规则；本轮原型只证明了前者的同进程可行性。

截至本轮，可以确认的是设计方法对真实游戏翻译具有高覆盖、高复用和可控误提取风险；
尚不能声称生产效果已经成立，因为 MV 纵向切片、公共化后的真实写回和游戏启动验证还
没有实现。后续实现的完成门槛应包含：

- 对 7 个样本执行真实 Extract，确认上述入口都形成正确的 Body / Speaker / 结构字段，
  身份与资源字段保持冻结；
- 在 `tmp` 中对游戏副本应用包含引号、反斜杠、换行和控制符的确定性伪译文；
- WriteBack 后重新解析全部 JSON 和插件嵌套 JSON，确认未选字段不变、还原配方全部
  消费、规则文件无需再次读取；
- 至少启动每种代表协议的游戏副本，验证名字框、语音、任务菜单、选择帮助和普通对话
  仍按原协议工作；
- 最后再用真实模型翻译评估文本质量。模型措辞质量与规则定位 / 写回正确性分别验收，
  不能用其中一项代替另一项。

## 5. 对现有外部定义的过度设计审查

以下是本轮样本与源码共同支持的审查结论，不是已经确认的最终 TOML schema。

### 5.1 Extract Rules

当前 `notes`、`event_lists`、`plugin_parameters`、`plugin_commands`、
`standard_fields` 五分区把必要能力和来源仪式混在了一起。

应保留：

- 精确文件、插件和结构路径；
- key、固定 index、任意数组 index；
- 嵌套 JSON 解码与反向重编码；
- 字符串内 PCRE2 捕获；
- 精确位置、来源类型、非重叠、零宽匹配、重复目标等失败保护；
- Extract 时物化、WriteBack 时不再解释外部文件的还原配方。

应删除或重塑：

- `event_lists` 要求用户重复标准 Map、CommonEvents、Troops 路径，并以空标签数组作为
  “只供插件命令路由”的魔法值；
- `plugin_commands` 硬编码 code 357 和参数 `[0] / [1] / [3]`，把 MZ 专有协议冒充
  通用规则；
- Note / Comment 专用 `<name:value>` 语法，与 PCRE2 形成第二套更弱的匹配语言；
- 普通路径规则拒绝非标准 `data/*.json`，迫使简单明确的叶使用 Lua；
- 不同分区暗含不同的“必须至少命中一次”语义。应统一行为，不应再增加 `required` 字段；
- 重塑时也不应把当前内部可由来源、路径和规则序号推导的 `label`、`field_name` 暴露
  成新的必填作者字段。

内部仍然必须区分普通 JSON 值、Note 捕获和 Comment 捕获，因为三者的编码和写回位置
不同；简化外部写法不等于把受信内部位置降格成一个无类型 `path + pattern` 字符串。

### 5.2 Placeholder Rules

- `pattern` 是现实必需字段。测试集中同时存在 `\F[...]`、`\fb`、`\fi`、
  `\ii[...]` 等插件协议，宽泛的“反斜杠加字母”会吞掉紧邻的自然文本。
- scope 过滤有价值，但每条必填非空 `scopes` 数组过重；缺席表示全局、存在时才限制，
  是更易写的候选语义。
- `label` 当前只影响 token 文本、诊断和 state，没有样本证明人类命名能改善结果；倾向
  由 ATT 使用规则序号生成不透明 token 并删除该字段。
- “保护外壳、翻译内部”能力可以保留，但无需再写 `translate = "text"`；固定约定唯一
  `(?<text>...)` 捕获即可表达，缺席则保护整个匹配。
- 跨规则重叠直接失败比按文件顺序静默切碎低优先级匹配更安全，也不需要 `priority`。

这些是下一层 schema 的候选简化，仍需在修改现行契约时一起确认。

### 5.3 Terminology

`term` 和 `translation` 是直接消费的核心事实；别名触发能力也有现实意义。但多数现有
样本只是重复写 `triggers = [term]`。候选简化是：缺席 `triggers` 时固定使用 `term`
自身，只有别名或不同触发文本时才显式提供数组。当前没有证据支持再增加 scope、正则、
优先级或按上下文选择多个译名。

### 5.4 MV Speaker 与命令局部规则

对于单字符串内名字框，`code`、`parameter`、`pattern` 正好分别表达命令、直接字符串
参数和插件协议，三者都必要。无需增加 `label`、`scope`、`translate`、`render`、
`priority` 或版本字段。规则只声明事实，ATT 固定负责：

- 遍历标准事件列表并按规则选中命令；
- 要求唯一、参与匹配的 `speaker` 命名捕获；
- 冻结完整匹配内的外壳，把匹配外文本保留为正文；
- 空 Speaker 原样保留但不建立翻译叶；
- 多次匹配、不同 Speaker、规则重叠和译后形状变化的明确失败语义；
- 保存精确还原配方并在写回后验证。

这里仍有一项必须留给下一层决定：同一个最小命令定位机制可以支持 `GabText` 等正文，
但 `speaker` 和 `text` 捕获具有不同的领域结果。最终契约应给它们固定而有限的捕获 ABI，
不能因为共享 `code + parameter + pattern` 就把任意命令的剩余文本一律解释成对话正文。

### 5.5 不合并成一个大规则文件

提取定位、占位保护、术语资源和 Speaker 投影虽然都适合 TOML，但它们拥有不同消费者、
校验、生命周期、持久化和写回责任。共同外部语法不构成共同 schema；把它们合并会制造
更多可选字段和非法组合，反而是新的过度设计。

## 6. 结论与下一层设计停止线

外部化方向正确。插件作者创造的局部文本协议不可能全部内建，让用户或 Agent 通过
TOML + PCRE2 / 结构路径声明这些事实，能覆盖大量真实游戏，并且全量样本已经证明局部
跨度可以精确物化和无损还原。

但当前 Rules 的评价不是简单的“功能太多”：它在外部写法上过度复杂，在真正能力上又
被五分区和 code 357 限得过窄。正确的简化不是删除结构路径或嵌套 JSON codec，而是让
作者只表达 ATT 不知道的游戏事实，把引擎路由、位置类型、编码、还原、冲突和验证收回
ATT。

```text
引擎稳定、跨游戏一致的语义                -> Builtin / MV-MZ 共享能力
单个已知字段内的静态、局部、可逆选择       -> TOML Rules + 路径 / PCRE2
跨命令、跨字段、跨文件、身份同步或代码语义 -> Lua
```

下一层可以围绕三种经过样本证明的最小来源选择继续设计，但此处不预先固定最终字段名：

1. 命令局部：选择 `code + parameter`，再以 PCRE2 选择语义跨度；
2. JSON：选择精确文件和小型结构路径，部分字符串才增加 PCRE2；
3. 插件参数：选择插件、参数和小型结构路径，复用嵌套 JSON codec。

规则系统到此停止，不加入通用 `where`、跨来源 join、状态机、脚本表达式、优先级、递归
搜索或完整 JSONPath。确有高频且跨游戏一致的块级协议时，再以真实消费把它提升为窄的
共享能力；单游戏复杂协议直接使用 Lua。
